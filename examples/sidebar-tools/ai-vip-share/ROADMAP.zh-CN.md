# AI VIP Share 网站快速登录与 Cookie 会话方案

日期：2026-10-30。状态：**按用户最新纠偏修订的设计提案，运行功能尚未因本文获得验证**。

**核心是方便、快速地登录网站，通过现有受控 Cookie 能力设置已授权会话。AI 网站只是首批场景，网站目录、会话模型、写入和恢复流程不绑定 AI 行业。** 保留 AI VIP Share 名称、安装身份与既有功能。

本文是后续设计与多网站演进的唯一方案入口。[README](README.zh-CN.md) 保存当前开发与历史证据；[历史设计](DESIGN.zh-CN.md) 和前版“两个 AI 网站权益查询”目标均不覆盖本次快速登录优先级。会员、兑换和代理继续保留，但不是每个网站都必须实现的基础业务。

## 1. 核心与可选模块

| 层次 | 功能与关系 |
| --- | --- |
| 通用核心 | 网站目录、目标页打开/选择、已授权会话取得、Cookie 预检/设置、结果核验、未知结果恢复 |
| 网站差异 | 固定目标、Cookie 作用域、验证方式、额外登录步骤；仅有实际差异时增加固定适配代码 |
| 会话来源 | 先复用现有服务端交付；其他明确授权来源按需求增加，不把新建导入/Vault/账号池当本轮前置 |
| 可选商业模块 | 会员、兑换、商品、分配规则；使用该来源时仍遵守真实授权，不硬编码为所有 Cookie 设置的通用门槛 |
| 可选网络模块 | 原受控代理仅在需要时使用，不以 START 为设置 Cookie 前置，不因通用化扩大代理范围 |
| 可选观测模块 | AI 套餐/额度/历史独立演进，普通网站接入不需要额度 API 或 AI Provider |

Cookie 不是所有网站唯一的登录条件。需要 localStorage、设备绑定、多因素认证或人工挑战的网站，明确提示额外步骤或能力未支持，不伪造“写入成功即登录成功”。

## 2. 主要用户流程与界面

**原「扩展 → AI VIP Share」入口 → 选择网站 → 获取已授权会话 → 核对目标与账号摘要 → 原可信入口确认精确 Cookie 批次 → 打开/刷新正确目标页 → 核对登录结果。**

建议主界面先展示“网站与快速登录”，再展示所选网站的会话状态与恢复；原会员、兑换、记录、商品与代理保留为可发现的辅助区。当前布局存在并行修改，后续 owner 先核对实际代码和归属，再最小调整，不能用新设计覆盖未确认的运行改动。

每站按当前阶段提供“获取网站会话 / 设置并打开网站”等主动作，同时始终允许用户主动“打开网站”，便于首次进入目标页并完成必要网站授权。旧 journal 的 success 只证明上次设置结果，不能据此推断当前会话可用。切站、查看详情、刷新列表不隐式写 Cookie、兑换或 START。

状态区分未配置、正在获取、待确认、正在设置、已写入待核验、登录已核验、过期、部分成功、结果未知和权限缺失。只有真实验证支持时显示“登录已核验”；没有程序化验证时显示“已设置，请在目标页核对”，不以 HTTP 200 或 Cookie 回读代替网页登录事实。

安装后不增加第二次通用启用，也不重复索要已有合法授权。缺失 Chrome 权限、网站 write 授权和每批真实确认继续走原可信链；便利性通过减少冗余步骤实现，不隐藏必要确认。

网站选择器不是页面授权。需要页面上下文时先打开/选择正确目标页，再由原 SDK 核验 Origin、Document、Store 和权限；导航或文档变化后重新核对。新增 UI 沿用 OpenDesk Tokens、公开 Shared UI、单 React Root，正常 Mac 窗口和默认缩放验证键盘、取消、返回及焦点。

具体身份按[现行公开 Cookie 合同](../../../docs/api/browser-sdk-execution-manual.zh-CN.md)区分：installed-tool `setMany` 绑定安装身份、网站 grant、Origin、Store、Partition 和精确批次；强 Document 绑定的 Host-only approve/execute 不是沙箱公开 API。涉及激活链接或页面上下文的步骤继续重核真实 Document，不把该保护冒称为所有 `setMany` 调用的公开保证。

### 2.1 首屏的最小信息与动作

保留原名称和导航，首屏按“网站 → 当前会话 → 主操作 → 更多服务”的顺序展示。无需新增一级导航、会员总览或工程配置表单；普通用户只需要识别网站、来源和目标账号。

| 区域 | 用户看见的内容 | 行为 |
| --- | --- | --- |
| 网站选择 | 固定目录中的名称和主机；未配置站点标可理解的原因 | 选择只更新展示；独立“打开网站”不依赖写入成功；没有任意 URL/Domain/SDK 命令输入框 |
| 当前会话 | 来源名称、脱敏账号、当前状态；无来源时“暂无可用会话来源” | 来源需要兑换时提供原“前往兑换”入口；普通来源不出现必须先开通会员的提示 |
| 已取得交付 | 目标主机、脱敏账号、将设置的 Cookie 数量和覆盖提示 | 主按钮“设置并打开网站”进入原可信精确批次确认；取消清除未提交交付并返回，不再叠加工具自建确认弹窗 |
| 设置结果 | 逐项结果与“已设置，请在目标页核对”或对应失败/未知事实 | 成功后打开固定目标；无法打开保留“打开网站”，不会重写；未取得可靠登录证据时不出现成功登录徽标 |
| 更多服务 | 原会员、兑换、历史、商品与客户端入口；所需代理状态 | 均可发现；已持有/释放待确认的代理 STOP 不随选站、无会员或来源断线隐藏 |

必要的恢复提示紧邻当前会话；不可归站的旧未知记录才显示全局恢复提示。账号、权限与未知结果不能只用颜色表达。取消/返回后焦点回到原动作；正常网站选择不会触发输入草稿丢失，正在写入时保持当前目标并说明等待。包摘要、epoch、requestId 与调试账本留在现有诊断，不作为普通登录表单字段。

## 3. 网站中立的数据与扩展模型

以下是待实施的业务模型，不是已经存在的 SDK API。

| 概念 | 最小内容与边界 |
| --- | --- |
| SiteDefinition | siteId、显示名、固定目标 URL、必要 Cookie 范围、可选验证方式、适配版本；无 AI 类型白名单，但实际操作仍受原 Authority 限制 |
| SessionSource | sourceId、来源类型、受信服务身份和来源授权；先复用现有交付，不读取其他个人数据 |
| SessionDelivery | deliveryId、siteId、sourceId、目标、有效期、账号/分配代次、Cookie payload；秘密仅在必要短时业务内存持有 |
| LoginAttempt | attemptId、来源/网站/目标作用域、状态、逐项回执与核验状态；写前持久化非秘密记录并回读 |
| OptionalEntitlement | 来源要求时关联会员/兑换/分配；不能要求普通网站接入这些商业模型 |

记录隔离至少覆盖 source/serviceOrigin、siteId、account/assignment 与 operationKind，再绑定真实目标；安装包摘要、epoch、grant 和页面身份继续由原 Authority 核验。字段不适用时须定义明确语义，不能用空值混合不同身份。两站返回相同 deliveryId/accountId 时不得互认。

### 3.1 网站声明与来源授权分开

网站声明随工具源码审阅发布，至少包括稳定 `siteId`、`label`、固定 `targetUrl`、允许的 Cookie 槽位与属性、允许的 `sourceId` 和核验方式。`siteId` 不从网页标题、当前 URL 或远端响应猜测；普通站没有必填的 `aiType`、套餐或额度字段。当前工具仍只接受目标自身的 Host/Domain，暂不顺带开放父域 SSO、多 Origin 批次或远端自选 Store/Partition。

公开 `setMany` 允许省略行内 `storeId` / `partitionKey`，但省略不证明工具已获知真实上下文。工具内部槽位元数据可以显式使用 `{storeId:null,partitionKey:'unresolved'}` 表示两项均未解析，不能将此标记发送给 SDK，也不能把它改成 `"0"` 或已知非分区。未解析与任意已知上下文均可能重叠；仍可依据真实 Host/Path 证明不相交，不能依据未知 Store/Partition 判定隔离。具体已解析上下文必须来自合法原授权入口，不从远端或测试服务自报。获取真实 context 的公开查询需要 `browser.cookies.read`，本轮没有新增该能力；尚未证实必须修改 SDK，保持 `SDK_GAP_NOT_PROVEN`。

来源声明固定其 `sourceId`、服务 Origin、既有请求端点和授权策略。仅选择网站或收到一份格式正确的交付不构成来源授权。以下是**工具内部待实现的分支**，不是新 SDK 方法，也不是可以由远端随意切换的权限开关：

| 来源策略 | 取得与写前必须验证 | 不要求的内容 |
| --- | --- | --- |
| 现有商业分配来源 | 真实绑定账号、当前公司/分配/兑换代次及服务端有效授权；复用现有会员与分配核验 | 不把该策略扩成所有站点的通用门禁 |
| 普通受控来源 | 该来源真实的主体身份、目标站点授权、当前会话/授权代次和有效期；无合法授权则拒绝 | AI 类型、兑换记录、商品、会员额度、代理租约 |

普通来源不能用伪造一张“有效会员卡”适配旧流程，也不能通过缺省 `requiresMembership:false` 直接放行。先提供该来源可验证的授权响应，再进入同一个 Cookie 预检与写入流程；服务端仍决定允许交付哪个账号。当前没有配置的普通来源显示“来源未配置”，不退回商业端点或本地缓存秘密。

### 3.2 身份、时钟和短时交付

内部操作作用域按固定顺序编码为结构化元组：`[sourceId, serviceOrigin, siteId, subjectId, authorizationRevision, operationKind, targetUrl]`。字段逐项校验，不用简单字符串拼接；商业分配额外绑定 `companyId`、`redemptionId` 和 `sharedAccountId`。`deliveryId` 与 `requestId` 仅在该来源/站点/授权代次内解释，不能单独用作全局主键。

没有账号/分配概念的来源使用经固定策略定义的带类型身份（例如已验证的来源授权主体与“无分配”状态），不能把缺失字段统一编码为空字符串。单次意图另绑定声明策略版本、选择代次和实际可用的页面身份；防重历史不随切站、账号变化或分配更新清空。

每次获取捕获所选网站、来源、服务修订与选择代次。返回时及写前重新核对；A 的迟到响应不得填入 B，切站时清除 A 的未提交秘密。来源时钟独立采样，沿用服务端时间加单调经过时间的短时估算；不能再依靠全局会员 `snapshot.serverNow` 给普通网站计时，也不能让旧响应倒拨时钟延长交付期限。

交付提交截止与 Cookie 生命周期分别校验：交付过期禁止新的写入，但不表示此前已安装 Cookie 自动失效；Cookie 尚未过期也不能证明来源授权或实际网站登录仍有效。

React 只接收脱敏目标、账号摘要、状态与逐项回执。Cookie payload 保留在现有控制器短时内存，取消、失效、切站、卸载或提交后清除；不得存入 React props/state、持久 journal 或导出。恢复时只能重新查询当前来源授权和非秘密事实，不能从旧 journal 重构 Cookie 请求。

### 3.3 写入状态与登录状态分别记录

| 用户动作 / 事实 | 设置状态与主操作 | 登录状态 |
| --- | --- | --- |
| 选择网站或重开 | 只读恢复；可打开固定目标、主动获取会话 | 未核验；旧观察只能标上次核验时间 |
| 获取成功 | 待确认；核对目标、来源、脱敏账号与批次范围；取消零写入 | 未核验 |
| 用户确认 | 写前 CAS 与回读成功后才调用原 `setMany`，等待期间禁用重复提交与切站 | 未核验 |
| 全批 `saved` 且 `verified` | 已设置；打开正确目标页，失败时保留“已设置，网页未打开” | 待在目标页核对 |
| partial / unknown / 回执丢失 | 保留逐项事实及写入锁；只允许核对，不提供一键重试 | 未确定，不能因页面碰巧显示某账号而解除锁 |
| 网站完成可靠核验 | 不改写 Cookie 批次回执 | 显示已核验的脱敏身份、时间与核验方式 |
| 仅用户人工核对或需 MFA | 保留“已设置”事实 | 明确标“用户已核对”或“需要额外登录步骤”，不冒称程序核验 |

选择网站、查看历史、刷新来源都不产生 Cookie、兑换或代理副作用。获取来源会话应幂等绑定当前 requestId；不能假定重新获取永远无副作用。打开/刷新使用固定且属于当前操作的目标，不能把成功回执用于另一个网站或任意活动标签页；没有可靠网页核验能力时，当前阶段以打开目标供用户核对结束，不新增 DOM 抓取权限。

普通新增网站尽量只增加经审阅的声明与定向验证；仅确有解析/验证差异时增加工具内固定适配。远端不得以配置下发可执行 JS、任意 SDK 命令或 PAC 脚本。支持更多网站不等于允许任意来源扩权。

## 4. 当前实现与最小改进

2026-10-30 上次观察：工具有 React 单 Root 与 DOM 兼容控制器；Cookie 使用原 browser.cookies.setMany，已有精确目标校验、写前 journal、逐项回执、unknown/partial 阻断和分配代次检查。现有会话取得与会员快照耦合，生产 COOKIE_TARGETS 为空；应区分通用设置能力和可选商业来源，不能简单删除来源授权。

实施分两步：先在原处理器引入捕获的网站/来源上下文并固定相关回归，再调整网站选择与展示次序。无需先把完整 `main.js` 拆成多层架构；也不将只被测试调用、产品未接入的通用模型标为已实现。

## 5. 会话冲突与恢复

保留 name/domain/path、Secure、HttpOnly、SameSite、有效期、Store、Partition，以及涉及页面步骤的 Document 和既有授权检查。一次 batch 只作用同一批准目标与上下文；跨目标不能拼批。多批并非原子事务，超预算先明确限制/缺口，不自动拆批重放。

同一 Profile 中，同 Store 和 Cookie 作用域的同站标签页会共享会话；siteId、标签页、工具实例不是账号容器。不得静默覆盖用户现有登录；共享身份域也按真实作用域检测重叠，不能仅看 siteId。同站多账号同时隔离不是本轮默认能力。

| 情况 | 结果与恢复 |
| --- | --- |
| 全批已确认设置 | 保存逐项事实并进入登录核验，不直接宣布网页登录成功 |
| partial/unknown 或丢回执 | 保留 journal、停止后续写入、不自动重放/换来源 |
| 写前存储或回读失败 | 不提交副作用，提示恢复记录不可用 |
| 切站、换账号、导航、撤权与晚响应 | 旧意图失效，不覆盖新状态；已发生的宿主副作用沿原 SDK 对账 |
| 旧 journal 可可靠归站 | 迁移至对应作用域，原未知锁不解除 |
| 旧 journal 不能归站或迁移失败 | 保留原记录和必要全局写入锁；新结构回读成功前不切入口、不删旧数据 |

工具撤权、本地清理、第三方网站端登出分别记账。不清空用户整站 Cookie，不强写旧快照覆盖新登录；没有归属/上游失效证据不承诺“已登出”。原代理 STOP 独立保持可用，Cookie 设置不自动 START。

### 5.1 Cookie 作用域冲突的判定

记录隔离和浏览器会话隔离是两件事。对同一个 Store/Partition，比较 Cookie 名称、规范域与 hostOnly 语义、Path 及实际目标匹配范围；端口不隔离 Cookie。不同 `siteId` 或不同 Origin 不能自动判定安全。相同主机的 `/session/` 和 `/workspace/` 也可能被 `/` Cookie 或父域 Cookie 同时覆盖。

先由原 Host 继续核对批准的精确批次。已知已有账号、重叠域/路径或无法确认冲突时，在写前明确提示覆盖风险并要求原可信确认；没有必要的读取授权时显示“无法核实当前账号”，不能按“空白站点”处理，更不新增 Cookie 明文读取。无法安全替换完整已批准槽位时停止，不扩大批次、清空整站或自动回滚。新增范围识别失败保留保守锁。

### 5.2 旧记录迁移与锁的释放

仍以原 `aiVipCookieDeliveryR137` 和安装态存储为入口。候选升级不得仅因为包版本或选站不同跳过旧记录；旧包 v1 记录不包含网站与来源声明时，按获审固定映射核对 `serviceOrigin`、`targetUrl`、账号及可用范围。不能可靠推断的字段保留为“旧记录归属未确定”，不补造默认网站。

1. 先读取并校验旧值和 etag；读取失败、未知格式或无从归站时保留原值和全局写入锁。
2. 可可靠归站时，保留 attempt、逐项回执、seen 与原 unknown/partial 状态，用原 CAS 一次写入新版容器并完整回读；并行实例 CAS 失败只重读，不合并猜测或删除旧记录。
3. 迁移未确认前继续旧入口的保守锁；新版回读确认后才切换读取分支。旧 `seen[]` 不含逐条来源/目标身份，不能因记录头可归站就把整个 seen 归给该站；保留为兼容防重屏障，不按新站重复发放或自动裁剪。unknown/partial 及其证据不受普通 TTL 淘汰。
4. 完成可靠归站后，仅当 Store/Partition/域/Path 不重叠已有充分证据，才可让无关站点操作继续；证据不足维持全局锁。单条 CAS 防重不等于多个网站批次原子提交，当前先串行写入。

网页人工登录成功只解决登录核验，不足以证明未知批次没有覆盖其他 Cookie。未知结果的锁只能经原 SDK/可信对账能力得到确定结果后解除；若当前没有该能力就保留锁并说明，不能新增“忽略并重试”按钮。
