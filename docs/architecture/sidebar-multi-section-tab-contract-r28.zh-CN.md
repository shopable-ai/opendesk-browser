# OpenDesk Browser · Side Panel 多功能区 Tab 布局契约 R28

日期：2026-10-13。状态：新增的 **Side Panel 组合/信息架构规范**，适用于「我的」「工具」等在同一个 Tab 内包含多个功能区、列表、详情、表单或设置的可信 UI。

**规范层级和唯一权威：**
- 跨界面尺寸、颜色、空间、缩放及隔离原则仍由 [R27](ui-layout-conventions-r27.zh-CN.md) 决定；本文件**不定义第二套 Tokens、主题或 CSS Reset**。
- Side Panel 原语、单一 gutter、工具 iframe 及布局密度由 [R20/R26](sidebar-design-system-r20.zh-CN.md) 决定；本文件只规定一个 Tab 内多元素如何分组、切换与排序。
- 基线源码：`src/ui/tool.html`、`src/ui/sidebar-tools.js`、`src/ui/tool-shell.css`、`src/ui/design-{tokens,system}.css`。
- 第一消费者：`#workbench-tools`；第二消费者：`#workbench-tasks → #scheduled-panel`。**借鉴结构，不照抄历史 CSS，也不把工具列表与定时任务做成同一个数据/授权系统。**

## 1. 为什么要补这一层：从「工具」Tab 提炼的正确做法

实际「工具」Tab 的一个可信入口包含：
- **索引视图**：`#sidebar-tool-list-view`，顶部只有「已安装工具」及添加/市场/导入入口；
- **同 Tab 中的多个区域**：已安装侧栏工具（主要）、已安装网页工具（次要）、Cookie 管理（低频高级、折叠）；官方发现/导入通过按需内联区域呈现，不强制每次占首屏；
- **详情视图**：`#sidebar-tool-display` 切换原索引；返回按钮位于标题左边，右侧是真正相关的工具操作；
- **低频设置/审阅**：只有进入相关功能才展开，权限/危险操作有独立确认。沙箱 iframe 拥有自己的内容区，不把宿主 CSS 跨世界注入。

由此抽取的**通用模式是 Index → Detail / Form / Management → Inline review**，而不是复制「工具」Tab 的每一种按钮、Cookie 区或 iframe。某些旧「工具」 CSS 已有历史数值和选择器，应继续按 R27/R20 增量收敛，不能把它们评为完美模板。

## 2. Tab / Section / Subview / Surface 四层职责

1. **Tab Root**：六个既有一级页签「我的 / 发现 / 工作流 / 开发 / 工具 / 云控」仍由现有导航控制。一个功能需求默认在既有 Tab 内新增「二级视图」，**不新建一级 Tab**。`role=tabpanel` 等原 ARIA 语义保留。
2. **Index（索引视图）**：一行简洁标题与操作入口；下方按重要性放 1 个主 Section、0–2 个次 Section，再放按需高级 Section。列表卡片为快速扫描服务，**不是参数转储**。
3. **Section（功能区）**：`od-toolbar` 区域标题 + 可选数量/工具动作，下面使用 `od-stack` 展示集合。多个 Section 相隔一个 `--space-4`。每区可独立 loading / empty / error，避免整个 Tab 显示杂乱状态。
4. **Subview（二级视图）**：详情、创建/编辑、任务管理、历史查看等，在同 Tab Root 下切换；头部“返回”**优先左侧**，紧接当前页面标题，右侧只放该视图的关键动作。切换时保留表单草稿或显式提示，不因为列表刷新丢失键盘焦点/输入。
5. **Surface（容器）**：`od-surface` 承担卡片自身边框、圆角和 12px padding；不要整个 Section 加一张大卡、内部每个元素再一张卡、再把日志做第三层卡。只允许一层页面级 gutter。

推荐 DOM 组合（示意，使用已有原语，不要求另建框架/类库）：

```html
<section class="od-page" aria-label="某个功能">
  <div class="od-toolbar">
    <strong>主要功能区</strong>
    <div class="od-toolbar" role="group" aria-label="主要操作">
      <button class="od-icon-button" type="button" aria-label="添加" title="添加">…</button>
    </div>
  </div>
  <div class="od-stack" aria-label="主要内容">
    <article class="od-surface">标题、最重要的状态、简短摘要、操作入口</article>
  </div>
  <section aria-label="其他内容">次要区域标题与列表</section>
  <details><summary>高级信息</summary>可诊断内容</details>
</section>
```

不允许借助增加永久隐藏的二级 Tab、复制第二个 Host 或重复持久化数据来完成布局组合。

## 3. 统一信息架构和屏幕空间规则

- **首屏优先任务与下一步操作**，不优先解释实现原理。空状态最多一条清晰说明 + 一个“下一步”动作，避免卡片、提示、零值指标三重重复。
- 同一个概念只出现一个主标题。比如独立页不要同时出现“OpenDesk 运行页 · 运行概览”和同等级的“运行概览”H1；次级标题只能表示真正不同的内容。
- **独立工具页 / 二级视图：标题默认只有标题。** 头部优先采用“返回（按需）+ 当前页面标题 + 必要的本页操作”。不要在标题下固定叠加产品说明、价值文案、重复的导航路径或数据来源，例如“书签管理 / 整理你的 Chrome 书签”“书签管理 / 与 Chrome 书签保持同一份数据”。此类信息按需移至帮助、空状态或对应功能区。**例外必须是当前决策确需的动态状态或定位信息**（未授权、未保存、当前目标/时间等），不能用第二行口号充当状态，也不能将重要错误仅做灰色副标题。
- **按对象就近放置新增与管理入口。** 可独立创建的“文件夹/目录/书签/列表”等集合，在集合区标题右侧放清楚的“＋ 新建”或同等可见入口，而不是把不同对象的创建动作全挤在全局页头或藏进不相关区域。自定义项目的重命名、移动、删除可放在当前行的可发现操作菜单；只读根节点不展示无效危险操作；菜单不可仅依赖 hover 才出现。表单/确认要在该 Side Panel 子视图内可用，不能依赖预览画布右侧的额外上下文面板。
- 视觉权重次序：**用户关注的对象/现在发生什么 > 下一次会发生什么 > 下一步动作 > 简短状态解释 > 技术细节**。不因状态可取到就平铺四张同权重卡。
- 标题用可读任务名；频率直接表达“每天 09:00 / 每周一、三、五 09:00 / 每隔 30 分钟”，原始枚举、TaskId、FireId、RunId 等仅保留到高级展开项。
- **一行重复动作通常最多两个高频入口**（如“暂停/恢复”和“编辑”）；危险“删除/卸载”应次级化并有原位确认，不与主要按钮同权重。底层动作身份和实际行为不变。
- 多个独立对象需要列表/详情，而不是把所有对象状态放在巨大单一长表单。打开某条详情时，返回应回到合理原上下文，不把用户送回错误的一级 Tab。
- Loading、empty、error、waiting、needs attention、running、settling、unknown、success 和 paused 等状态区分明确；状态文案不是原始枚举，不能仅凭颜色表达。常驻警告仅在真正需要行动时出现。
- 行内确认应展示对象、操作、权限范围和后果；已有被验证并安装的固定版本身份必须保留。没有合法可见 Host 时不能假装后台执行。

## 4. 响应式与操作密度

继承 R27/R20 的 `--od-page-gutter`、`--space-1/2/3/4`、`--od-icon-size` 等权威值，不引入新的全局间距。

顶部与详情动作按 [R20/R30 工具基准](sidebar-design-system-r20.zh-CN.md) 组合：`od-page-head` + `od-page-title` + `od-page-actions`，同区域标题/正文/控件之间为 8px。右侧 icon 仅承载当前对象或区域的常用操作；返回在左侧，执行/安装/权限确认保留文字。正文的复制、刷新等移到所属区域的头部，不创建重复入口，也不把按钮嵌进 details 的 summary。具体色彩和尺寸由共享组件负责。

- **320 / 360 / 420 CSS px Side Panel**：标题、状态、下一次时间能够独立换行；主操作不被硬挤压；`min-width:0` / `minmax(0,1fr)`、`overflow-wrap:anywhere` 优先，避免整页横向滚动。
- **更窄有效宽度（含实际 Chrome 200% zoom）**：把动作换行或收进受信菜单，不能靠缩成难以点击的 20px 图标维持假性“一行”；触摸/粗指针需要更大的命中区域。
- **独立可见扩展页**：信息密度随宽度扩张，正文可用中心最大宽度，但不自动“平铺四张平均的统计卡”。单独设计“重点任务/当前运行”焦点，附属摘要收敛在小区域。
- 正文以 12–14px 的可读性和 ≥1.45 行高为基线，11px 只允许真正次级的简短标注；危险或恢复步骤不能靠 11px 灰字承载。
- 保留 Tab/Subview 焦点路径，Tab、Shift+Tab、Enter、Space、Escape 以及可见 focus-ring。常见隐藏状态必须由语义 `hidden` 控制，不保留无效空白。
- 截图需来自真实构建/真实 CSS。**DevTools viewport 仿真 ≠ Chrome 真正 200% 浏览器缩放，也不是用户 Mac Profile 验收。**

## 5. 多功能区的代码组织、可信边界与复用门槛

- 不因 UI 同属于一个 Tab，把安装的侧栏工具、Page Installed、Task、Cookie、云端任务合并成一张数据表或统一权限；各自保留原 **Authority / Registry / Host / Install generation**。
- 用户工具 iframe / sandbox 内容有自己的 CSS、gutter、生命周期；仅使用数值和语义主题映射，绝不能获得可信宿主 CSS、Token 注入、权限或隐形 Worker。DOM 在可信宿主的 UI 才能使用现有 `od-*` 原语。
- 在 `tool-shell.css` 中用视图/区域作用域选择器布局，避免跨 Tab 的通用 `section/p/button` 选择器。可以复用原布局原语；不要为了一个消费者加“万能新组件/第二套 Design System”，至少经两个真实消费者验证重复模式才考虑提升为共享 CSS 原语。
- 需要表单、列表、详情、状态的地方先按各自业务模块拆职责；UI 组件不应拥有第二套调度器、RunId、授权、异步重试或数据库。
- 一次 UI 改动需核对已有 DOM IDs、自动化测试选择器、表单参数、Stop/Resume/Delete 行为、发送者身份和安装权限；仅更改视觉，不放宽执行规则。

## 6. 将本规范应用于「我的 → 定时计划」R2.4

下面是**目标交互合同，不代表现有 UI 已达到质量门槛**。

**Side Panel / 定时计划索引**
- 标题行：**左侧返回 +「定时计划」**，右侧一个清晰“新建”主入口；“打开运行页”降为上下文操作，不与新建抢视觉权重。
- 如有运行宿主，显示一行紧凑的可读状态；无宿主时提示原因和“打开运行页”，不要重复免责声明。
- 每条计划最多四层：①名称 + 当前状态，②**下次执行时间**（最醒目的值），③中文频率/任务来源（一条次要行），④主要动作“暂停/恢复”“编辑”，其余删除及 Run/Result 等在详情/更多操作。
- 无计划空状态：一句说明 + “新建计划”，不要有额外没有数据的卡片/重复 CTA。历史先默认折叠，按需要加载更早记录。
- 保留 R2 实现的已验证任务来源选择、右侧两个固定新建/管理 Icon、精确网站/权限显示、内联验证、下一次时间预览和确认步骤。

**计划 Form / 编辑**
- 单列逻辑区：名称与固定任务 → 目标网页及参数 → 执行时间及预览 → 高级/错过规则 → 二次确认。表单 label、错误与字段保持 ARIA 关联；编辑不暗中替换 version/hash/generation。
- “新建脚本”和“管理任务”仍是任务来源选择右侧的两枚独立 Icon，不混入下拉项目；在窄宽度下优先保证 Select 可用，不修改权限/安装逻辑。
- 不要让表单的帮助信息、技术版本、重复说明同时堆满第一屏；安全确认只在提交前出现。

**独立运行页 / 可见 Host**
- 主标题只出现一次，附一个简短运行宿主状态；“Chrome 关闭时不能后台执行”放低优先级辅助说明/可展开帮助。
- 主体强调唯一首要对象：**正在运行**（如有）否则**下一次即将运行的计划**，显示名称、时间、状态及暂停/停止等与原 Authority 绑定的合法动作。
- 最近结果、运行宿主情况是小型次要信息，不再默认用四张同权重的大面积统计卡；完整计划管理入口清晰但不抢首屏。
- 对失败、等待、UNKNOWN 给出可理解的下一步，不暴露 `completed`、`WAITING_HOST` 等原始状态作为主要文案。
- `scheduledRunner=1` 必须继续使用原可信 `tool.html` / Controller RunHost，而不是新建第二套执行器。

## 7. 验收门槛（各项独立 ≥95 才能称质量达标）

强制矩阵：Side Panel 300/320/360/420/520px；独立运行页 360/594/760/980px；Chrome 100/125/150/**真实 200%**；至少空态、1 条、20 条、100+ 历史、长中文、长 URL、等待 Host/Target、权限撤销、Running、Success、Failed、UNKNOWN、Paused。

必须证明：
1. **信息架构**：用户能在首屏回答“安排了什么、什么时候执行、现在有没有运行、需要做什么”；主次标题与操作顺序一致。
2. **视觉和密度**：页面 gutter 一层、区块间距遵守 R27/R20、无重复标题、无大面积无意义解释文本、卡片不过度嵌套。
3. **真实行为**：创建/保存/确认、编辑、暂停、恢复、删除、历史分页、独立 Host 打开和关闭、Stop 使用原 RunId，无回归。
4. **响应式/可访问性**：无整体横向溢出或不可见按钮；Tab/Shift+Tab/Enter/Space/Escape、aria、焦点和 WCAG AA 对比度通过。
5. **隔离与维护**：保留已有信任边界，不扩大权限，不增加 SW、Host/DB 或不必要的 CSS API。
6. **原生证据**：固定 Git SHA + WXT package hash + Chrome 版本/Profile + 截图和日志；不使用一个静态 mock 证明原生 UX。

**95/100 是评审目标，不是新文件存在就已达到。未采集证据的每个维度标记 NOT_TESTED，原始失败保留。**

首个专项执行目标见 [Scheduled Tasks R2.4 UI GOAL](../framework/prompts/goal-scheduled-tasks-r2.4-ui-multi-section-final-20261013.zh-CN.md)。
