# 云控业务旅程设计：本地站点搜索、跨平台发布与手机 App 安装

2026-11-19 · 设计阶段。三条旅程分别以验证目标详情或有界搜索结果、核实各平台发布结果、在指定手机验证目标 App 版本并首次打开为终点。下文的验收条件供后续取证，本轮已实测原单页 fixture 的搜索与落地，见总设计 §1；表内拟议云任务与手机步骤待验。A/B/C 是业务旅程编号；R5.2 原生双任务中的 Task A 是表单，Task B 是搜索。

## 共同入口与授权

业务发起人选择已安装的固定任务并提供参数。浏览器所有者在「云控」审阅任务版本、网站、参数范围与正文回传选项，再将指定任务委托给外部 Client。每次执行均核对 Provider、Executor、Pairing、Grant、Task 版本与双摘要、安装 ID 和代次、精确 Origin 及当前权限。外部请求只能提交固定任务与合法参数。业务审批人决定可发布的内容与目的地，手机操作者决定设备端动作，两项决定均有各自的确认时点。

浏览器本地按同一次请求关联 requestKey、Job、Assignment、Run、持久 Result、Worker 释放状态与 Provider 回执。默认只回传最小状态；标题、URL、正文等业务证据留在相应受控端。外部 Client 读取正文须同时具备任务回传许可与该 Client 的读取许可。收到投递超时先凭原键核对原 Job；持久结果已存在时只补原收据，receiptKey 使用原 ResultId。发生动作而结果未知时保留 OUTCOME_UNKNOWN，停止自动重放。

## A · 在本地 Chrome 测试站逐页搜索并打开命中项

**角色与输入。** 测试站维护者提供可复位的两页 fixture，浏览器所有者只授权测试站的精确 Origin，业务人员给出查询、目标标题及翻页上限。以下为待实现的 fixture 合同，既有示例只提供 Locator 和导航接管依据。本地起点设计为 `http://127.0.0.1:43111/journeys/search`。每轮用独立测试会话复位登录态、页码及三个计数（搜索提交、翻页、详情点击），不复用其他人的会话。[本地搜索示例](../../../examples/tasks/visible-search-navigation.js) · [受控 Locator 合同](../../framework/modern-page-api.zh-CN.md)

用户填写的业务参数示例为 `{"query":"云控","targetTitle":"云控发布指南","maxPages":2}`。query、targetTitle 均为去除首尾空白后 1–60 个字符的字符串，maxPages 为 1–2 的整数，包括第一页。BFF 另从本轮 fixture 会话填入 manifest 声明的只读 testSession 字符串（UUID），由测试站关联同一次意图；不接受业务页面代填该字段。四个字段构成试点 Task 的闭合参数。目标按完整标题精确匹配。拒绝未知字段，当前试点只支持标题和单一批准站点。推广时在 BFF 的已批范围中选择 scopeId（限定站点、路径、卡片数、页面数和全程时限）；matchKind 可设计为精确标题、规范化 hostname 或平台记录 ID 的有限枚举。host 匹配按解析后的 URL.hostname 全等，域名后缀伪装应拒绝；重定向和目标落地仍须按批准的 Origin/path 核对。Origin、网址、选择器、凭据均不可由 Client 任意指定。试点全程预算 30 秒，每步最多 10 秒且受剩余预算约束，达到任一上限结束并记录已验页数。

| 固定查询“云控”的结果页 | 按 DOM 顺序排列的卡片（固定 ID 与可见标题） | 翻页控件 |
|---|---|---|
| 第 1 页 | 101「云控入门」、102「云控发布指南（旧版）」 | 唯一可见链接「下一页」，指向同 Origin 的第 2 页 |
| 第 2 页 | 201「云控权限说明」、202「云控发布指南」 | 无下一页；202 的链接为 `/journeys/apps/202`，详情 h1 为「云控发布指南」，可见记录编号为 202 |

**执行与取证。** 通过 `page.getByLabel('搜索关键词',{exact:true})` 填写并用 inputValue 读回，点击唯一的「搜索」按钮一次。设计中搜索、翻页及详情均为同 Origin 的整页导航，使用 `click({waitUntil:'domcontentloaded',timeout:10000})`；每次交接后重新核对 Origin、路径、当前文档、查询回显及页码，再创建 Locator。以 `page.locator('#results').locator('article[data-id]')` 枚举卡片，在卡片内读取标题链接及 href。整页只有一个可见的精确标题命中才点击，零命中且未到上限才尝试「下一页」。每次点击链接前核对解析后的 Origin 及预期路径；多义链接停止。记录每页实际卡片 ID、页码、点击对象及可见计数，本机原 Result 关联同次 Run 与释放回执。

**首文档怎样拿到本轮标记。** 拟议测试站与 BFF 先在试验环境登记同一非秘密 testSession。BFF 从固定模板构造同源起点 `/journeys/search?s=<testSession>`，不接受业务网页提交的 URL。测试站仅受理已登记且未结束的标记，首个文档显示该标记与新生成的 documentInstance。原 Task 在 fill 或 click 之前核对实际 Origin、路径、页上回显标记与冻结参数一致；缺失、过期、错配立即结束，搜索提交数应为零。分页/详情沿同轮标记生成不同文档实例；登录和站点授权仍沿原链。

**如何排除同名搜索串证。** 拟议 fixture 为每个业务意图分配唯一非秘密测试标记，并在每次实际送达文档时生成独立 documentInstance。BFF 将标记随本次冻结参数保存，Provider 仍以原键投递。测试站按标记、实例及事件序号独立记录页码、卡片与计数；原 Task 在当前已授权原文档内读回标记、实例和落地 ID，留在原本机 Result。由获准的 Chrome 可信诊断将该 Job 的 Assignment、原 Run/Result、owned target、原生 documentId 与同一步读回的实例对应，再核对原回执和释放。无匹配时在最后一张已查结果页读回实例。另起一条同标题同计数的测试会话，应因标记和实例不同拒绝关联。此关联不能由 fixture 自报原生 documentId；可信记录若缺映射就保留 INCONCLUSIVE，零新提交地查原记录。

百度现有任务可复用“填写后读回、单次提交、有限读取”的经验；两页 fixture 的翻页、点击及异常分支仍须在本地 Chrome 单独取证。[百度搜索源码](../../../task-packs/baidu.search/src/baidu-search-top3.js)

## B · 先验收单平台草稿，再逐平台审批和发布

**角色与归属。** 以“11 月更新公告”为例，编辑部是原稿 owner，维护原稿 ID、revision、标题、正文和素材清单。官网运营与社区运营各自拥有平台稿，负责本站账号、栏目、受众、排版和平台草稿 ID。二者都引用确定的原稿 revision；平台裁剪或改标题只产生该平台稿的新 revision。原稿更新时列出受影响的平台稿，由各 owner 决定是否同步并重新送审。

1. **先验收官网一份草稿。** 输入原稿 revision、平台账号「官网运营」、栏目「更新公告」、标题、正文、封面及附件、预定公开范围。操作者只点“保存草稿”。重新打开平台返回的草稿 ID，逐项读回账号、栏目、标题、正文、封面／附件标识与顺序、可见范围、草稿状态、平台版本或更新时间；核对格式转换后的预览、原稿与平台稿 revision、内容摘要。公开内容列表新增数应为零。字段漂移交平台 owner 修订，远端保存回执未知先查草稿箱。
2. **审批实际发布。** 审批人逐平台看最终预览，签认具体账号、受众、两级 revision、内容与附件摘要、批准时间及允许提交的起止时间。例如官网仅许北京时间 2026-11-20 **10:00 ≤ 允许提交时间 < 10:15**，社区稿另审。执行器在点击“发布”前重新核对时钟、审批有效性、登录账号及平台现存草稿摘要；排队时在窗口内而执行时已过期，保留草稿并要求新审批。撤销、改稿、换账号也阻止点击。批准范围只涵盖该目标一次提交。
3. **多平台发布与防重。** 每个平台批准项以审批记录、平台草稿版本和账号标识一次业务发布，关联独立 requestKey 与 Job。并发请求、双击和投递丢包均回到同一批准项查询；同键异内容拒绝。每个平台单独记录实际提交时间、内容 ID、审核状态和可用链接。读回官网公开条目才标“已发布”，社区仍在审核就显示“平台审核中”。
4. **部分完成与未知。** 官网已发布而社区点击后失联时，保留官网结果，社区显示 OUTCOME_UNKNOWN。按原 Job、账号、草稿 ID 及提交时段，只读核对平台审核队列、已发布列表和原 Result。确认已提交即关联原平台记录，即使窗口已结束也可继续查证。原动作明确终止且平台证实未提交后，才由 owner 在有效审批下重新发起；超窗须重新批准。证据不足保持未知，不换键补发。

**首次保存草稿丢了应答，编辑查哪一份。** 首个可控测试平台应在首次写前为“租户、平台、账号、原稿修订、本次草稿意图”分配唯一业务引用。BFF 先保存该引用；平台在创建草稿的同一事务内建立唯一的意图引用→草稿 ID 关联，在受权账号的草稿箱或只读接口按该引用查回草稿 ID、账号、版本、摘要。适配器读回字段后由编辑签收。写前发现登录错号、缺素材或引用不合法，停止且保存点击数为零。写后丢应答，只在原账号查询；即使同账号存在相同标题、相同摘要的旧稿，也只能认回该意图唯一关联的对象。第三方若缺少平台生成的创建回执、按意图查询或等效的不可混淆关联，则仅记录未知并交平台 owner 查原记录，禁止补点保存。业务引用只用于关联，接口仍需验证租户、账号及读权。

**一个批准项如何避免产生两个 Job。** 发布项目按租户、平台、账号、原业务发布项维护稳定子项 ID，修订、撤销、重新批准均保留关系。BFF 在网络调用前，以子项 ID 和已核准的发布代次作唯一约束，事务内锁定子项，检查当前审批 revision 与原稿/平台稿摘要，写入唯一意图、原 Provider 键及不可变绑定快照。两个标签页即使提供不同 requestKey，也只读回同一批准项已有的意图；摘要不符拒绝。只有赢得派发权的一方能 submit，丢响应、重启或无法确认派发时只查原键。已发布/仍未决子项禁止靠新审批 ID 绕过。确证未提交且旧执行已终结，业务负责人方可授权新的尝试代次，引用前一次记录。验收至少并发两个不同键，再让首次 dispatch 应答丢失，核对一个业务意图、一个 Provider Job、最多一次实际发布点击和一个平台对象。

**派发进程在首次外呼前崩溃。** 拟议 BFF 在事务内保存唯一发布意图，另存派发领取代次。持有该代次的进程须先以条件写登记准备外呼，再允许发送原 Provider 键。若崩溃时仍是可证明从未领取的意图，业务运维核对原代次及有效审批，才允许合法派发者首次发送同一原键。若已登记准备外呼，即使看不到网络日志，也向用户显示“派发待核”，查询原键和原平台；查不到不能证明未发。发布项目负责人负责结案，旧执行未封闭时不得再派。组件用例分别在事务提交后领取前、准备外呼后及应答前中断，核对意图数、Provider 键与实际副作用。

**怎样证明旧尝试已结束。** 可控平台在最终发布事务内锁同一稳定子项，校验当前批准和尝试代次，再写公开对象。平台运维从同一权威存储核对旧事务已回滚、同一子项无已发布对象，并以条件写在同一锁下关闭旧代次的写权；已提交对象优先被查回。业务还须在原 Job/Run 确认旧执行终结或取得平台对原尝试永久拒写的终结记录，保留审计引用。隔离测试随后把延迟的旧代次提交送到最终处理器，预期拒绝、对象增量零；仅有网页关闭、超时或当前查不到对象均不满足。确认旧尝试无效果且不能再写后，业务负责人才能在有效批准下明确开启新代次，继续使用稳定子项关系。平台无法证明这些条件时保持未决。

**谁在最后一刻核准。** 首个可公开发布的候选选择由发布项目控制的单一官网测试平台。拟议同源草稿确认页从平台服务端加载当前批准项，原 Task 经受控 Locator 读回目标账号、两级 revision、摘要、批准状态、服务器时间与截止时间；缺字段、撤批、已过窗、断线或审批无法读取时停止。点击仅向该平台已有发布流程提出提交。平台最终发布处理器必须在同一事务内按服务端可信时钟校验生效窗口、最新审批 revision、当前账号、草稿/素材摘要及单次意图，再条件写入发布对象；已撤批、已消费、过窗或版本变化即拒绝写入。过窗时按钮可能已被浏览器点击，结果应区分“提交尝试”和“批准生效时公开”。业务页不对外提供新的脚本执行权；此处是发布项目待实现的业务校验，现有云 ControlFence 继续负责执行端授权。

试运行使用独立测试目标、专用账号与仅草稿/模拟权限，正式发布处理器拒绝试运行身份；不能用真实公开发布来验证 Candidate。负例依次覆盖排队后撤批、确认页打开后到期、提交瞬间改稿、试运行进入正式发布、同一批准项异键并发。每例检查平台公开对象增量为零（并发成功用例最多一个）。第三方平台若无法提供等效的最终约束，先只交付草稿和供获授权人员审核的原平台入口，无人值守公开发布保持未开放。每家平台单独证明最终写入及恢复能力。

**验收终点。** 单平台草稿可独立签收。多平台总览逐项显示草稿、待审批、可提交、已过期、审核中、已发布或未知，并能从每项回溯到审批窗口、唯一投递与平台事实；一个平台成功不能关闭另一项。

## C · 定位目标 App、打开商店、下载并在手机确认安装

**角色与输入。** 发起人指定 App 名称、发行方、商店条目 ID（或包标识）、目标系统、要求版本及目标设备。浏览器操作者负责查找和核实下载来源，手机所有者确认该设备上的安装与首次打开。商店、系统和版本按本次请求填写；同名应用必须核对发行方和标识。下列步骤分别签收。

| 步骤 | 谁做什么 | 证据、验收与恢复 |
|---|---|---|
| 1. 定位 App | 浏览器在已批准站点搜索，按名称、发行方、标识筛选。 | 记录匹配条目与目标系统；同名异发行方排除，无法唯一确定则停止。 |
| 2. 打开商店 | 浏览器打开获准的官方商店条目，核对真实 Origin、条目 ID、发行方和系统兼容性。 | 记录商店条目与可见版本；地区限制、登录失效或跳到未批准来源时保留原因，禁止改找镜像。 |
| 3. 下载 | 商店若提供官方安装包直链，可由具备下载权限的已安装工具在浏览器发起；商店若仅支持设备安装，由用户在指定手机打开同一条目并按商店流程下载。 | 直链分支记录来源、downloadRef 和同一引用的终态。设备商店分支记录该设备该条目的下载进度或终态，若商店将下载与安装合并呈现，单独下载终态记“未单独观察”。桌面浏览器成品只签收桌面下载；手机仍须在受支持商店或系统安装入口另行核验。 |
| 4. 手机确认安装 | 手机所有者在系统或商店界面核对设备、发行方与安装对象，明确确认；若系统在下载开始前即要求确认，按实际顺序记录确认时间。 | 记录已确认、已取消或系统拒绝。未确认保持待用户操作。回执未知先查看商店和系统应用列表，不重复触发安装。 |
| 5. 验证安装版本 | 在该手机的系统应用信息或 App 自身版本页读取已安装标识和实际版本，与请求比对。 | 保存设备、标识、要求版本、实装版本和观察时间。商店宣传版本不能替代实装版本；若需先启动才能看版本，记录实际取证顺序。已预装须单列，不能作为本次新装证据。 |
| 6. 首次打开 | 用户从刚安装的条目点击“打开”，核对前台 App 与预期启动页。 | 记录本次安装后的首次启动时间、实际前台标识和可见页面。崩溃、权限提示待处理、错版本分别记录；仅在实装版本符合且观察到预期页面后关闭旅程。 |

**当前下载 SDK 的来源授权与 completed 证据缺口。** 源码中 `browser.downloads.download({url,filename?,saveAs?})` 的调用主体是已安装工具。Host 绑定工具 ID、版本、packageHash、installEpoch，要求 `user.export`、Chrome 的 `downloads` 权限及下载 URL 精确 Origin 的有效网站权限。下载适配器另以发布方元数据约束允许的文件类型、预期大小、版本与可得的签名/摘要，拒绝与目标系统不符、类型或来源不明的文件；最终 Origin、重定向和产物完整性须由受权来源取证，SDK 只给有限状态时保留“文件未核验”。输入是无凭据的 HTTP(S) URL。商店页面和实际下载来源若不同，要单独核对下载来源的权限；Controller 的搜索授权不能直接调用这条工具 SDK。Chrome 原生保存或风险提示仍由用户处理。[操作契约](../../../src/framework/sdk/browser-contract.js) · [Host 权限判断](../../../src/platform/chrome/context-menus.js) · [公开签名](../../api/browser-sdk.developer.generated.md)

驱动发起成功仅返回 `{downloadRef,status:'started'}`。原工具用 `getOwned({downloadRef})` 读取 Chrome 对同一原生下载的状态：`in_progress`、`complete` 或 `interrupted`，并取得 bytesReceived 和可选 totalBytes。业务记录“下载完成（completed）”须保存同一引用实际读到的 `state:'complete'`；本设计没有该 App 同次 Chrome 的这条证据。引用失效、Worker 重启或撤权后应保留最后已知状态，人工核对原下载，不自动重下。该查询也不返回包签名或实装版本，手机安装确认与首次打开仍需设备端取证。[下载驱动](../../../src/platform/chrome/browser-downloads.js)
