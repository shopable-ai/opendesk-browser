# WebCodex：云端模型、本机文件工具与既有 ChatGPT 对话的可行性边界（2026-10-10）

> **文档性质：产品需求澄清 + 技术事实 + 反面决策记录（ADR）；不是新方案实施完成报告。**
> **状态：约束生效；最终接入路线尚未选定；真实目标对话、当前账号权限和 macOS Chrome 全链路仍须实测。**
> 适用：OpenDesk Browser main / OpenDesk Go 实际主分支（现为 master）。优先处理单台 Mac、已有 Go 与浏览器扩展、用户指定的**原官方 ChatGPT 对话**。不据此扩大到 Windows、多机或任意网页 RPC。
>
> **必须先读的结论**：在网页注入 opendesk-sdk，只让网页或受控浏览器代码具备某些能力，**不会给运行在云端的 ChatGPT 模型自动注册本地工具**。用户已经指出并不接受靠每次人工“读回答→复制／回填→发送”推动任务的方案作为产品终态；此前建议的“DOM 自动接力 + MCP Tunnel 双通道”也**尚未获得认可，不能写成已确定架构**。

## 1. 用户真正要解决的问题（产品验收合同）

用户从目标 Mac 目录执行一次受信 CLI 接入；随后在**当前指定的官方 ChatGPT 已有对话**中提出任务，AI 能够自主按需读取已授权工作区文件、基于真实结果继续分析并发起下一步修改，真实写盘由受信执行器完成，有可复核的文件差异、权限、SHA-256 和读回证据。

- **不接受**：每次读取都要用户手动点击“识别请求”“复制”“粘贴”“发送”；侧栏显示结果后要求用户充当消息中继；模型仅生成没有被执行的 JSON；需要另开 Codex/API 线程才算完成。
- **可区分的安全确认**：接入目录时的一次授权、敏感写入时按实际权限要求的审阅/批准，与“每次读文件都要人为转发结果”不是同一概念。不能为减少点击绕过平台官方确认、原有只读授权或 Go 的最终权限检查。
- 若当前账号／产品入口实际不能提供足够的模型工具权限，报告为**目标受阻**；不要悄悄把需求降低成“带人工中继的文件编辑演示”后宣称成功。
- 本 ADR 只冻结**目标和技术边界**，不宣布实现已通过，也不强行选定某一个具体方案。

## 2. 已确认的运行边界，不得再误解

| 环节 | 真实能力 | 容易犯的错误 |
| --- | --- | --- |
| 网页 Page/USER_SCRIPT 中的 opendesk-sdk | 受浏览器沙箱与扩展授权约束的网页侧能力入口 | 以为网页对象自动成为模型服务端可调用的函数 |
| Chrome 扩展 + Native Messaging + OpenDesk Go | 可从本机受信入口访问已授权目录，现有文件服务已具备读写及 SHA 基准保护 | 以为 Native 连接成功就代表模型获得读取结果 |
| 官方 ChatGPT 网页对话 | 模型消费**实际发送并进入对话上下文**的消息，以及平台正式接入的工具结果 | 把侧栏显示、输入框回填或用户消息 DOM 存在当成云端消费证据 |
| 平台正式工具调用（如已启用的 MCP） | 模型可请求工具，平台将工具结果纳入后续推理 | 以为安装扩展或隧道就自动给当前账号/当前对话添加读写权限 |

技术事实：**同一对话的文本往返在原理上可行**，因为文件结果可以通过下一条真实用户消息进入云端模型上下文；这与“模型直接调用正式文件工具”是两个不同能力。当前一次推理本身不会因为网页 JavaScript 新增 SDK 方法而挂起、等待本机 JS 返回。

- 不要求必须采用内网穿透。扩展经 Chrome Native Messaging 访问本机 Go 时无需让服务开放公网入站端口。
- 真正的服务端模型工具调用必须另有正式工具注册、身份认证和返回通道。若选择私有 MCP 服务，Secure MCP Tunnel 是**可能的传输手段之一**，不是模型工具权限本身，也不是所有实现的必需前提。
- 独立使用 OpenAI API/function calling + Go 本地执行器可拥有真实工具回路，但**不能自动继承现有官方网页对话的会话历史和身份**，不能用它冒充本目标达成。

## 3. 本轮对候选方案的判定（不是排名或选型结论）

| 候选 | 理论条件 | 当前判断 / 不可宣称 |
| --- | --- | --- |
| 逐次人工处理结构化文本、用户发送读回结果 | 浏览器扩展 + Go 能读文件并将结果交给用户 | **仅能做阶段性 P0／降级演示；用户不接受作为最终交付**。旧 R3 人工流程的验证价值保留，但不能因此称目标已满足 |
| DOM 监听 + 扩展自动回填／自动提交／反复循环 | 实际网页结构、发送交互、身份稳定性以及安全边界均通过实机证明 | **备选实验路径，未获用户认可，不是当前冻结的主架构**。无需公网穿透，但脆弱性和非正式工具语义必须明示；不把一两个自动化 DEMO 当可长期维护的生产连接 |
| 正式 ChatGPT MCP 工具 + 本机 Go Adapter（可经 Secure MCP Tunnel） | 当前账号、模型模式、工作区、原对话均**实际允许目标读写工具**；独立验证 tool discovery、调用、回传与写入确认 | **值得先做资格与最小调用核查，但没有资格证据前不能保证可用于本目标**。Tunnel 只解决连接，不解决套餐/会话权限；不应强制用户部署公网代理或建立第二套文件授权 |
| OpenDesk 自行运行 Responses API / Codex App Server + 本地文件工具 | 可以用新的模型运行时、独立线程承载任务 | **另一个真实可行的产品方向，但不能替换“当前官方网页既有对话”目标**；除非用户以后明确改变需求 |

**重要：用户已反馈上一版“自动文本桥接 + 正式 MCP 双通道”方案体验较差、不太合适。因此不得默认并行建设两套通道，不能基于未经同意的技术方案大量扩展代码或 UI。**先做可行性证据和目标约束判断，方案选型应留待新事实或用户明确方向。

## 4. OpenAI 产品层限制：必须核对当前官方文档和实际账号

2026-10-10 查阅的官方说明：
- [ChatGPT 开发者模式和 MCP 应用](https://help.openai.com/en/articles/12584461-developer-mode-and-full-mcp-connectors-in-chatgpt)：完整 MCP 的写入/修改操作向 Business、Enterprise、Edu 分阶段提供；Pro 开发者模式的自定义 MCP 能力主要为 read/fetch。**这是本次查阅的产品状态，不是永久不变的协议事实。**
- [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)：本机 tunnel-client 主动向 OpenAI 建立出站 HTTPS，把已授权 MCP 调用转发给本机私有服务；它仍要求 Platform/ChatGPT workspace 的相应权限、工具注册与运行中的 client。
- [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)、[Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)：网页脚本、扩展隔离环境和本机 Native Host 是不同信任与运行空间。

**验证要求**：进入工程实现前，先在用户实际目标账号与**原有对话**里确认：能否添加自定义工具、该工具是否真实可见、是否允许 read/write、写入是否必须平台确认、是否能继续原会话、隧道／连接是否属于可用权限。不允许根据计划名称、静态文档、示例账号或 MCP Inspector 推断本机账号必然可写。

若产品权限不满足目标，应报 **BLOCKED_BY_PLATFORM_PERMISSIONS / NOT_TESTED** 并列证据；不能通过伪造回调、修改 DOM 提示或取消写入确认来“修复”。

## 5. 保留的现有代码资产与验收地位

已有历史成果仍可复用：
- R1/R2：受限文件工作区、Go Native files 服务、显示/编辑预览、单文件提案、SHA 版本冲突、显式保存、读回核验。
- R17/R17.1：CLI 目录来源、短期租约、同名多目录、真实访问级别和 Workspace/Sidebar 关联。
- R3 增量：模型文本 list/read 请求解析、结果回填、提案身份与保存前校验已进入源码/组件验证流程；具体提交和证据以 [WebCodex 工作流](../../framework/workstreams/webcodex-chat-edit-r2.md)、[当前 Mac 验收 GOAL](../../framework/prompts/goal-webcodex-chat-edit-r2-local-acceptance.zh-CN.md) 以及实时 Git HEAD 为准。

**这些已实现的软件构件不等于“云端模型直接拿到本地工具”。** 现有工作流记载本次源代码/定向测试/打包验证，但当前用户 Mac 的真实 Chrome、原官方对话 P0、两轮真实文件修改仍不可在缺少原生证据时宣布 PASS。

也不要为了探索正式工具接口，重写已存在的 Workspace、Go 文件服务、CLI 授权、RunHost，或把普通网页升级为有任意 files.write、Shell、跨目录修改权限的远程接口。

## 6. 下一次选型之前必须做的最小证据检查

1. **目标身份先决条件**：确认当前官方 ChatGPT 对话 ID/URL、可用工具模式、账号实际权限；不悄悄换模型线程或新建聊天。
2. **能力关口**：若评估 MCP，实测原对话真实模型能发现和发起工具调用、工具结果能被后续推理使用；分别测 read 与 write 的平台权限和确认行为。只在本机工具模拟成功不算通过。
3. **数据关口**：使用未知随机标记文件，初始模型上下文不得提前包含正文；真正 Native 读取结果由后续模型准确引用。读取/回填/网页发送/模型消费分别出证据。
4. **操作体验关口**：一项自然语言任务能完成多轮按需读取，**无人工逐轮复制、点击转发和发送**；若还有用户操作，逐一说明是否为首次授权、写入确认还是人为中继，不模糊混写。
5. **写盘关口**：写入仅限 CLI/Workspace 已授权目录，遵守只读、租约、相对路径、安全格式、版本基准、外部编辑冲突及撤权。真实成功应含 Go 执行结果、读回和独立磁盘 SHA 核对。
6. **故障关口**：旧请求重放、重新生成回答、SPA 换对话、标签页刷新、未知写盘结果、断线、多目录和迟到结果 fail closed，不自动扩大权限或盲目重放写操作。
7. **报告口径**：逐项区分 FACT / DESIGN / IMPLEMENTED / COMPONENTS_PASS / MAC_NATIVE_CHATGPT_PASS / FAIL / NOT_TESTED / BLOCKED；不给无证据的“100% 可行”“95+ 验收通过”。

只有上述关键证据明确之后，才可重新评价 MCP、文本桥接或其他产品入口是否适合。**不要因为能构造一条技术链路，就默认它满足用户要求的体验与权限条件。**
