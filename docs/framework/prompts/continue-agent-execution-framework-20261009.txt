# 梳理 AI 编程执行的结构性问题：调用链、证据、进度与停止条件

请继续与我梳理 AI 长任务的执行方式，并形成可复用、可检查的工作规则。默认中文，表达清楚、具体，避免流程堆叠。

一、我要解决的问题

AI 经常执行很长时间，但用户看不到方案、步骤、判断依据和实际进度，只看到反复执行测试。不清楚哪些已通过、哪里失败、为什么再次执行、什么时候能够结束。

axiosx 是一个具体案例：它通过浏览器插件注入网页。
1. 先检查是否注入成功，OpenDeskSDK 和 axiosx 是否存在。
2. 调用一个真实 GET，判断请求和返回是否正常。
3. 没有返回时，看服务端是否收到请求。
4. 服务端收到后，看插件后台是否收到原生回执。
5. 后台有回执后，看 MAIN/Worker 的回传、错误投影和编解码是否正确。
6. 最后核对持久结果、授权、停止与恢复边界。

我需要理解这些做法的专业名称，并找到系统性解决方案：让其他功能也能够按关键步骤拆解，执行中暴露证据和进度，失败后有明确分支，防止无意义重试。

四、需要梳理的具体内容

1. 区分专业概念

解释“调用链路/调用流程”“端到端验证”“链路追踪”“可观测性”“故障定位”“假设驱动排障”“阶段检查点”分别解决什么问题。

明确哪些是程序系统的观测方法，哪些是 AI 执行过程的管理规则。我们提出的执行约定可以自行命名，但不要把自定义名称冒充行业标准。

2. 复盘为什么长时间执行却看不到进度

检查是否存在以下情况，并区分已证实、合理推测、材料不足：
- 开始时没有明确目标、范围、通过条件和停止条件。
- 有任务列表，却没有按调用依赖和故障分支安排顺序。
- 没有区分实现缺陷、观测缺陷、授权/环境问题与缺少证据。
- 成功证据没有复用，每次对话重新构建或全量测试。
- 失败后没有说明新假设或变化，反复执行同一个检查。
- 只有执行活动，没有形成“观察结果→判断→下一步”的可检查记录。
- 用测试数量、耗时或忙碌程度代替功能通过情况。
- 已有约定其实足够，但执行中没有遵守。

对最后一种情况尤其谨慎：如果已有规则足够，指出执行偏差及如何检查落实，不继续靠堆文档制造更大框架。

3. 建立最小执行约定

执行前，给出：目标、当前证据、实际缺口、关键步骤、步骤依赖、通过条件、验证范围和停止条件。简单任务保持简单；不要每个微小修改都套完整仪式。

每一步至少能回答：
- 本步要证明什么？
- 输入和前提是什么？
- 预期观察到什么？
- 实际观察到什么，证据在哪里？
- 当前是待执行、进行中、通过、失败、受阻，还是尚未测试？
- 根据结果，下一步是什么，为什么必要？

失败后先定位失效边界。把问题分成产品行为、观测方法、运行环境、授权和证据缺口；对应处理，不默认修改业务代码。

重复执行须有具体变化：代码修复、新假设、新输入、环境变化或观测方法变化。未变化且已有确定失败的操作不盲目重试；确有暂态问题时说明依据，并设置有限重试条件。

测试前检查跨对话复用：成功且相关输入、合同、环境未变则引用；有变化只补受影响验证。不得把组件、旧包、原生、F3 或安装证据相互升级。

约 60 秒提供一次有意义的状态更新：当前步骤、实际结果、关键证据、下一步。长命令仍在运行时说明等待对象和结束条件，不编造新成果。

用明确事件作为检查点：定位到故障、修复完成、验证通过、环境受阻、发生范围变化。不要为显示活跃而增加重复日志。

完成时回答原目标是否达成、哪些未测、剩余缺口是什么、资源是否已释放。若当前范围已经满足通过条件，停止；若失败后没有可行恢复路径，准确报告阻断原因和所需输入。

4. 用 axiosx 展示如何实际应用

用一个紧凑表格或纯文本流程，覆盖：
注入/授权 → MAIN 或 Worker 调用 → relay/broker/网络驱动 → 服务端 → 原生回执 → 回程编解码/错误投影 → 持久结果。

每个节点列出通过证据，以及失败后应进入哪个分支。区分“变量存在”“请求已发出”“服务端已收到”“后台收到回执”“调用者拿到完整结果”，这些是不同结论。

将“后台有正文、Worker 没有 cause”放到正确边界，解释为什么应集中检查错误返回和投影，而不是重新做网络框架、注入或 HTTP UI。

有跨异步边界时，说明如何关联 requestId、operation、runId、resultId、document/owner 与源码/包身份；复用已有标识和日志。只有现有证据确实不能定位问题时才建议补观测，不先新增另一套 tracing 平台。

5. 给出可复制模板和轻量落实办法

产出三个短模板：
A. 开始执行前的方案与验证表。
B. 执行中的状态更新：当前步骤／观察结果／判断／下一步。
C. 收尾记录：目标结果／变更／验证与复用／剩余缺口。

模板应能判断执行是否合格：每项都有实际事实，不能只填“继续排查”“加强验证”“持续优化”。

说明哪些约定可以靠工作记录检查，哪些适合将来用轻量工具辅助，哪些涉及授权和未知副作用、需要产品本身守住。清楚区分“提示词要求”与“机制实际强制”，不声称一份提示词能保证所有 agent 永远遵守。
