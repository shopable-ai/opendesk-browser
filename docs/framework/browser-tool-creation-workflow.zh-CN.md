# OpenDesk Browser 自然语言扩展开发工作流 R2 — 需求推理与功能树先行

日期：2026-10-15。状态：**R2 三案例需求推理已做源码约束桌面校核；现有 Skill 可分段人工调用；端到端自动化产品入口尚未实装**。

**目标：** 用户用一句话描述“想做什么”，AI 先读取真实产品、源码与相关历史，推理用户场景并生成可追溯的需求/功能树；通过需求关卡后，才生成可操作 HTML、正式代码、测试并安全交付。**不能从一句话直接跳到界面或编码**。这不是第二套 SDK、Runner、Host、Agent Skill、Chrome Extension 或发布系统。

现有规范：[AGENTS.md](../../AGENTS.md) · [八个 Skill 路由](../../.agents/skills/README.md) · [Sidebar Tool 开发](../api/sidebar-tool-development.zh-CN.md) · [预览合同](../api/sidebar-preview-kit.zh-CN.md) · [测试证据](testing-guide.md)。本工作流编排已有能力，不复制技术权威；有冲突时，以当前源码与对应正式安全合同为准。

## 一、普通用户只做三件事

1. **描述想法**：“我想在 ChatGPT 左边有几个按钮，点一下输入完整提示词，还能把选中文字通过右键添加为按钮。”
2. **看需求和可点击 HTML**：AI 自动整理产品用途、使用场景、功能树和操作界面；用户只修改不符合预期的地方，不需要填写 API、权限和构建配置。
3. **体验与验收**：AI 负责源码、测试和打包；真实权限、删除、发送和发布按正式授权流程由用户决定。不能访问 Mac/真实 Chrome 时记录 NOT_TESTED，而不是要求用户反复重复产品需求。

**用户只描述部分需求是正常输入形式。** AI 必须主动补齐可合理推断的必要细节，但不允许虚构用户已批准的高风险决定。

## 二、九个环节、四道关卡

| 环节 | AI 必须完成 | 产物 | 继续条件 |
| --- | --- | --- | --- |
| 0. 恢复现场 | 读取最新 main、AGENTS、相似工具、已批准原型、现有源码/测试和实际可读的历史交接 | 事实/版本/冲突与断点 | 不把旧聊天总结当成最新 Git 状态 |
| 1. 需求理解与推理 | 理清用户目标、典型用户、触发场景、前后状态、输入输出、成功体验、异常恢复 | **一页需求摘要 + 用户场景** | 先说清“解决什么问题” |
| 2. 功能树生成 | 拆成 F0→F1→F1.1；为每个核心叶子补齐场景、操作、成功/失败、优先级、数据/权限和验收 | **唯一功能树文档 + 场景追踪表** | P0 不得存在只有名字的功能 |
| 3. 需求校核与技术路由 | 区分用户决定/源码事实/AI 推断/待确认；核对现有 Skill、SDK、Host、权限、可实现性 | 需求差距、实施边界、关键决策 | **关卡 A：需求闭环**；高风险未知不能擅定 |
| 4. HTML 交互原型 | 从功能树生成可点击/可输入的完整场景；网页注入 + Side Panel 按需分别预览，同一规则 | 完整 HTML、模拟数据、必要截图/来源 | 必须能实际操作，不只画静态图 |
| 5. UI 评审定稿 | 用功能树逐项测试主路径、空态、保存/取消、异常、撤权、键盘和小尺寸；用户反馈后定向修正 | UI 评审记录、功能覆盖、定稿 SHA | **关卡 B：用户看得懂、操作得了** |
| 6. 正式开发 | 根据真实运行世界在工具自身项目开发；复用原 SDK/沙箱/Host/安装器/权限/设计系统 | 源码、功能编号→文件映射 | 不建第二套执行或状态机制 |
| 7. 分级测试 | 定向 Node/DOM → 模拟 Chromium → 同源构建/包校验 → 可用时真实 Chrome/网站/IME | 同候选 PASS/FAIL/BLOCKED/NOT_TESTED | **关卡 C：真实功能，不拼旧成绩** |
| 8. 保存交付 | 更新唯一文档和交接、普通提交 main/推送、安装说明、剩余问题与下一步 | SHA、证据、可接续断点 | **关卡 D：可继续维护** |

当任务只是修已有工具时，先定位受影响的 F/S/A 编号，**只复查受影响环节**。用户明确只做设计/原型时止步相应阶段，不能自动发布。

## 三、核心新增：需求推理引擎（不是问卷）

### 1. 证据顺序与冲突解决

- 最新用户明确要求、已确认产品边界；
- 仓库最新源码/AGENTS、现行设计系统、SDK 合同、可追溯的原型与测试；
- 同项目已核实的场景、之前决定及关联项目经验；
- 实际**可访问**的历史对话、总结和用户附件：可以辅助，但不能保证所有旧会话、未提交文件始终可读；
- AI 根据常见用户行为提出的假设或便利性建议。

如历史对话出现“按钮在输入框右边”而用户后来要求“主内容区域左边缘”，以**最新明确决定**为产品目标；工程安全约束与权限仍需独立遵守。每项重要决定记录依据、时间和受影响功能，而不是写“我们以前似乎通过”。

### 2. 从一句话补齐八种信息

- **用户与动机**：谁在何种频率下需要，现有做法有什么麻烦，真正希望节省什么。
- **主要使用场景**：在哪里打开、由什么行为触发、哪些网站/Tab/侧栏、前置状态是什么。
- **完整用户旅程**：入口→点击/输入→处理→反馈→编辑→确认→返回/重开，谁负责最终发送或保存。
- **场景变体**：有/无草稿、多次点击、长文字、多标签、权限变化、导航、缩放/窄屏（按任务范围）等。
- **失败与恢复**：取消、保存失败、并发冲突、配额超限、编辑器不存在、权限撤销、状态未知、数据保留。
- **数据和风险**：读什么、写哪里、是否出站、谁能访问、持久化期限、删除后如何处理、可否撤销。
- **优先级和不做项**：P0 最小价值闭环，P1 可选增强，P2 延后；不因为 AI 可以写代码就无限加功能。
- **成功的客观证据**：用户看到什么、实际数据怎么验证、测试路径与运行环境、什么情况必须拒绝。

### 3. 把确认事实和推断分开

| 标识 | 含义 | 执行处理 |
| --- | --- | --- |
| `USER_CONFIRMED` | 用户明确描述或本轮批准 | 在授权与安全范围内落实 |
| `SOURCE_VERIFIED` | 当前源码、正式原型或测试确实支持 | 保留 SHA/来源，变化后核验 |
| `AI_INFERRED` | AI 从使用场景推导的必要细节或建议 | 说明理由和信心；低风险可先放预览，不伪称用户已批准 |
| `NEEDS_DECISION` | 对权限、隐私、收费、不可逆动作或重大范围有影响 | 优先问一个关键问题，其余无冲突部分继续 |
| `OUT_OF_SCOPE` | 明确不做或推迟 | 不擅自加入 P0 |

**不因输入简单就发十几个问题。** AI 自动补齐不涉及高风险的合理细节，展示简短摘要供用户纠正；必要决定再问。猜测不能替代安装/权限批准、远程上传授权、数据删除确认或真实来源验证。

## 四、唯一需求与功能树文档

每款工具维护一个可持续更新的功能树：普通 Sidebar App 优先写在已有 `examples/sidebar-tools/<id>/README.zh-CN.md` 的“场景与功能树”章节；受信任第一方功能按 `src/<feature>/README.zh-CN.md` 的产品文档所有权。已有权威需求设计文件时更新原文件，不创建互相竞争的 R1/R2/R3 产品总文档。证据与断点沿用原 `docs/framework/workstreams/<id>...` 主交接记录。

**功能树的叶子节点不是一行功能名。** 每个叶子必须说明：它服务哪个 S-ID 场景、用户从哪里操作、前置条件、预期结果、失败反馈、数据与权限、副作用、优先级、如何验收（A-ID）。可选再关联 UI 视图 V-ID、源码模块 C-ID、测试 T-ID。

### 输入例子

用户说：“ChatGPT 左侧做几个提示词按钮，点击填入完整文字；选中文字右键快速添加。”

AI 从已明确的用户要求和可核实的 R1.2 原型恢复产品选择，生成以下**候选树**（树不等于真实代码全部交付）：

```text
F0 ChatGPT 提示词快捷按钮
├─ F1 网页内快捷使用 [P0]
│  ├─ F1.1 主内容区左边缘竖排、垂直居中、窄屏安全折叠
│  ├─ F1.2 一两个汉字短标签、完整名称/多行正文 Tooltip
│  └─ F1.3 点击插入当前草稿，保留文字/光标、不自动发送
├─ F2 侧边栏管理 [P0]
│  ├─ F2.1 列表、新建、编辑、删除确认、启停、排序
│  ├─ F2.2 完整名称、短标签、正文、圆角方/圆形
│  └─ F2.3 存储配额、并发冲突、错误恢复及持久化
├─ F3 选区右键快速添加 [P0：用户明确要求]
│  ├─ F3.1 已授权网站的 Chrome 原生右键入口
│  ├─ F3.2 一次性选区→预填创建→用户确认保存
│  └─ F3.3 独立开关，关闭后菜单消失、数据保留
├─ F4 权限与生命周期 [P0]
│  ├─ F4.1 工具身份、Origin、安装/启停/撤权
│  └─ F4.2 SPA、旧请求、Editor 不唯一、卸载清理
└─ F5 验收交付 [P0]
   ├─ F5.1 源码、工具包、版本同源
   └─ F5.2 模拟与真实 Chrome/ChatGPT 分级证据
```

**场景和验收追踪表（节选）：**

| 场景 | 关联功能 | 可观察结果/异常要求 | 验收 |
| --- | --- | --- | --- |
| S01 已写半段草稿后点击 | F1.3 | 当前有效光标插入、原草稿不丢、绝不自动发送；编辑器变化拒绝 | A01 |
| S02 网页选中文字后右键添加 | F3.1–3.2、F2.3 | 创建页预填、用户修改/确认后才保存；关闭前不产生数据 | A02 |
| S03 关闭右键开关 | F3.3 | 菜单隐藏，已有按钮/文本仍在 | A03 |
| S04 未授权或保存发生冲突 | F2.3、F4 | 旧请求拒绝、编辑草稿保留、不会提示假保存成功 | A04 |

需求可继续细化，但每增加一项必须证明用户价值；不要用功能编号数量替代完成度。

## 五、关卡 A：缺它不能跳到 HTML

- [ ] 有用户目标、价值与完整的 P0 主使用场景（不是只讨论“做一个按钮”）。
- [ ] 每个 P0 功能叶子有 S-ID 和 A-ID；每个 S-ID 都有成功/失败结果与明确操作入口。
- [ ] 已考虑必要的保存、取消、空态、错误、权限/撤权和恢复；不要求每个产品无意义地展开全部极端情况。
- [ ] 说明数据来自哪里、保存到哪、风险和范围，未经授权不上传或自动提交。
- [ ] `AI_INFERRED` 不伪装成 `USER_CONFIRMED`；关键 `NEEDS_DECISION` 有处理办法。
- [ ] P0/P1/OUT_OF_SCOPE 分清；架构能路由到现有一个主 Skill 和真正可用的宿主/权限合同。
- [ ] 不能实现的动作标 `BLOCKED`，不能伪造 API 或另起一个安装器。

通过后先做**HTML 可交互原型**，而不是把功能树立即翻译成后台逻辑。若涉及网页按钮与 Side Panel 管理，应在原型中完整呈现两种界面及其状态关系；页面间的模拟内存不可冒充真正跨标签同步。

每个工作选择**一个主 Skill**，跨边界才协作；普通应用不变成第二个 Chrome Extension，不复制 Host/SDK/消息协议。历史 [Extension Factory R2](workstreams/extension-factory-r2.md) 是已废弃并移除源码的定制 Page QA 实验，不是现行可调用通用工厂。

## 七、跨对话防丢失和增量更新

- 通用编排只维护**本页**；工具自身的功能树/场景在唯一产品文档；每项工作的源码与测试情况在唯一主交接记录。
- F-ID / S-ID / A-ID 保持稳定，关联原型文件、源 SHA、正式模块和验证；用户改一个位置，只更新受影响的功能及测试。
- 决策记录至少包含“旧决定→新决定→用户或证据来源→影响的 F/S/A”。不要每次另建总 GOAL 把原决定覆盖掉。
- 新对话优先读最新 main、原项目 README、已提交 HTML 与主交接记录；可访问的历史摘要可以补充，**不能保证所有旧对话、附件或未推送变更一定可访问**。
- 结束时更新 main HEAD、已完成/未验证/阻塞的 F-ID、真实测试命令与证据、最近 SHA、下一条最小行动。
- `DESIGN_REVIEWED`、`SOURCE_WIRED`、`NODE_PASS`、`SIMULATED_CHROME_PASS`、`PACKAGE_PASS`、`REAL_CHROME_PASS`、`REAL_SITE_PASS` 各自独立，未执行标 `NOT_TESTED`；不能以模拟 95+ 宣称产品已达 95+。

## 八、可复用的普通用户启动提示词

> **GOAL：在 OpenDesk Browser 中制作一个工具：[用一两句话描述想法]。请先恢复最新源码、已有 Skill/原型/历史决定，主动补全用户角色、使用场景、前后状态、操作流程、异常、数据与权限，再生成带 F-ID/S-ID/A-ID 的完整功能树。区分 USER_CONFIRMED/SOURCE_VERIFIED/AI_INFERRED/NEEDS_DECISION，先通过需求关卡，之后给我可点击的 HTML 原型试用；我确认后直接按现有框架开发、测试和提交 main。不要重新造 SDK/Host/设计系统；重要结论和每轮断点更新到已有项目文档。**

用户可只填方括号内容。AI 负责编排与验证，**用户明确要求止步需求/预览时不得擅自发布或删除数据**。

## 九、工作流自身的验证

此页是**文档方法**，不是已实现“一句话自动生成安装”的产品能力。以后须在普通 Sidebar 工具、网页内按钮/原生右键工具、Page/React/Vue 场景分别跑完真实项目，独立评估需求完整度、用户额外问答数量、P0 场景→代码/测试覆盖、复用成本、权限和真实安装；每维 95/100 是目标而非当前实测成绩。

## 十、R2：可执行阶段合同（2026-10-15 增量）

**此节是 R1 方法的落地校核，不是第二套 Workflow/Skill/Runner。** R2 的实际三案例候选及反例对照见 [唯一演练与证据记录](workstreams/browser-tool-creation-workflow-r2-20261015.md)。当前已完成的是**一次源证据约束的需求推理演练及文档化关卡**，不是自动安装成品，也不是独立 AI 多轮盲测。

### 10.1 每阶段最小输入、输出、门禁与失败恢复

下表补足第二节九阶段的**执行语义**；每一阶段更新现有工具 README/主交接（不是另建数据库），标注写入人、读取的 source SHA、已验证的能力和待处理项。不得因文档存在就伪造模型读取历史、脚本执行或真实权限。

| 阶段 | 输入 → 必须产物 | 通过判据（PASS 的含义） | 不通过如何收敛 |
| --- | --- | --- | --- |
| 0 恢复 | 一句话 + 当前 main/AGENTS + 工具 README/源码/交接/原型 → **事实账本、锁定的产品决定、冲突表、写入范围** | 每项关键产品决定可定位来源；区分当前源码和旧版本；已核对唯一 owner/变更文件 | 丢失文件时标 `UNAVAILABLE`，不能猜；源码与 README 不同取实际代码为当前实现，决定冲突记录待定；只暂停受影响文件 |
| 1 推理 | 用户原话 + 事实账本 → **目标、角色、触发/频率、S-ID 主旅程、至少一条失败旅程、边界** | 说清“谁在何处用它解决什么”；输入/输出、保存与重新打开可描述；没有技术问卷 | 补充低风险必要步骤为 `AI_INFERRED`；高风险仅问一个 `NEEDS_DECISION`，其余继续；必要时回到阶段 0 查证 |
| 2 功能树 | 场景 + 事实/未定项 → **分层 F-ID 树、P0/P1/OUT_OF_SCOPE、S↔F↔A 双向矩阵** | 每个 P0 叶子的界面、交互、成功、失败恢复、权限/数据、A-ID 都非空；P0 用户旅程无孤儿场景 | 对照用户起点→完成→离开→重开补漏；删除无价值的 AI 新增项；**禁止功能名清单通过** |
| 3 可行性/授权 | 功能树 + 现有 Skill/SDK/运行世界/实际代码 → **权限差距、可复用路径、关键待批准项** | 所有 P0 都有真实实现入口或明确 `BLOCKED`；推断事实未冒充用户授权；**Gate A** 只在阻塞型未知解决或安全降级时通过 | 发现现有 SDK 不支持时改为 `NEEDS_DECISION`/分期、可实施子集继续；不编造 API/Host/权限；不得默认开启危险副作用 |
| 4 交互原型 | Gate A + F/S/A + 正式设计源 → **含正常/空/错误/权限/加载与危险确认的 HTML** | 可点击输入、保存、取消、错误恢复；关键 P0 至少可以**模拟**操作；网页注入与 Side Panel 分面记录 | 源码同源工具用已有 preview 构建，纯设计稿用 Preview Kit；缺 F-ID 场景就补局部视图，不套用静态图片 |
| 5 UI 评审 | HTML + 场景 A-ID + 用户反馈 → **交互检查结果、决策差异、原型源版本** | Gate B：主路径和异常可以实际操作、键盘/焦点/操作反馈合理；没有反历史位置/风格/信息层级的改变 | 用户只改一个需求则追踪受影响 S/F/A/UI，修对应预览；不能反复重画其他已批准页面 |
| 6 正式开发 | 冻结受影响 F/S/A + 真实 Tool/SDK/Host/Design System → **源码映射、版本/包、权限申请实现** | 每个 P0 F-ID 标明源码文件/函数及正负向测试入口；框架/沙箱边界真实保持；源码有别于模拟 HTML | 架构能力缺口交原 owner 的现有 Skill；权限需用户确认；不能在动态工具中塞特权 `chrome.*`，不新建安装器 |
| 7 分级验证 | 当前候选 SHA/包身份 + A-ID + 可用测试环境 → **源码、Node、模拟浏览器、包与真实 Chrome 各级证据** | Gate C：实际运行**过**的每个 A-ID 有结果及同候选身份；未知行为不当 PASS；未测的关键原生项保持 `NOT_TESTED` | 失败定位 F/S/A 和环境，定向回到 4/6；真实环境不可达如实 `BLOCKED/NOT_TESTED`，不重试有未知副作用的写入 |
| 8 交接 | 修改清单 + 门禁结果 + 用户认可范围 → **唯一主文档/交接记录、commit SHA、受影响编号、下一步** | Gate D：独立新对话能凭文件/最新 main 接续；未完成项与所有权清楚；安全正常提交，不冒充发布 | 文件漂移重读再增量合并；失去写权限则明确阻塞；未完成业务不能靠最终总结改成 PASS |

**关卡 A 的实质**：需求完备到足以制作有意义的 P0 原型，不要求已经实现代码。**关卡 B 的实质**：可交互地证实设计，不是几张截图。**关卡 C 的实质**：已执行且可追溯的正确行为，非测试文件的存在。**关卡 D 的实质**：下一次工作可以只读文件接续且不伤害他人的并行改动。阻塞某一 F-ID 不必停止不相交且安全的 F-ID。

### 10.2 一句话需求推理的可检查算法

1. **拆原话，不补写用户意见**：抽取对象、动作、操作位置、目标结果与明确否定词；保留引用。句中没写的数据同步/自动发送/收费绝不升格成 `USER_CONFIRMED`。
2. **先恢复决定，再做常识推理**：以最新明确用户要求、已批准交接/原型、当前正式源码和现有契约为证据；区分“产品同意这样做”与“源码目前已经具备”。已核实的历史决定不会因为新一句短话而清空。
3. **推演完整 S-ID**：对每个核心动作做「进入前→触发→输入→系统作用→可见结果→保存/取消→离开/重开」；按真实风险补失败、空态、权限失效、并发、重复、未知副作用。简单笔记不必强加网站权限场景，书签删除必须有可信确认场景。
4. **生成最小 F-ID**：只把主旅程缺了就不能成立的功能设为 P0；已有明确批准的相关能力也须纳入；改善效率但不影响闭环的设 P1；脱离动机且引入新权限/数据处理的设 `OUT_OF_SCOPE` 或 `NEEDS_DECISION`。
5. **逆向质询**：删除某个 P0，用户是否仍能达到目标？把某个建议加上，会不会要求新的数据访问、付费、云传输或发布？前者若能达成则可能不是 P0，后者不得静默批准。
6. **写出失败预言机 A-ID**：每项至少可观察的成功状态与拒绝/失败后的用户可恢复状态；对写入类操作不以“Promise resolve”代替实际持久化和结果确认，对受保护资源不以 UI 隐藏代替撤权。
7. **审查后只展示一屏人话**：产品目标、2–4 个重要场景、精简功能树、AI 自动补全、最多一个阻塞性待决；详细授权来源、权限清单、测试矩阵折叠在可追踪文档。用户对方案纠正只改变受影响编号，不重新假定全部需求。

每个判断必带 **provenance**（`USER_CONFIRMED`/`SOURCE_VERIFIED`/`AI_INFERRED`/`NEEDS_DECISION`/`OUT_OF_SCOPE`）和理由；`SOURCE_VERIFIED` 的来源要有路径+源版本（必要时函数或行）；`AI_INFERRED` 按低/中/高不确定性标注。**代码存在不意味着权限已有或功能获批准；用户批准不意味着代码已实现。** 同一条功能可以同时保存“用户目标来源”和“实现证据”，不能用一个单标签遮盖两者。

### 10.3 F/S/A 双向追踪与最小差异修复

编号以工具命名空间固定，例如 `F-QN-002`、`S-QN-002`、`A-QN-002`；正式工具已存在编号时**沿用旧编号**并只建立映射，绝不靠重新编号制造“全覆盖”。删除功能留 `RETIRED` 墓碑及原因，不回收 F-ID。

一个 P0 叶子至少有以下列（文档表格或同义 YAML 均可，但不添加第二运行状态库）：

```text
F-ID | 一句话价值/优先级/证据与来源版本
S-ID | 用户/前置条件/具体界面和动作/完成后反馈
A-ID | 可观察成功/失败或撤销恢复/所需数据和权限
UI   | 界面视图与原型来源（没有可见 UI 则标 runtime-only）
CODE | 现有或计划的工具模块/SDK/信任世界（不能编造）
TEST | 定向测试、候选 SHA/环境/结果（未执行=NOT_TESTED）
```

**追踪约束**：
- 任一 P0 的 F-ID 必须能找到 ≥1 S-ID 与 ≥1 A-ID；每条 P0 关键场景 S-ID 必须由 F-ID 覆盖，并有 A-ID；每条 A-ID 的行为可由其关联源码或设计态原型审查，不存在只靠测试数凑覆盖率。
- 有用户操作的 F-ID 必须有 UI 动作和反馈；每一个可点击的危险按钮必须能反向追踪 F-ID、授权和失败/取消 A-ID。正式源码有实际 F-ID→模块/函数→测试证据映射；“计划加入”不能标 `SOURCE_WIRED`。
- 需求变更用 `变更原句→旧/新决定→来源→受影响 F/S/A/UI/CODE/TEST→是否破坏锁定原型` 记录。位置改变只改相应按钮布局与断言；存储 schema 变化才追存储、迁移、消息与恢复。对不相交功能保留已验收证据；若候选 SHA 变化涉及共同依赖，则重新核实影响面，不假复用。
- 三案例的候选编号仅是测试基准，不冒充正式工具原权威文档里的 IDs。正式项目进入阶段 6 前，应将经用户确认的映射写入**原项目 README/需求权威位置**，不是在工作流例题文件维护正式产品决定。

### 10.4 现有 Skill/Workflow/Task/AI Provider 的真实复用边界

**当前可做（人工分段编排，不是自动产品入口）**：

- 普通用户仅输入「做一个 OpenDesk 工具：[一句想法]」。AI 在本对话阅读 `AGENTS.md` + 本工作流 + 原工具 README/交接 → 执行 0–3；一屏摘要供纠正 → 按需调用**现行一个主 Skill**（一般为 `opendesk-sidebar-tool-dev`，需要特权时依据所有权改选 `opendesk-trusted-sidebar-feature` / `opendesk-extension-runtime`），阶段 4–5 用现有 `opendesk-ui-preview`，阶段 6–8 用原 `opendesk-sidebar-tool-package`、官方安装器与测试。Skill 由 AI 路由；普通用户不填写 Skill、Host 或权限字段。
- 静态源码路线：`.agents/skills/README.md` 是八个活跃 Skill 的**文档路由**；`scripts/sidebar-preview-kit.mjs` 是可编辑设计稿的生成与检查；`scripts/preview/build-preview.mjs` 是已有适配的正式包同源 Mock 预览；`scripts/build-sidebar-tool.mjs` 仍是唯一工具打包器。生产预览仅对已支持的 `--tool`/`--surface` 使用，不模拟网页注入为真实 ShadowRoot。预览外壳只用浅色主模板；不新画与 Prompt Shortcuts R1.2 相冲突的界面。
- `src/framework/workflow/contract.js` 的 `opendesk.workflow.v1` 是限权网页 `navigate/observe/fill/click/wait/extract/assert/confirm` 操作；`compiler.js` 生成这些网页动作；`src/ui/workflow/provider.js` 的 AI Provider 规划上述网页动作，原 Task/RunHost 负责执行与回执。**这不是** F/S/A 产品需求→工具工程文件→安装的 Skill Orchestrator，也不能借网页 Task 绕过代码审阅和用户安装手势。
- 历史 Codex Skill 触发评估脚本 `scripts/agent-skills-r22-eval.mjs` 可在真正可用的本机 Codex 环境只读验证路由，但**不能在当前网页会话中把仓库内 Skill 文件的存在当成已成功自动触发**，也不能静默用模型计费替用户执行。
- 未发现已验证的“一句话→功能树→双界面原型→独立工具源码→安装验收”**单一公开运行入口**。将此缺口记为 `PRODUCT_ENTRY_NOT_IMPLEMENTED`；没有检查过的未来消费者记 `NOT_VERIFIED` 而不笼统宣布全仓绝对不存在。

**未来若接入产品入口，最小合同**仅是让一个现有可授权的 AI/编辑入口按阶段读取已有文档并路由现有 Skill，交接使用 `{工具 ID、用户原话、锁定决定/来源 SHA、阶段编号、F/S/A 差异、阻塞项、已有证据、下一动作}` 这些**逻辑字段**（保存在已有工具 README/主交接），不新建独立 Runner/Authority、业务 Store、Task 格式、Provider 密钥通道、隐式 Chrome 许可或第二套配置。每个正式写入与安装动作仍由原权限/打包/用户确认合同执行；产品入口不存在时不能显示“已一键生成安装”。

### 10.5 三案例反方结论与逐维证明限制

[Case A Quick Notes / Case B Prompt Shortcuts / Case C Bookmark Manager](workstreams/browser-tool-creation-workflow-r2-20261015.md) 均先以**一句不完整输入**推理，后以实际源码/已批准原型对照；追踪候选 **23 个 F-ID，各有 S-ID/A-ID**，并保留最小 P0 与未批准建议的区分：

- Quick Notes：必须补存储持久、取消/删除、冲突/未知状态；但不能因 AI 能做就把账户同步或网页自动采集升为 P0。发现 README `1.1.8` 与当前配置 `1.1.9` 不符，是“不能盲信历史说明”的具体反例。
- Prompt Shortcuts：必须恢复双 HTML、左主内容边缘、仅插入不发送、内容优先、右键选区与**两个独立开关**。HTML 模拟内存不代表两个真实视图同步；通用多 AI 架构也不代表其他网站已获授权。
- Bookmark Manager：必须包含 Full 权限、原生分页树、编辑读回、危险目录删除票据、撤权/观察与未知结果恢复；R2.5 当前 UI 候选与后续“原位编辑”提议要按版本区分，不能在工作流演练中改写正式页面。

| 单独评分维度 | 只认可的核心证据 | 此次 R2 状态 |
| --- | --- | --- |
| 需求完整性、场景覆盖、功能树一致性 | 独立真实用户短句盲测、双向映射/反例审查 | `DESK_REVIEWED`，独立重复模型成功率 `NOT_TESTED`，95 分 `NOT_SCORED` |
| 交互质量 | 当前实际 HTML、点击/键盘/异常与 source SHA | R2 未新建或执行 UI，`NOT_TESTED` |
| 技术复用 | 读取真实 Skill/SDK/Runtime/Compiler 与源码归属 | `SOURCE_REVIEWED`；端到端自动调度 `NOT_IMPLEMENTED` |
| 安全 | 许可/身份/副作用的负例 + 同候选真实运行 | 文档与源码风险 `DESK_REVIEWED`；真实安全验收 `NOT_TESTED` |
| 验证可靠性 | A-ID 对应的真实命令、失败日志、包/Chrome 候选身份 | 静态映射可核查；真实产品 `NOT_TESTED` |

目标是各维度 **≥95/100**，但不能靠自评、总平均、案例/文档数量或已有别的候选 PASS 宣称达标。本轮只对现有功能做需求推理与书面反例，不新增安装/授权/发布或真实用户数据访问。

### 10.6 低门槛首屏与下一最小行动

首屏给用户的自然语言回应示例：

> 我理解你要在浏览器侧栏快速记录想法。默认只保存在本机。主要操作是打开、输入、保存、重开与删除确认。为了避免数据丢失，我补充了未保存提醒和保存失败恢复；暂不做云同步。下面是精简功能树与可交互预览；若你只想改某个功能，直接说“把这一项改成……”即可。

技术来源/全部 S/F/A/包身份不强迫普通用户阅读，但在正式文档中可展开复查。**本次最小下一行动**：用 Case A 的单句，在实际可观测的模型+当前 Skill 下从 0→Gate A→HTML 交互原型走一次，记录它自动补全的 P0 漏项、问答次数和真实调用事件；再用 B/C 校验历史一致性、安全和复杂数据。若环境不支持可交互 HTML，应报告限制及可用的完整文件，不能假报在对话中已预览。


## 十一、R2.1：可恢复交付链、证据状态与升级（增量合同）

**继承第十节的 9 个工程阶段和 4 道关卡，不创建第二套状态机或 Registry。** 用户可见的十个环节是对既有阶段的更细进度投影：需求收集（R2-0）→ 场景推理（R2-1）→ 功能树（R2-2）→ 需求审核（R2-3/Gate A）→ HTML 预览（R2-4）→ UI 确认（R2-5/Gate B）→ 源码开发（R2-6）→ 测试构建（R2-7a）→ 原生验收（R2-7b/Gate C）→ 交付（R2-8/Gate D）。

**状态是从已保存产物、批准决定和当前源码版本推算的证据投影，不是新的运行时数据库。** 只用现有工具 README 的 F/S/A 需求和主 workstream 中的阶段断点；不要把十个名字写进 `src/framework/workflow/contract.js`。该文件的 `opendesk.workflow.v1` 只处理受限网页动作，不能调用 shell/Git/构建/安装，也不能将开发权限交给已安装的动态工具。

### 11.1 十阶段检查点合同

每个检查点的公共必填字段：`阶段名称、输入文件/用户话、产物路径、来源/产物 SHA、F/S/A 范围、证据等级、失败或阻塞原因、可安全重试条件、下一步、需用户确认的事项、实际 owner`。文件缺失、SHA 漂移、审批缺失、来源无法读取时为 `NOT_TESTED/STALE/BLOCKED`，不自动提升为 PASS。跨会话应先读 **main + 工具正式需求文件 + 主交接** 再推导有效检查点，历史聊天、无来源的模型总结不是 authority。

| 用户可见环节 | 输入 → 输出 | 必须实际满足才可继续 | 失败、重试与必要人工决定 |
| --- | --- | --- | --- |
| 需求收集 | 用户一句话 + 最新 main/历史决定 → 需求原文/冲突来源 | 原文不被 AI 扩写成“已批准”；实际来源可读 | 文件不可读标 BLOCKED；用户只决定阻断性歧义，非阻断部分继续 |
| 场景推理 | 原文/来源 → S-ID 主旅程、失败和恢复 | 用户、触发、操作、保存/取消、离开/重开、失败恢复齐备 | 缺场景只重推 S-ID，保留已确认来源；未知风险先记录 |
| 功能树 | S-ID → F-ID P0/P1/不做 + A-ID | 全部核心 S↔F↔A 双向可追；无未授权功能 | 缺叶子退回对应场景；新增建议不得静默升 P0 |
| 需求审核 | 功能树/权限/现有 SDK → 决定与批准记录 | Gate A；`NEEDS_DECISION` 的重要权限/不可逆行为已明确获准或安全缩减 | 用户不决定则安全停在该 F-ID，其他独立部分可继续 |
| HTML 预览 | Gate A + 现有 Token/预览 Skill/源 SHA → 交互 HTML | 至少 P0 主流程、空/失败/撤权/危险确认可模拟，源和 Mock 清晰标示 | 对应节点不达标只修受影响原型；模拟绝不是实际安装 |
| UI 确认 | 预览 + 用户反馈 → 定稿来源/差异 | Gate B：关键动作可真实点击且用户接受方案 | 未确认不自动进入危险写入；局部修改不重画其余屏幕 |
| 源码开发 | 已确认 F/S/A + 原工具项目/唯一 SDK/安装器 → 源码映射 | 每个 P0 指向实际函数/文件；缺能力标 BLOCKED，而非伪造 Host | 仅在 owner 范围内改动，不偷走其他 Agent 改动；需许可时阻塞受影响功能 |
| 测试构建 | 现行源码/打包器/Node/Mock → Test、包 SHA、已执行结果 | 同候选 Node/预览/包检查通过；记录测试命令/输出 | 失败按 F/S/A 定向返工；可无副作用重试，源变更则陈旧证据作废 |
| 原生验收 | 明确候选包/版本 + 独立 Chrome/Profile + 用户授权 → 安装、更新、读写、停用/撤权收据 | Gate C：只有实际已安装 Chrome、真实点击/权限和存储读回才 `REAL_CHROME_PASS` | 无环境 `NOT_TESTED`；未知安装/数据修改先读真实结果；不可盲重放，用户确认危险操作 |
| 交付 | 上述检查点 + 实际 diff/提交 → main SHA、已交付/未测及断点 | Gate D：新对话不猜测就能恢复、交付物与安装状态不混淆 | 有并行漂移只重验受影响文件；没真实安装记录不得写“已安装” |

同一阶段可并存 `SOURCE_WIRED` 与 `NATIVE_NOT_TESTED`；不要压缩成一个“完成”布尔量。可见状态建议用「正在整理 / 需要你决定 / 已有预览 / 已完成源码验证 / 等待真实安装验收 / 已交付」，高级面板才显示 F/S/A、SHA 和原始测试。**验证阶段的假 PASS 不得使后续阶段自动推进。**

### 11.2 从最后可信检查点恢复：判定与动作

1. 读取最新 `main`、当前工具 ID 的唯一 README/正式需求、当前源码、原型源锁与主 workstream；建立“上次接受的来源 SHA”与“现在的来源 SHA”的差异，不根据旧对话标签盲恢复。
2. 自最早受影响的 F-ID 回溯它的 S-ID、UI/CODE/TEST 和授权；该 F-ID 及下游输出标 `STALE`，不相交部分保留独立有效的证据。共有 UI Token、安装器、SDK 协议改变时，按真实消费者扩大影响边界，不只靠路径前缀。
3. 最后一个具有**产物存在 + SHA 一致 + 同候选验证证据 + 必要用户批准**的阶段才可复用。纯 `SOURCE_WIRED`、模型文字、未执行的测试文件、Mock HTML 均不能提升为真实安装检查点。
4. `UNKNOWN_EFFECT`（保存/删除/安装/更新/发布/任务执行无明确回执）是**恢复拦截器**：先只读检查真实存储或原生安装状态、当前包哈希/安装代际、用户数据与权限，无法核实时保留草稿和证据、等待人工处理；绝不可把未知结果自动转为下一次写入。
5. 已有批准只覆盖原作用域、版本、Origin、权限和后果；工具 ID/能力/网站权限或危险操作变化须重新独立确认。现有 Host/Authority/安装器是唯一执行权威；开发 AI 不拥有静默 install/release 授权。
6. 交接记录只记真实发现与下一**一个**最小动作，例如「复核 Quick Notes 新版本是否保留 notes 数据」，不为了推进状态删除历史失败证据。

### 11.3 需求变更只修改影响闭包

输入例子：「把 ChatGPT 快捷按钮从输入框附近调整到主内容区域左边缘。」该位置实际上**已经是 R1.2 已确认产品决定**；若最新源码/原型符合，不产生新代码提交。若真实实现偏差，仅定位 `F-PS-004 / S-PS-004 / A-PS-004`，查双 HTML 中网页按钮位置、未来可信 ChatGPT 适配模块的定位以及布局/窄屏/SPA 相关测试；不改变 `F-PS-001/002/003/006/007` 的提示词正文、存储、两个开关、右键菜单，也不重写通用 SDK/安装器。当前正式可信适配路径若尚不存在，写 `NOT_IMPLEMENTED` 而不编造 CODE 路径。

每次差异记录格式在**对应工具原有需求/交接**下追加一条即可：`变更原句 | 旧→新决定与来源 | 受影响 S/F/A | UI 源/正式 CODE/TEST | 权限/Schema/迁移变化 | 复测等级/结果 | 保留原证据的理由`。不得新建全局影响关系数据库。布局变化不会自动导致存储迁移；改变键结构才可能需要迁移/兼容测试。

### 11.4 已安装工具的版本、数据和权限升级

1. **稳定身份**：先核实当前已安装 Tool ID、`tool.config.json` 与实际包 Hash；小功能更新保留原 ID，提升 `major.minor.patch` 中适当版本，禁止“同版本暗改执行字节”，用户确认正常更新。
2. **存储兼容**：找出旧数据键/schema、已有保存/并发标记、迁移时机、失败恢复方式；先读取/验证再写新结构，确保老数据不丢。Quick Notes 已有 `note` → `notes` 兼容读取与旧键清理；`storage.local` 无自动云同步/备份承诺。新“搜索”若能只读筛选现有 notes 数组，就不应擅自变更存储 schema。
3. **权限差异**：逐项比对旧/新 capability、Chrome optional 与站点 Origin，用户明示确认新增或变更的授权；现有权限不可推断为所有新能力已批准。工具更新、启用、网站授权、当前文档、原生操作是不同门槛。
4. **失败回退**：打包/预览失败不影响已安装旧包。更新未知或失败先只读核验实际当前安装 ID/version/hash 与可用数据；不得卸载清空用户数据作为“修复”；需要回退旧包要确认是否与当前存储向后兼容，并按现有安装器显式审阅。
5. **重验闭包**：只读 UI 增强至少复查原有存储/过滤/焦点及升级后数据读回；改 schema、权限、可信代码或安装器时扩大影响到迁移、撤权、更新和真实 Chrome。已测旧候选的 Native PASS 绝不能未经身份核对继承到新包。

### 11.5 工作流正确性与效率必须可反证

现有 `scripts/agent-skills-r22-eval.mjs` 的 `--mode reasoning` 是**相同一句用户输入的只读 Codex baseline/guided 配对评测**，复用原本机 Codex 安全沙箱/日志，不创建第二 Agent Runner；它检查路由/读取事件以及部分关键词提示，只生成 `CHECKLIST_*_REVIEW_REQUIRED`，**不等于模型语义正确或真实用户完成任务**。运行结果私存 `~/.codex-evals/`，需预先已登录和用户知晓模型调用/费用；未经执行仍记 `NOT_TESTED`。

人工盲判实际模型输出时逐例检查：意图、P0 场景遗漏、失败/恢复、未经请求的产品扩张、`USER_CONFIRMED`/推断错位、最新源码/历史冲突处理、P0/P1/OUT_OF_SCOPE、功能树到 UI/CODE/TEST 对齐，以及阻断性问题数量。**任何假造能力或未经许可的危险行为一票否决**，不能靠平均关键词覆盖超过 95 分。

效率实验固定同一个源码 HEAD、模型/设置、相同初始句子、可用 Skill 目录和判卷规则；base 未显式提醒使用 R2，guided 显式使用 R2。原始模型事件/最终文字保存在私有评测目录，分别记录用户额外问答次数、需求→可交互 HTML 修订轮次、HTML↔源码差异、变更涉及文件/测试数量、复用原 SDK/Skill/Host 数、耗时及费用（可获取时）、真实安装结果；**统计只属于实际观察**，未运行不得声称效率提升。评价者应查看完整语义和来源而非仅看关键词匹配。六组输入包含简单、复杂、模糊、相互矛盾和有危险权限的需求，见该脚本。

**当前明确缺口**：OpenDesk 并没有已证实可从浏览器产品入口自动发起 `Skill→项目文件写入→原打包器→用户安装` 的运行时编排。现有 Skill 是 AI/Codex 的指导；本 R2.1 只增强可执行**评估和现有样板链证据**。不得把 `--mode reasoning` 的只读核查当作真实自动开发/安装功能。
