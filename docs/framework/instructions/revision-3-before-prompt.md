## 用户最终能做什么

选择要操作的网页范围并授权 → 输入 async 函数体与参数 → 保存一个版本 → 选择这个版本运行 → 看到返回结果或错误 → 下载结果文件。

首先用下面的脚本跑通真实网页，再验证输入、点击、等待和读取：

```js
await page.goto(params.url);
return { title: await page.title(), url: await page.url() };
```

用户还必须能可靠地使用它：

- 运行版本 A 时保存版本 B，不改变正在运行的 A；删除脚本也不破坏正在运行的版本。
- 运行中能停止，错误和超时能显示原因，不重复执行已经发出的未知写操作。
- 关闭工作台后，旧任务被隔离；重新打开能查到已保存的状态。显式重跑才开始新任务，不恢复旧程序栈。
- 结果和错误确实保存下来；下载确实完成，实际文件内容与记录的 hash 一致。
- 全程不依赖采集模板、采集权限凭证、行数据或封存流程。

## 怎样继续做

1. 先证明用户输入的脚本能安全地运行。沿用已批准后端中 classic Blob 的已有局部证据，补齐实际用户代码、操作等待、停止、隔离和页面执行验证。保留失败加载方式的真实结果。
2. 必需验证通过且独立复核有效后，完成工作台及现有公共底座接线，让用户真正能编辑、保存、选择版本、运行、停止和查看结果。
3. 在真实浏览器中验证整条用户流程、故障情况、版本一致性、持久结果和实际下载文件。所有原始必选用例通过，并完成独立代码与功能复核后，才宣布完成。

继续执行已经授权、可逆且仍在原范围内的工作，不停在说明或计划上。不能用“测试还没做”证明“无法继续”；不能要求四种加载方式全部成功来擅自扩大原合同。某种非必需加载方式失败，只记录并停止该分支，不据此断言整个后端失败。必需能力真实失败、必要前提确实缺失或独立审批不能通过时，按原始停止规则保存证据并暂停；不造替代后端、不扩大研究。

## 用户怎样判断结果

每次报告只写：**已经能做什么、实际验证了什么、还差什么、下一步交付什么。**

需要比较时，只使用“用户要求｜实际操作｜实际结果｜证据｜是否通过”表。失败、未测和不支持必须分开；评分、构建成功、计数和内部状态不能代替功能证据。工程细节放附件，不混入用户说明。
