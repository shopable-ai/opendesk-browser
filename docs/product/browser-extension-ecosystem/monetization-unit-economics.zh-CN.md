# OpenDesk 盈利模式、付费架构与单位经济 R2

> 2026-10-12；**提议的商业模式**，不是已收取的订阅费或真实收入。收费应对应可验证的用户结果和维护价值，而不是按“功能越多越贵”制定价格。

## 一、优先研究的 12 类盈利模式

| 模式 | 谁付费 / 价值单位 | OpenDesk 可复用基础 | 为什么值得/不值得先做 |
| --- | --- | --- | --- |
| 个人 Pro | 开发者/每月或每年 | 开发/诊断/源码管理 | 可低成本验证，但低客单支持成本需控制 |
| 独立 B 专业 Pro | QA、SEO、运营个人/产品许可 | Extension Factory + 特定模块 | 明确单一用途；每产品商店维护 |
| 团队席位 | 研究、客服、运营团队/人月 | 工具模板、权限、协作 | 付费理由是共享、审计、管理 |
| 企业授权 | IT/组织年度合同 | 受信 Host、分区和企业管控 | 采购/隐私合规复杂，可能有续费 |
| 企业定制实施 | 企业/项目验收 | Controller、Page、任务框架 | 最值得先问真实买家，需防范围蔓延 |
| 站点适配维护 | 网站业主、IT/域名和维护期 | Script + Fixture + 更新 | DOM/API 变化带来持续服务价值与成本 |
| 私有白标/ISV 交付 | 合作厂商/合同及维护 | 多产品构建（待完成） | **必须满足 CWS 特定 Host/白标例外条件** |
| 开发者工具链 | 扩展开发团队/构建或席位 | 编译、打包、验证、权限审计 | B 工厂本身成熟后才出售 |
| 作者发行托管 | UserScript 作者/项目或席位 | C 市场、版本和许可证 | 先证明安全发行和作者愿付费 |
| 合法 SaaS API/监测 | 有持续云服务需求的用户/额度 | SDK + 可选后端 | 数据合法来源、配额和成本很关键 |
| 合法生态交易服务费 | 付费工具作者/成交 | 市场交易与审核（尚未实现） | 税务、退款、恶意代码、对账昂贵，后期再说 |
| 优惠返利/推广 | 商业伙伴/明确用户受益的交易 | 购物脚本或 SaaS | CWS Affiliate 严格约束，默认不纳入前期收入 |

不建议把“销售用户浏览数据”“静默植入广告或返利 Cookie”“大量换皮插件销售”列为商业模式。

## 二、官方支付与 CWS 合规底线

Chrome Web Store 原生支付系统已停止新支付；参考 [Google 官方源码中的支付退役说明](https://github.com/GoogleChrome/developer.chrome.com/blob/main/site/en/docs/webstore/cws-payments-deprecation/index.md)。新的付费扩展应另行选择合规支付处理方，清楚披露价格、续订、退款、卖家身份和隐私处理；[CWS 接受用户付款政策](https://developer.chrome.com/docs/webstore/program-policies/accepting-payment)。

最低商业身份分层：
- Chrome 扩展 ID：发行和安装身份，**不是账号或许可证**。
- 付费账号 / 企业组织：收款、席位、订阅、订单和税务责任。
- Entitlement：按产品+账号/组织+许可版本授权付费功能；不能信任 UI 中的 paid=true。
- Chrome Host/Authority：每次真实 API 操作仍独立检查网站、目标、操作和用户许可；付费**绝不绕过** Chrome 权限。
- 本地使用和离线：能离线的免费基础功能尽量独立；订阅功能离线宽限期、停订数据导出、换机和迁移另立合同。
- 不将支付密钥嵌入扩展；敏感订单和支付信息不写入公开日志。

## 三、定价验证而不是先编造“合适价格”

观察买家原有替代开销、采购权限、维护期望，再用真实报价、合法的付费候补、试点合同或小规模价格实验验证。**非真实支付、非采购意向书不能记为收入。**

可测试的定价单位：个人/月或年、企业/团队席位、组织年度协议、站点/月维护、项目实施费、合法 API 用量。选择用户能理解、成本能控制的单位。一次性无维护工具可试买断；长期更新/云任务/团队管理更适合订阅或 SLA。

竞品存在性：Text Blaze 的[官方价格页](https://blaze.today/plans/)在 2026-10-12 检索显示 Free、Pro（年缴折算 $2.99/月）、Business（年缴每席 $6.99/月）、Enterprise 联系销售。它证明此类工作流有**分层定价实例**，但不证明 OpenDesk 应沿用数额、拥有一样的利润或市场需求。

## 四、严格区分收入、贡献与利润

| 指标 | 计算方式与必要数据 |
| --- | --- |
| MRR | 活跃实际付费订阅账户/席位 × 净月合同价；排除免费用户 |
| 客户月贡献毛利 | 到账收入 − 支付/退款 − 可变 API/服务器 − 可变客服与支持 |
| 产品月度贡献 | 全客户贡献毛利 − 研发、适配、CWS 发版/审查、法务等固定成本 |
| 渠道 CAC | 同口径获客与销售支出 ÷ 净新增**付费**客户（0 时不可计算） |
| 回本月数 | CAC ÷ 新付费客户月贡献毛利（毛利 ≤ 0 时无正向回本） |
| 付费留存 | 同一 cohort 期末仍付费 ÷ 同一 cohort 期初付费；注明窗口 |
| LTV | 仅在真实毛利和 churn 有可靠队列证据时估计；否则 NOT_MEASURED |

每个独立 B 扩展除了共享代码，还应分摊商店审核、Chrome 版本升级、支持、隐私披露、回滚、站点变更与维护者值班成本。**安装总量、编译速度、已生成插件数量都不是收入指标。**

## 五、收费和用户信任的冲突治理

- 若收费基础功能，安装前明确告知，免费试用承诺与实际可用功能一致。
- 不因开通 Pro 自动读取全部浏览历史、私有页面或 Cookies；逐项授权。
- 禁止将访问网页得到的数据用于个性化广告或出售给数据商。[Limited Use](https://developer.chrome.com/docs/webstore/program-policies/limited-use)。
- 购物联盟必须事先披露，带来当下直接透明的用户收益，并且每次应用代码/链接/Cookie 前有相关用户操作。[Affiliate Ads](https://developer.chrome.com/docs/webstore/program-policies/affiliate-ads)。
- 广告若被研究，也应是清楚标注、可移除、不干扰原站的独立合规产品行为，不能破坏用户体验或模仿系统提示。[Ads](https://developer.chrome.com/docs/webstore/program-policies/ads)。

## 六、最先验证哪种付费组合？

**建议从服务可成交性开始，逐渐产品化。**
1. 企业重复表单/报表：一项固定范围的试点实施费 + 可选明示的年度维护。
2. 电商卖家 Listing/SKU/毛利辅助（EXP-005）：先核实日常任务、合法后台数据、购买者和适配成本，再研究席位或维护费。
3. 消费者实际到手价/购物决策（EXP-007）：先证明价格准确与重复使用，不预设消费者订阅或购物联盟佣金。
4. 研究剪藏、UserScript 作者发行与 Factory B2B2C：保留独立候选，先有可验证价值再讨论收费。

**Page QA Inspector 商业定价设想已归档；当前仅为 `DEPRECATED / NO_RELEASE / MANUAL_FIXTURE_ONLY` 工程历史样品。**

商品的统一止损门：长周期用户无法留存、单位贡献为负、服务无法合法交付或维护时间无法覆盖收入，则调整商业形态或暂停投入。
