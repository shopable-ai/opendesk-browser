# GreyDove Marketing Universe：全球内容营销与 SEO/GEO 扩展规则

版本：1.0  
建立日期：2026-11-17  
适用品牌：GreyDove（灰鸽）  
品牌方向：Browser Automation & Scripts（浏览器自动化与脚本工作台）  
文件性质：长期营销方法、内容架构与 AI 内容生产规则；不是对外宣传文案，也不是产品功能交付证明。

## 1. 本规则要解决什么问题

GreyDove 的内容营销不能只围绕品牌名、产品介绍或少数功能写文章。用户在认识 GreyDove 之前，通常会先搜索自己遇到的问题、正在使用的竞品、可替代工具、实现方法、行业工作流和技术概念。

因此，GreyDove 应建立一个持续扩展的 **Marketing Universe（营销内容宇宙）**：

> 以真实用户问题和搜索意图为入口，以市场/竞品/替代方案为参照，以可验证的产品价值为连接点，通过主题集群、内容关联和转化路径，让不同搜索入口的读者逐步理解问题、比较方案、验证 GreyDove 是否适合自己，并最终尝试和持续使用产品。

这不是“为了 SEO 多写文章”，而是持续建设一套市场知识资产和用户获取系统。

内容宇宙应覆盖：
- 用户问题：用户为什么搜索、想完成什么任务、目前怎样解决。
- 市场类别：用户脚本管理器、浏览器自动化、RPA、AI Browser Agent、浏览器扩展开发工具等相邻领域。
- 竞品与替代方案：用户正在用什么、还有哪些工具组合、各自适合谁。
- 方法与教程：用户如何解决问题、如何选择、如何实施。
- 行业场景：重复出现的真实业务流程和用户工作。
- 产品证据：GreyDove 当前版本究竟能做什么、需要什么前置条件、有哪些限制。
- 转化与留存：如何从文章进入真实演示、安装、首次成功和后续复用。

## 3. 营销内容宇宙的总体结构

内容不应是互相孤立的文章，而应组成“核心支柱页 → 主题集群 → 具体问题页 → 产品证据/行动入口”的网络。

### 3.1 八大内容支柱

| 支柱 | 主要回答的问题 | 典型内容 |
| --- | --- | --- |
| A. 市场类别与概念 | 这些工具是什么，有什么区别？ | Userscript Manager vs Browser Automation；RPA vs Browser Agent；浏览器脚本与扩展的区别 |
| B. 竞品比较与替代方案 | 已有工具有什么优缺点，如何选择？ | GreyDove vs Tampermonkey；ScriptCat vs Tampermonkey；Tampermonkey alternatives；Automa alternatives |
| C. 用户问题与解决方案 | 某个具体问题怎样解决？ | 如何自动填写重复表单；如何在网页运行 JavaScript；如何把重复操作做成可复用任务 |
| D. 教程与实践 | 具体步骤是什么？ | 编写网页脚本、调试、管理权限、固定依赖、创建浏览器自动化任务 |
| E. 行业与角色场景 | 哪类人会遇到什么重复工作？ | 电商运营、客服、开发者、QA、研究人员、行政运营的合法网页工作流 |
| F. AI 与自动化工作流 | AI 如何参与创建、审阅、执行和复用？ | AI-created browser tools；AI-to-reusable task；AI 编写脚本后怎样验证 |
| G. 安全、权限与可靠性 | 怎样判断脚本可信、执行可控？ | 网站权限、脚本来源、依赖锁、版本审阅、撤权、失败恢复 |
| H. 生态、兼容与迁移 | 不同工具、浏览器和技术怎样协作？ | GM API 兼容、MV3、User Scripts API、WXT/Plasmo、脚本迁移与限制 |

支柱是长期主题，不代表每个支柱都要立即大量发布。应先选择有真实用户需求、与当前产品价值相关、能拿出证据的内容。

### 3.2 竞品比较是重要入口，但不是唯一入口

竞品相关内容可覆盖多种搜索意图：

- 品牌对比：GreyDove vs Tampermonkey。
- 竞品对比：Tampermonkey vs ScriptCat。
- 替代品清单：Tampermonkey alternatives、Automa alternatives。
- 细分场景比较：用户脚本管理器 vs RPA、Browser Agent vs deterministic automation。
- 迁移与兼容：Can a Tampermonkey script run in GreyDove? 只有有真实兼容矩阵时才可发布为确定答案。
- 选择指南：Best browser automation tools for developers / operations teams。必须定义评估范围、候选集和测试日期，不能伪装成无依据的客观排名。
- 竞品深度评测：分别介绍对手的真实优势、局限、适用用户和当前版本。

对比文章的目的不是证明 GreyDove 在所有方面都更好，而是帮助读者做出正确选择，并解释 GreyDove 在哪些任务、条件和工作流上值得考虑。

## 4. 从“搜索词”扩展为“用户问题图谱”

每个主题都要从真实用户任务出发，而不是先堆关键词。

一个可复用的选题展开方式：

1. 用户正在使用什么工具？
2. 用户想完成什么任务？
3. 现在的工具在哪些情况下足够好？
4. 用户遇到的限制、成本、摩擦或风险是什么？
5. 用户会搜索什么问题、比较什么方案？
6. 有哪些直接竞品、间接竞品和工具组合？
7. GreyDove 对这个问题是否有真实、可证明的价值？
8. 当前版本是否已经能让读者完成该任务？
9. 读者下一步最合理的行动是什么？

### 4.1 示例：围绕 Tampermonkey 建立主题集群

核心主题页：
- 浏览器用户脚本、自动化与 RPA：工具类别和选择指南。

比较文章：
- GreyDove vs Tampermonkey：用户脚本管理器与浏览器自动化工作台的区别。
- Tampermonkey vs ScriptCat：功能、生态、权限与适用人群。
- Violentmonkey vs Tampermonkey：开源、兼容和脚本管理差异。
- Tampermonkey alternatives：有哪些替代方案，分别适合谁？

问题与教程：
- 什么是 UserScript？.user.js 怎样工作？
- 浏览器脚本管理器与 Chrome 扩展有什么区别？
- 如何编写一个简单的网页 JavaScript 脚本？
- 如何让重复的浏览器操作变成可复用自动化任务？
- 如何检查浏览器脚本的来源、依赖和网站权限？

兼容与迁移：
- Tampermonkey GM API 与 Chrome User Scripts API 有什么区别？
- 一个现有油猴脚本能否迁移到 GreyDove？
- 从用户脚本转向浏览器自动化任务，需要改变什么？

注意：兼容、迁移类文章必须有逐 API、逐脚本或逐场景证据。没有验证时，应写成“兼容性研究/当前限制”，不能写成“完整支持”或“无缝迁移”。

### 4.2 示例：围绕浏览器自动化建立主题集群

核心主题页：
- Browser Automation Guide：浏览器自动化是什么，如何选择实现方式？

比较文章：
- Browser Automation vs RPA。
- Browser Agent vs 固定脚本自动化。
- Playwright vs 浏览器扩展自动化。
- Automa vs Axiom vs 代码型浏览器自动化。

问题与教程：
- 如何自动填写重复网页表单？
- 如何从网页读取结构化数据？
- 如何重复执行一个多步骤网页流程？
- 如何在 AI 生成脚本后验证它？
- 浏览器自动化每次运行都需要 AI 吗？

场景文章：
- 电商商品信息检查。
- 客服后台重复查询。
- 运营表单和数据核对。
- 网页 QA 与回归检查。

所有行业文章都必须验证真实需求、用户权限、业务准确性和产品可用性。不能因为某个行业关键词有搜索量，就把尚未实现的行业工具包装成已交付产品。

## 5. 搜索意图与内容漏斗

每篇文章应有一个首要搜索意图和一个主要读者，不要一篇文章同时争夺所有关键词。

| 阶段 | 读者心态 | 内容类型 | 合理 CTA |
| --- | --- | --- | --- |
| 认知 Awareness | 我遇到了问题，但不知道有哪些方案 | 概念解释、问题解答、教程、行业场景 | 阅读相关指南、查看演示 |
| 比较 Consideration | 我正在比较工具或替代方案 | 竞品对比、替代品、选型指南、兼容说明 | 查看功能证据、对比真实限制 |
| 评估 Evaluation | 我想知道它是否适合我的实际任务 | 实测、案例、安装前置、权限说明、成本对比 | 尝试当前可用版本、运行合法 Demo |
| 转化 Conversion | 我准备安装或开始使用 | 安装指南、版本选择、商店页面、快速开始 | 安装、开始首次任务 |
| 留存 Retention | 我已经使用，想提高效率或解决问题 | 进阶教程、故障排查、更新说明、工作流案例 | 完成下一次任务、复用已有工具 |

CTA 必须指向真实存在、可访问且符合当前产品状态的入口。官网、Chrome Web Store、Demo、下载、隐私政策或支持链接尚未正式部署时，不得编造链接或宣称已上线。

## 6. 竞品研究和比较文章的硬性规则

竞品文章必须以公平、最新和可复核为基础。

### 6.1 竞品事实核验

每个对比对象至少记录：

- 产品名称、官网、官方文档和公开仓库（如有）。
- 当前版本号、发布日期、稳定版/Beta/Preview 状态。
- 目标浏览器、操作系统和地区可用性。
- 关键能力及其官方说明。
- 许可、定价和使用前置条件（如与文章相关）。
- 证据类型：官方文档、公开源码、商店版本、实际测试、用户报告或研究推断。
- 信息核查日期和来源链接。

不能把 GitHub main 分支的开发代码写成稳定版已发布能力；不能把 Beta 说成正式稳定版，也不能把历史缺陷说成当前版本缺陷。

### 6.2 比较对象必须包含最强替代方案

不能只选弱小或过时竞品。用户实际完成任务时可以使用合理的工具组合，因此对比应包含：

- 单一直接竞品。
- 同类产品中的强势替代品。
- 可以组合完成同一任务的工具链。
- 浏览器或操作系统原生能力。
- 当原生能力已足够时，承认用户没有必要安装 GreyDove。

例如，比较网页脚本开发时，不能只比较 Tampermonkey 的编辑器，还应考虑 Vite、vite-plugin-monkey、WXT、Plasmo 与用户脚本管理器的组合。

### 6.3 比较维度应按用户任务选择

不要每篇文章机械复制一张功能表。可选择：

- 用户要完成的任务及成功定义。
- 首次设置和安装前置条件。
- 日常操作步骤与维护负担。
- JavaScript / UserScript / GM API 兼容程度。
- 跨页面、跨标签或页面增强能力。
- 权限和安全边界。
- 固定版本、依赖和更新机制。
- 是否需要 AI、Native、Node 或云服务。
- 单次运行成本、重复运行成本和维护成本。
- 可观察结果、失败处理和恢复能力。
- 用户数据、隐私和可迁移性。

每个结论应标注事实、测试结果或推断。没有同条件实测，不得给出性能领先或总体排名。

### 6.4 竞品比较要能诚实回答“谁应该选对方”

每篇比较文章都必须写清楚：
- 哪些用户应该继续使用竞品？
- 竞品有哪些 GreyDove 暂时不具备的成熟能力？
- GreyDove 当前在哪些具体工作流值得尝试？
- 有哪些限制和额外前置条件？
- 何时用户根本不需要更换工具？

诚实地建议用户继续使用竞品，不会削弱品牌；它能提高文章可信度，减少错误预期。

## 7. 产品事实、宣传声明与证据等级

营销内容只能使用与当前版本相符的产品事实。

必须区分：
- 研究设想 / ROADMAP。
- 源码存在 / SOURCE_IMPLEMENTED。
- 组件测试 / COMPONENT_TESTED。
- 构建验证 / BUILD_VERIFIED。
- 真实 Chrome 原生验证 / CHROME_NATIVE_VERIFIED。
- 正式发行 / PUBLICLY_RELEASED。
- 用户实际采用与业务结果 / USER_VALIDATED。

这些状态不可互相替代。源码有实现不等于普通用户可以安装；Node 测试通过不等于真实 Chrome 通过；Chrome 本地通过不等于已经上架；上架也不等于用户已经获得价值。

沿用 marketing-playbook 的宣传级别：
- M0：准确的产品方向与有边界的现有能力描述。
- M1：绑定具体发行版本、源码/包身份和真实演示的功能主张。
- M2：在预先定义的任务、设备、对手、时间和数据集上完成公平基准后，才能发表限定范围的比较结果。
- M3：只有 first-claims-ledger.json 对应声明获批后，才能使用符合审批范围的全球/区域/类别“第一”等主张。

以下词语不得无证据使用：全球第一、世界首个、最安全、最快、完全兼容、所有网站、零配置、无需许可、永久后台、永久免费、无成本、100% 成功。

新增排名或首创声明必须先进入唯一的 first-claims-ledger.json 流程。不能在博客、广告、客服、社交媒体或视频简介中绕过审批。

## 8. SEO 与 GEO 内容质量规则

目标不是制造关键词页面，而是让每篇内容成为值得用户阅读、搜索引擎索引和其他系统准确引用的事实资源。

每篇正式文章应满足：

1. 直接回答标题中的问题，重要结论放在开头。
2. 有明确读者、任务、搜索意图和适用范围。
3. 提供原创分析、实际步骤、真实截图、数据、代码示例或可复现证据中的至少一种；比较文章应有自己的比较方法。
4. 关键事实引用一手来源，竞品能力优先使用官方文档、发行说明、公开源码和商店页面。
5. 明确更新时间、版本、浏览器和功能限制。
6. 提供适量内部链接，连接支柱页、相关比较、教程和产品证据。
7. 使用自然语言覆盖同义表达，不堆砌关键词。
8. 标题、Meta Description、URL slug 与正文内容一致。
9. 页面正式上线时配置正确的 canonical、可抓取正文、sitemap 和适用的结构化数据。
10. 只有真实存在且可访问的产品入口才可以作为 CTA。

不得：
- 批量生成只有关键词或竞品名称不同的薄内容页面。
- 将同一篇文章简单改写成多个城市/国家版本以获取流量。
- 虚构搜索量、排名、流量、引用次数、客户案例和转化率。
- 把 AI 搜索引用、品牌提及或搜索曝光直接当作新客户。
- 为了排名隐藏限制、误导比较或贬低竞品。
- 在官网尚未部署时宣称文章已被 Google/Bing 收录。

GEO（生成式搜索优化）应建立在清晰、准确、可引用的事实内容上，不承诺任何 AI 系统必然引用或推荐 GreyDove。

## 9. 选题发现与优先级

选题来源包括：

- Google/Bing 搜索建议、相关问题、Search Console、Bing Webmaster Tools。
- Chrome Web Store 评论、GitHub Issues、竞品论坛和官方社区。
- Reddit、开发者社区、问答网站、YouTube 评论和公开讨论。
- 客服咨询、用户访谈、真实使用过程中的失败点。
- 竞品更新日志、产品文档、API 变化和兼容性问题。
- GreyDove 自身的真实任务、Demo、测试证据和功能缺口。

每个选题先建立一份 Brief，至少写清：
- 目标用户与真实任务。
- 用户原本使用的工具/方法。
- 首要搜索意图和自然语言问题。
- 内容类型与主题集群。
- 直接竞品、间接竞品和最强替代方案。
- GreyDove 的关联价值。
- 当前可用功能和证据。
- 不可宣传的功能或未经证明的结论。
- 文章独特价值、CTA 和内部链接。
- 事实核查日期与下次复核条件。

### 9.1 内部优先级评估

可用 1–5 分进行内部选题排序，建议维度：

| 维度 | 权重 | 判断问题 |
| --- | ---: | --- |
| 用户问题强度 | 20% | 是否存在明确、重复、真实的用户痛点？ |
| 产品关联度 | 20% | GreyDove 是否对这个问题有实际价值？ |
| 证据准备度 | 20% | 能否提供源码、测试、实测、截图或可复现材料？ |
| 搜索意图清晰度 | 15% | 是否知道读者在搜索什么、想得到什么答案？ |
| 转化相关性 | 15% | 读者完成阅读后是否有合理下一步？ |
| 内容差异化与维护成本 | 10% | 是否提供独特价值，信息是否容易过时？ |

该分数只用于决定先研究或先写什么，不是文章质量、市场规模、SEO 排名或专家认证。证据准备度为 1–2 的主题，可以先做研究，不应直接发布产品宣传文章。

### 9.2 选题状态

建议统一使用：
- IDEA：仅发现想法。
- RESEARCHING：正在核对用户需求和市场。
- BRIEF_READY：选题 Brief 完成。
- EVIDENCE_BLOCKED：产品或竞品证据不足。
- DRAFTING：正在写作。
- FACT_CHECK：事实与来源审核。
- READY_TO_PUBLISH：内容审核完成。
- PUBLISHED：正式公开发布。
- UPDATE_REQUIRED：版本、竞品或产品事实发生变化。
- RETIRED：内容已过时或不再适用。

## 10. 每篇文章的标准结构

文章不要求完全相同，但建议至少包含：

1. 标题：明确用户问题或比较对象。
2. 开头结论：直接回答读者最想知道的问题。
3. 适用读者与场景。
4. 用户问题与搜索意图。
5. 方案/竞品/工具的真实介绍。
6. 对比方法和评估维度（比较类文章）。
7. GreyDove 对应的能力、限制和前置条件。
8. 真实证据、可复现步骤或来源。
9. 何时选择 GreyDove、何时选择其他工具。
10. FAQ：回答相关但不同的真实问题。
11. 下一步 CTA。
12. 进一步阅读与相关内容。
13. 来源、版本和最后核查日期。

每篇文章的编辑元数据应包含：
- Content ID（稳定标识）。
- 内容类型与主题集群。
- Primary Search Intent。
- Primary Query 与 Secondary Queries。
- 目标语言/地区。
- 目标读者。
- 对比对象及版本（如适用）。
- 产品版本和证据等级。
- SEO Title、Meta Description、Slug。
- 内部链接与外部来源。
- CTA 目标。
- 状态、作者/审核者、发布日期和复核日期。

## 11. 内部链接与内容关系

每篇文章不能成为孤岛。建立有意义的双向内容关系：

- 竞品比较文章 → 类别解释页、对应竞品专题、相关教程、GreyDove 产品证据页。
- 教程文章 → 对应产品功能说明、常见问题、示例项目。
- 行业场景文章 → 真实工作流、合法数据边界、相关自动化教程。
- 安全文章 → 权限说明、版本管理、安装/更新文档。
- 支柱页 → 汇总并链接所有相关主题集群。
- 相关子文章 → 回链支柱页，必要时链接同一用户旅程的下一步内容。

链接必须帮助读者继续解决问题，不为提高链接数量而机械互链。每篇文章应有一个主要转化目标，避免多个 CTA 争夺注意力。

## 12. 双语与全球化

GreyDove 的品牌面向全球，但不能把中文文章逐字翻译成英文就认为完成全球 SEO。

对英语、中文、日语等市场，应分别核查：
- 当地用户实际使用的产品名称和搜索表达。
- 当地市场的主要竞品、替代方案和发行渠道。
- Chrome Web Store 地区可用性。
- 当地隐私、权限、法律和商业环境。
- 该语言版本是否有真实可用的安装、演示和支持路径。

每个地区页面应有自己的用户问题、竞品和证据。没有本地证据时，不使用“日本第一”“中国领先”“欧美最受欢迎”等区域宣传。

## 13. 内容表现与商业结果

SEO 不能只看关键词排名。至少分层观察：

### 搜索表现
- 搜索查询、地区和语言。
- 展示量、点击量、CTR、平均位置。
- 搜索结果是否与页面意图匹配。
- 页面索引、canonical 和抓取状态。

### 内容参与
- 阅读深度、有效停留、内部链接点击。
- 读者是否进入演示、安装指南或功能说明。
- FAQ 和教程是否真正解决问题。

### 产品转化
- Chrome Web Store 页面访问和安装（在可获取数据时）。
- 首次成功安装/授权/任务完成。
- 首次成功时间与失败原因。
- 7 天 / 30 天自然复用。
- 合格线索、付费意愿和实际商业结果（如产品已具备对应能力）。

### GEO 观察
- AI 搜索引用的页面和查询（仅在工具可用时）。
- 引用是否准确、是否遗漏关键限制。
- 引用带来的真实访问和后续转化。

搜索曝光、AI 引用、点击、安装、首次成功和长期复用是不同指标。不得把其中任何一个自动等同于收入或产品市场契合。

## 14. 内容维护与更新

内容宇宙是持续维护的市场知识，不是一次性发文项目。

以下事件触发复核：
- GreyDove 新版本改变了可宣传的功能。
- Chrome API、Chrome Web Store 政策或浏览器版本要求变化。
- 竞品发布新稳定版、Beta、价格或关键能力变化。
- 原文引用的产品链接、下载链接、商店链接失效。
- Search Console/Bing 数据显示搜索意图发生变化。
- 用户反馈指出事实错误或文章没有解决问题。

竞品比较文章应在发布后定期复核，建议至少每 90–180 天检查一次；快速变化的 AI/浏览器产品应更频繁。过时文章应更新、明确标注历史版本，或退役，不能保留过时比较冒充当前结论。

## 15. AI 内容生产的统一执行规则

AI 可以承担市场研究、搜索意图归类、竞品资料整理、内容 Brief、初稿、内部链接建议和更新检查，但不能在没有证据的情况下自动发布。

AI 每次处理选题必须：
1. 读取当前 main 的营销规则、品牌规范、相关产品文档和竞品资料。
2. 识别这次工作是市场研究、选题、Brief、写作、事实核查还是更新。
3. 搜索并记录当前一手来源，注明版本、日期和证据等级。
4. 查找最强竞争反例和合理工具组合。
5. 对照当前产品真实能力，不将规划内容写成已交付功能。
6. 输出独特的用户价值，不复制现有文章或只替换关键词。
7. 标记所有未知、待验证和不可宣传事项。
8. 建立内部链接和明确 CTA。
9. 更新选题状态和复核日期。
10. 未经明确授权不得擅自发布到官网、商店、社交媒体或广告渠道。

禁止为了满足文章数量目标而生成内容重复、事实薄弱或没有用户价值的页面。
