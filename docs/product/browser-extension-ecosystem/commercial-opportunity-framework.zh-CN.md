# OpenDesk 商业机会发现与筛选框架 R2

> 2026-10-12。**研究模型**，不是实际付费收入或用户访谈结论。仅增量关联 [84 条 OPP](opportunity-register.json) 与原 R8 188 项能力 / E01–E40，不创建第二份功能账本。

## 一句话结论

**从“能够开发什么扩展”转向“谁反复遇到具体问题、谁有预算、谁愿意持续为可靠结果付费”。** OpenDesk 的工程复用能力是成本优势，不是需求和分发的证据。

## 一、五层机会漏斗

| 层级 | 决策问题 | 必须要有的真实依据 |
| --- | --- | --- |
| 用户工作 | 哪个岗位、哪个网站页面、哪一步重复/出错？ | 真实任务观察、使用频率、现有解决方法 |
| 经济损失 | 一次失败耗费什么时间/资金/责任？ | 真实返工/工时/错误记录，不能拍脑袋 |
| 购买者 | 真正能批准付费的是用户、主管还是 IT？ | 明确采购角色、预算和当前付费替代 |
| 产品形态 | UserScript、OpenDesk 工具、独立扩展还是云服务？ | 权限、单一用途、实时数据、分享与维护要求 |
| 长期经营 | 如何获客、续费、修网站适配器，收入能否覆盖成本？ | 渠道成本、支付行为、更新工时和留存 |

同一问题可能先作为 A 内的工具（免费验证）→ C 网站脚本包（自然传播）→ B 垂直产品（专业付费）；这不是必须走完的流水线。应为每个需求选最轻的合适交付方式。

## 二、14 个商业机会思考视角

| 视角 | 如何发现 | 下一步怎么验证 |
| --- | --- | --- |

| 高频重复 | 多人反复复制、填写、验证 | 记录自然工作周期的次数 |
| 错误成本 | 审批、发布、报告漏项 | 找有记录的返工或损失 |

| 现有付费产品 | 已有人为类似工作付费 | 用官方价目和真实采购证据确认 |
| 新手使用门槛 | 用户有价值但不会写 JS | 用零安装和无引导试用验证 |

| 获客渠道空白 | 用户搜索解决问题而非“插件” | 测试精准教程/行业合作渠道 |

这些视角是**发现问题的方法**，不是“14 个领域 × 12 行业 × 每站点一个扩展”。如果命中已有 OPP，增补证据；有独立购买者和不同工作成果才考虑新增 OPP。

## 四、从想法到商品的五道 Gate

1. **G0 合法/安全**：CWS 单一用途/重复内容、权限、网站条款、数据许可、隐私；任一失败立即 BLOCKED。
2. **G1 真痛点**：目标用户实际做过该任务，能解释现有替代和频次/损失。
3. **G2 真可用**：一次真实 Chrome 点击流程、可解释错误、停用和恢复；静态 Demo 不算。
4. **G3 真留存和付款**：自然再次使用、真实报价/审批/订单。口头“愿意买”仅是线索。
5. **G4 真经济性**：付款减可变成本/支持/适配后仍合理；能保障升级、回滚和终止服务。

每个 Gate 独立判定。不能用平均分制造“95+ PASS”；没数据时写 NOT_MEASURED / NOT_TESTED。

## 五、四条优先商业假设

- **短期现金流假设**：向已有重复网页工作流的企业卖“明确任务的部署+维护”，先验证能否付费，而不是先做全能 SaaS。
- **商业产品假设（电商优先）**：先调查卖家 Listing/SKU 等有预算的运营重复工作流，以及消费者实际到手价的真实价值与合法来源；优先用 A 工具或 C 脚本验证，确认付费、维护、差异化后才考虑 B 独立扩展。此前 Page QA 首款商业立项已废弃，仅留技术样品。
- **长期留存假设**：Research Clip & Cite 先看连续两次自然工作周期是否主动引用，再考虑付费团队协作。
- **生态基础设施假设**：脚本作者的发布/更新/回滚服务先做安全试运行；没有作者付费证据前，不计算抽佣。

实验具体定义和零结果状态见 [commercial-experiments.json](commercial-experiments.json)。

渠道：实际岗位工作观察、公开竞品/价格、网站产品更新、Greasy Fork 脚本维护请求、GitHub issues、专业论坛、企业销售访谈、现有 OpenDesk 工具自愿反馈。商业记录必须有检索日期、产品版本和确切来源；公开仓库不保留个人 Cookie、企业原始工作页、支付凭证。

## R1.0-WEB · 2026-10-20 商业机会决策增量（研究状态，不替代已有 OPP/EXP）

> 检索日：2026-10-20；基于 GitHub main 上已有 84 条 OPP、R5 24 个领域 / 45 个竞品研究入口，以及本轮对竞品官网、CWS 商店和 Google 官方政策的公开检索。下列 30 条是已有 OPP 的**引用子集**，不是新增或重编号；竞品特性和价目来自公开自述，不是对付费人数、营收、留存或本机产品体验的证明。FACT / HYPOTHESIS / MISSING 不得互相升级。

### R1 战略判断

1. **竞争的是具体工作结果，不是浏览器扩展数量。** 以免费单一任务获得第一次自主成功；将可核对的结果交付、团队协作、维护、企业适配和业务系统集成变成有独立购买者的付费品。OpenDesk 框架复用是内部成本优势，不能单凭它证明市场需求。
2. **三条候选路径**：A AI 提示词/文字/图片的结构化保存并投递；B 授权企业网页表单/操作执行与部署维护；C 合法来源的卖家 Listing、行业资料及报表核查/整理。不要把未经授权的整站抓取、竞品 Cookie、广告注入或刷商店评价作为流量策略。
3. **分发形态分离**：A 先做可用的当前浏览器内工具与页面按钮，再根据用户需求审核独立 CWS 单用途扩展；B 先卖一项有范围的授权实施合同，未必要在 CWS 公开上架；C 只从官方导出/用户提供的 CSV/被允许读取的数据切入，再考虑云同步/监控服务。
4. **渠道判断**：先任务意图词+内容 SEO+真实 CWS Listing；竞争品牌词只能小额验证，既不默认便宜，也不误用商标广告文案。见 [获客验证](distribution-and-validation.zh-CN.md)。

### 唯一先行可证伪产品：AI 图文工作产物交付（EXP-003）

产品单一用户承诺：**用户在 ChatGPT 等已授权网页主动选择一段回答、提示词或生成图片，保存为可追溯、可读回、可导出的本地工作产物；可选人工指定目的地。** 它不是浏览历史后台采集器或重新实现通用浏览器自动化。

1. 打开获用户允许的 AI 页面，点一个显眼但克制的「保存」动作；不自动发送输入、抓取其他会话、扫描所有标签页。
2. 用户选择内容/图片及来源；展示实际将保存的文本、URL、时间、图片数、文件体积和可改名标题。图片如果只是短期 URL，不能把 URL 当作图片已持久化成功。
3. 调用已有可信工具/Browser SDK 能力保存；要求明确写入回执和重开后读回。失败给重试或保留本地草稿；未知结果先读回，禁止盲目重复写。
4. 第一版目标是 Markdown+资源清单+已核对的图片附件，可导出到浏览器可用目录或用户明确选择的目的地。**任意静默写入指定本地目录不属于普通 Chrome 插件默认能力**；需要另行评估用户授权目录、File System Access 可用性或既有受控 Native Host，不承诺无需授权。
5. 输出保存回执后才提供付费询问：「是否需要团队共享/直接投递到现有企业工作流？」记录真实询价而不是让保存主功能变收费门槛。
6. 先复用现有正式代码，不重新造 SDK、AI 运行器或第二套知识库；真实 Chrome 图片获取、动态网站适配、文件复开仍然 NOT_TESTED。

**预先建议的停止门**（均为 HYPOTHESIS、可调整但实验前先冻结）：10 位符合画像用户的无引导首次任务中至少 7 位成功；有至少 5 位跨两个真实工作周期主动再次使用；至少 2 位描述明确需要的外部交付动作和既有付费替代。若没有自然复用/付费买方，应缩窄到单一导出任务或 STOP，不做付费平台。项目本阶段未采访、未试用、未收费，这些门槛尚未开始验证。

| **Build：开发/增量修改** | 现有公开 SDK、源代码、开发/预览/安装能力，以及维护和权限成本 | 现有工具缺少有价值且可安全开发的一小部分时 | AI 生成代码 ≠ 真实 Chrome 可用 ≠ 正式升级已通过 |
| **Buy：外部产品/服务** | 用户主动输入或核对的业务条件、可核查供应商资料和真实可提供的服务 | 现有/自研不合理或用户明确需要外部能力时 | 模型推荐 ≠ 商家资格、报价、可交付保证或有效商机 |

**中立性：**若免费已有工具或合理自研更适合，应如实显示；不得以供应商付款改变未付费的自然匹配结论。真实商业排序/赞助机制若未来单独开展，须先通过政策、数据用途和利益冲突专项审查。

### 六领域共性、依赖与已有权威归属

| 领域 | 用户侧最小闭环 | 必须区分的结果 | 既有归属或前置证据 |
| --- | --- | --- | --- |
| 内容、图片与知识资产 | 用户选择一条回答/选区 → 保存 → 重新读回/导出 | 文本/链接保存 ≠ 原图文件已持久化 | [Knowledge Inbox](../../../examples/sidebar-tools/knowledge-inbox/tool.config.json)、[Web Markdown Clipper](../../../examples/sidebar-tools/web-markdown-clipper/tool.config.json)、EXP-003 |
| 企业工作流与投递 | 用户确认目标及授权 → 明确执行 → 读取外部真实结果 | 打开网页/发送请求 ≠ 目标记录已创建 | 既有 Controller/Workflow、可信 Host；EXP-001 |
| 工具与服务发现 | 明确需求 → 核对已装工具/可信候选 → 用户比较 | 查询结果 ≠ 产品质量或实际匹配成功 | [官方工具 Catalog](../../../official-tools/catalog.json)、现有只读商品工作流；新的供应商资料待验证 |
| 自愿商机 | 用户选择供应商及分享字段 → 询价 → 供应商确认 | 点击/送达 ≠ 合格商机 ≠ 成交 | 需独立商业服务与真实供应商验证，尚无完成证据 |
| 交易、分佣与激励 | 明确下单 → 商家权威订单/退款/履约 → 可核算权益 | 订单按钮/页面文案 ≠ 付款/履约；点击 ≠ 可计费结果 | 商家、支付及权益系统的合法接口与合同，当前只保留研究 |
| 开发者生态 | 本地源码/已有项目 → 受审预览/安装/升级 → 用户持续使用 | 代码/包存在 ≠ 真实安装和长期维护 | 既有 SDK、Tool/Page/Task 类型及安装器；EXP-004、EXP-008 |

六领域只是**关联索引**，不是再新增六个 OPP 或 EXP。源内容、需求摘要、目标系统、执行回执、供应商、询价和订单只是逻辑关系；没有多个真实消费者及授权证据前，不增设平台级统一商业数据库或通用 Lead/Order SDK。

### 现有能力复用：先证实缺口，再投资

- Prompt Shortcuts 已具备软件/扩展开发需求模板与用户草稿操作；Knowledge Inbox 已具备来源记录、可编辑草稿与 Markdown 交付路径。数据模型对字段、存储容量和修订有严格限制，不得未经迁移审查追加“商业意图”“商机”等字段或另建同义知识库。
- Workflow 已有受限的“搜索 → 打开用户指定商品详情 → 独立核对名称和价格”只读工作流复用代码；**不代表**多供应商自然匹配、支付、下单、分佣已经实现。来源：[segment-replay.js](../../../src/ui/workflow/segment-replay.js)、[direct-execution.js](../../../src/ui/workflow/direct-execution.js)。
- Shared AI Provider/Conversation 是既有可信宿主与业务消费者资源；商用工具不得凭新 consumer 字符串读取其他业务会话或绕开独立授权。React UI、SDK、Host、Scheduler、安装/撤权、包身份均坚持**现有单一事实来源**，普通第三方沙箱不得获 Chrome/Native 特权。
- 2026-10-25 的 GitHub main 源码抽样显示官方 Catalog 12 个登记项目、Prompt Shortcuts 配置 1.1.19、Knowledge Inbox 配置 1.2.9；**仅是该日期的 SOURCE_PRESENT 快照**。执行时必须重新查最新配置与安装证据，不能以旧 README、源文件或构建成功冒充当前 Mac Chrome PASS。

### 隐私、产品边界与外部商业渠道：独立硬门

1. 私人对话、Cookie、已保存知识、浏览数据及其聚合/派生内容不得用于个性化广告或转售线索；不后台扫描全部聊天寻找商机。用户选择用于**已披露产品用途内**的最少内容，仍须核实具体权限和合法处理依据。**单次点击“同意”并不自动解除 Chrome Web Store 的数据用途限制。**参考：[Limited Use](https://developer.chrome.com/docs/webstore/program-policies/limited-use)、[Chrome Web Store User Data](https://developer.chrome.com/docs/webstore/user_data)。
2. 产品自然匹配与商业赞助必须区分；不伪装 AI 平台原生广告、不为广告插入扩大原扩展权限或破坏单一用途。确实需要独立付费推广，应另作产品/渠道与政策审查，不能因为放入一个 Sidebar Tool JSON 就假定合规。参考：[Quality Guidelines](https://developer.chrome.com/docs/webstore/program-policies/quality-guidelines)、[Affiliate Ads](https://developer.chrome.com/docs/webstore/program-policies/affiliate-ads)。
3. 用户主动询价须明确接收方、分享范围、目的和可撤销/后续处理规则；只提供用户核准的必要字段，不自动带 ChatGPT 来源 URL、其他会话、内部目录、密钥或账户信息。供应商内容是不可信数据，不可转成浏览器脚本执行指令。
4. 付款、退款、佣金、权益发放的权威事实来自合法商家/支付/订单系统及合同，不在浏览器 Host 伪造订单真值。不得通过后台联盟 Cookie 替换、诱导安装/评价、绕过目标 AI 平台限制获益。官方 ChatGPT 广告/应用/购物渠道为**独立外部平台**，不能冒充其广告或结账身份。
5. 平台安全、隐私/站点规则、安装身份/撤权和 UNKNOWN 恢复属于独立否决门；不能由任何 95+ 方案自评或商业机会综合分抵消。

### 从方案到证据：一条低成本 Use / Build / Buy 对照任务

**建议的首个只读研究切片（候选，不替代既有 EXP）：**选择一条非敏感 AI 对话中的“开发某个浏览器工具”真实需求；用户明确指定内容 → 使用现有工具保存与整理 → 对照 Use（已安装工具）、Build（现有开发入口）、Buy（仅在用户主动查找时的外部服务）。若用户本来需要协作工单，可用其自有 GitHub Issues **手动**完成一次投递并核对真实链接；这不是“已实现 GitHub API 连接器”，也不强制把 Issue 作为所有行业 MVP。

| 证据级别 | 允许确认的事实 | 不允许自动晋升为 |
| --- | --- | --- |
| L1：本地保存、读回 | 记录/文件在既有权限范围内可核对 | 企业系统已收到 |
| L2：用户核准需求 | 用户审阅了目标、约束、未确定项及实际分享文本 | 已创建外部任务 |
| L3：准备投递 | 内容已复制或目标界面已打开 | 外部写入成功 |
| L4：用户回填外部链接 | 用户报告已提交，关联了真实目标链接 | SDK/API 独立读回已验证 |
| L5：外部权威读回 | 目标 ID、身份、实际内容/状态与请求匹配 | 已付款、已履约或已产生收入 |

对结果未知、授权撤销、目标变化、需求修订冲突、AI 建议中的未证实事实，应停止高风险操作并**先核对后重试**。模型回答、点击成功、发送请求、获得某个 ID 都不能单独证明外部业务完成；Stop 也不撤销已产生的外部副作用。

**实验时比较用户的最佳现有替代方案**（手动流程、已有工具或其他成熟产品），不要只和故意低效的“纯复制”作对照。记录真实任务成功率、完成时间、返工、无引导重复使用、采购角色、实际付款及可归属维护成本；研究员主动记录非敏感结果即可，不为试点建设会话内容遥测。样本量/阈值在实验开始前预注册并注明局限；当前均为 NOT_MEASURED。
