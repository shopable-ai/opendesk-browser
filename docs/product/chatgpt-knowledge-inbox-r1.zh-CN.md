# ChatGPT 知识收件箱：需求排序与 R1 实现

日期：2026-10-11。定位：把值得留下的 AI 回答，变成有来源、可整理、可再用、可导出的个人知识资产。

## 1. 产品判断

建议把入口命名为「保存」，把工具命名为「知识收件箱」。用户经常只是想留住一段内容，当下未必知道最终要放到博客、项目文档还是灵感库。先轻量保存，随后整理和投递，可以覆盖即时使用、稍后处理和长期积累三种情形。

ChatGPT Projects 已允许把某条回答保存为项目来源，因此产品机会不宜建立在「官方不能保存回答」上。差异应放在：精确保存、来源与提问、个人整理流程、开放 Markdown，以及用户自己掌控的文件和外部目的地。[OpenAI 官方说明](https://help.openai.com/en/articles/10169521-projects-in-chatgpt)

Obsidian Web Clipper 的模板、创建/追加笔记，Readwise 的持续导出，分别提供了「保存时结构化」和「保存后进入既有知识库」的同类需求信号；它们能证明这些工作流已有产品支持，不能直接证明本工具的市场规模或按钮点击量。[Obsidian 模板](https://obsidian.md/help/web-clipper/templates) · [Readwise 导出](https://docs.readwise.io/reader/docs/faqs/exporting)

### 主要用户和场景

| 用户 | 频繁发生的动作 | 当前痛点 | 希望得到的结果 |
|---|---|---|---|
| 高频 AI 使用者 | 留下某条答案或一小段 | 整段对话长、日后不好找 | 一键保存，带来源，可搜索 |
| 内容创作者 | 积累选题、提纲、半成品 | 灵感与正式文章混在一起 | 灵感库 → 草稿 → 博客草稿 |
| 产品/研究人员 | 按项目积累结论、比较和决策 | 问答失去上下文，难合并 | 保存提问、标签、批注、主题文稿 |
| 开发者 | 保存代码、命令、解决过程 | 复制破坏格式，找不到当时环境 | 代码保真、问题上下文、可复用片段 |
| 学生/知识工作者 | 存笔记、理解结构、稍后复习 | 收藏很多却很少再用 | 结构导图、搜索、回顾队列 |
| 公司团队 | 把已确认内容放入部门系统 | 格式不统一、投递没回执 | 统一 MD 模板、明确目的地、可核对的写入 |

## 2. 评分方法

以下为产品优先级假设，使用 1–5 分，不是调查统计、实际流量、工程质量或完成度评分。

- **频率 F，30%**：目标用户在日常对话中会多常用到。
- **价值 V，30%**：减少复制整理成本、降低丢失或提高复用的程度。
- **覆盖 C，20%**：可以覆盖多少类用户与工作流，不等于已测流量。
- **差异 D，10%**：相对于简单复制或官方已有保存方式的增量。
- **难度 H，反向 10%**：实现、授权、维护和验收成本；5 为最难。

**总分 = 6F + 6V + 4C + 2D + 2(6−H)，满分 100。** 同分不表示需求等价，实际顺序还要结合依赖关系和当前框架能力。比如可靠投递虽然排序在中段，但一旦开发公司系统连接器，它就是必备基础。

## 4. 按获客、留存与付费价值选择

这里的「流量潜力」指获客假设，尚无关键词量或使用数据支撑。

| 目标 | 优先验证 | 为什么 | 应观察的指标 |
|---|---|---|---|
| 吸引首次安装 | 一键 MD 导出、图片保存、结构导图 | 场景直观，用户容易理解前后差异 | 看到入口→安装→首次成功导出的转化 |
| 形成日常使用 | 收件箱、搜索、标签、草稿、固定文档追加 | 保存后持续找回和加工，价值可累积 | 7/30 日回访、每周复用记录数、待整理清空比例 |
| 提高个人深度价值 | 本地目录、命名模板、主题合并 | 嵌入既有知识工作流 | 保存后的二次使用率、连续使用周数 |
| 验证团队付费价值 | 公司系统、队列回执、博客草稿、管理规则 | 节省多人的重复整理与投递成本 | 投递成功率、失败恢复率、同一团队重复使用 |

不建议第一版摆满一排目的地按钮。主按钮保留「保存」，次按钮为「Markdown」，其他动作进入「更多」。等数据明确用户最常用的目的地，再提供默认目的地和快捷操作。

定期回顾与 AI 分类值得后续做，但第一版就静默分析所有对话或上传所有收藏，会扩大权限、费用与维护成本。可先保留本地可解释的标题/列表结构导图。当前实现不采集遥测，也没有为建议的指标启用后台埋点。

## 5. 本次已经实施的范围

| 功能 | 本次实现 | 具体边界 |
|---|---|---|
| 官方按钮下面增加工具按钮 | 保存 / Markdown / 更多；沿用安装工具机制 | 只适配已授权的 ChatGPT 官方域，受页面 DOM 变化影响 |
| 单条回答保存 | 正文、提问、标题、时间、对话 URL、消息 ID | 保存当前可见回答；可打开来源对话，未自动滚动到原回答 |
| 精确选区 | 完整位于一条回答内的文字选择 | 选区保存不自动携带完整提问，避免额外内容进入摘录 |
| 收件箱 | 待整理、灵感、草稿、归档 | 四种明确状态，可手动调整 |
| 搜索与整理 | 搜索正文/提问/草稿/标签/备注，自定义标题 | 项目可先用标签表示，尚无独立项目层级或标签筛选器 |
| 草稿编辑 | 草稿独立于捕获原文，保存后导出编辑稿 | 未保存编辑有离开提示，尚无崩溃后自动恢复 |
| 去重和并发 | 内容指纹去重；原文变化另存；修订号阻止旧窗口覆盖 | 没有可视版本时间线/差异比较 |
| Markdown | 页面直接下载，收件箱复制和下载 | 超过旧复制接口限额仍可完整下载；链接保留不等于附件离线化 |
| 结构导图 | 本地解析 Markdown 标题/列表，最多 160 节点，可折叠 | 不是语义总结或自由编辑的图形思维导图 |
| 图片入口 | 当前已显示图片的逐张下载 | 最多 12 个入口，允许域有限；无图片打包/二进制 Native 写入 |
| 本地工作区交接 | 已保存 MD → 受信任 Workspace → 选择已授权目录 → 创建并读回 | 整份 MD 含元数据 ≤32 KiB；交接不是磁盘写入，也不证明云盘同步完成 |
| JSON 备份 | 下载全部原文、草稿和元数据 | 尚无导入恢复 UI |
| 权限与退出保护 | 独立网站授权、撤权移除按钮、卸载清除数据与未载入交接 | 强制撤权/包升级仍可终止旧沙箱；未保存内容不是持久记录 |

容量为 200 条 / 4 MiB；单条正文和编辑稿各不超过 150,000 UTF-8 bytes。大内容不会静默截断或挤掉旧收藏；超限时用户可以先下载、备份和整理。提问只保留前 2,000 字并明确标记节选。

### 本地目录与系统同步的三种不同能力

1. **浏览器下载**：用户选择保存位置或使用 Chrome 下载设置。Chrome Downloads API 不提供任意绝对路径写入权。[Chrome Downloads API](https://developer.chrome.com/docs/extensions/reference/api/downloads)
2. **Native 工作区文件**：沿用 OpenDesk 已授权目录能力，对明确目录内的文件执行写入并核对。扩展与 Native 程序之间需要规定的通信通道，不能从沙箱里任意调用系统文件 API。[Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)
3. **第三方 API 投递**：需要明确目的地、连接方式、权限和回执。不同公司的系统不可用一个未经配置的「同步」按钮完成。

此次实现了第 1 层与第 2 层的 MD 交接。第 3 层没有接入真实账户或公司系统；图片自动进入指定目录、定时同步、双向同步、固定文件追加均未完成。

## 6. 下一阶段顺序

### R2：个人长期积累

优先实现固定 MD 追加、命名模板、常用目的地、备份导入、多条主题合并、图片附件包。固定文件追加需要冲突检测、明确追加位置和幂等标识，不能用「下载同名文件」代替追加。附件保存需要将临时地址变成真实文件，并把 Markdown 链接改为相对路径。

### R3：外部目的地

依据实际使用对象选择一个 API 作为首个连接器，例如用户实际博客的草稿接口或公司正在使用的知识库。统一的动作应包含：所选记录、输出格式、目的地、文档身份、写入模式、完成回执。凭证只存在受信任连接层，不能写进可分享工具 JSON。

博客默认创建草稿，预览后再公开发布。WordPress 的文章 API 明确区分 `draft` 与 `publish`，这可以落实成两个不同动作，而不是把保存与发布混为一谈。[WordPress Posts API](https://developer.wordpress.org/rest-api/reference/posts/)

企业目的地只有明确 API/认证后才能定实施范围。优先确认「写到哪个已存在文件夹/草稿区」「新建还是追加」「谁能看到」「成功如何核验」；不要求用户现在就填写这些信息来阻塞本次可独立完成的工作。

### R4：提升整理效率

有稳定积累后，再做可选 AI 摘要、分类建议、回顾提醒和跨模型站点适配。建议结果先呈现给用户核对，仍保留原文、来源和编辑历史。

## 8. 手动添加、删除和官方工具安装入口（v1.2.0）

> 本节为知识收件箱 v1.2.0 的新增操作说明，上一节 R1 实施范围保留历史语义。完整验证状态以独立 workstream 和实际构建 SHA 为准。

### 如何把知识收件箱添加到浏览器扩展

- 打开 OpenDesk Browser Side Panel 的「工具」，在「发现工具」中找到官方「知识收件箱」，审核所需能力并安装。它是官方 **optional** 工具，不与用户自己手动写入的记录混为一谈。
- 在「我的工具」打开「知识收件箱」，不需要先访问 ChatGPT 就能新建本地记录。
- 若要在 ChatGPT 对话中显示「保存」操作，必须另外对实际 ChatGPT 页面授予网站访问权限；未授权仍可使用手动新建、阅读和删除。
- 卸载整个小工具：从 OpenDesk Browser 的工具详情执行卸载。**卸载工具不是删除单条笔记**；卸载会按现有安装清理合同处理该工具的数据，先下载 JSON 备份。

### 如何手动新建与删除内容

1. 在收件箱顶部点击「＋ 新建」；如果还没有记录，也可以直接点击空状态的「新建第一条知识」。
2. 输入标题与 Markdown 正文，按需选择「待整理／灵感／草稿／归档」、标签和备注，点击「保存知识」。标题和正文必填。支持 Cmd/Ctrl+S 快速保存；返回或 Esc 会对未保存内容二次确认。
3. 新建条目与从 ChatGPT 抓取的回答都显示在同一列表，使用同一套搜索、分类、编辑、导出与配额。手动记录标为「手动创建」，不生成虚构的 ChatGPT 来源对话；只有捕获的回答能打开来源。
4. 删除单条记录：点击列表里的记录，进入详情页，直接点击工具栏「删除」并确认。操作不可撤销；大量清理前先用列表的「管理 → 下载 JSON 备份」备份。
5. 删除是逐条操作，不增加危险的「一键清空」或未设计恢复语义的批量删除。

数据继续由扩展可信服务在 `chrome.storage.local` 中保存。单条正文不超过 150,000 UTF-8 字节，最多 200 条且总数据不超过 4 MiB；读写经已安装工具身份、修订号冲突保护和可验证的存储提交。页面沙箱不能直接调用浏览器存储。来源 URL 对自动捕获要求合法 ChatGPT 域名；手动记录没有来源 URL。现有 JSON 备份包括手动记录，但 **JSON 备份下载不等于数据恢复/云同步**。

## 9. v1.2.1 详情页「正文优先」布局

当前主线只优化原有 `knowledge-inbox` 官方工具的界面与交互，不改变数据格式、权限、沙箱 RPC、安装机制或后端。

- **阅读模式**：保持名称、分类、来源和主要操作，但压缩头部与工具栏空白。阅读正文仍使用不会执行 HTML 或加载远程图片的既有渲染器。
- **编辑模式**：点击「编辑」后，顶部保留返回链接与小号「编辑知识」标识，隐藏重复的阅读标题、日期、分类标签、复制、删除等阅读工具栏。第一屏只呈现紧凑的**标题输入 → Markdown 正文**。
- **折叠的低频信息**：原本横在正文前面的分类、标签和备注移动到正文后面的「分类、标签与备注」原生 `details`，默认收起；摘要保留当前分类及已填标签、备注提示。展开、收起都不丢字段，也不会触发数据写入。
- **保存 / 取消**：编辑区底部保留可见的「取消」「保存修改」和未保存状态，支持 Cmd/Ctrl+S；取消和返回遇到未保存编辑必须二次确认。确定放弃后，再次进入编辑时重新载入最后的持久化值。
- **新建模式**：相同的正文优先顺序，标题与内容必填，字节限制反馈保留在正文下；分类、标签、备注属于可选折叠信息。顶部返回与底部取消都执行同一离开保护。
- **信息不丢失**：历史 `markdown` 原文始终不可变；编辑稿、分类、标签与备注照旧独立持久化。阅读状态仍可查询原始问答，手动笔记无虚构 ChatGPT 来源。

验收重点是 360/400/600/1000 CSS 宽度、明暗色、真实焦点和原生输入。受控 Chrome 测试不仅检查保存，还检查编辑模式先看到正文、默认折叠次级信息、确认丢弃后不复活旧输入、保存恢复阅读模式。**以上为设计合同，不因写入代码自动等价于原生测试通过。** 具体候选、测试结果及构建预算阻塞见 `docs/framework/workstreams/knowledge-inbox-r245-content-first-editor-20261011.md`。

## 10. v1.2.2：输入校验与阅读工具栏精简

在既有「正文优先」布局上继续精简，而不是增加一套编辑器。

- **阅读态**优先保留「复制 Markdown、编辑、删除、更多」；使用频率相对低的「结构导图」已移入「更多」中。查看导图仍可返回正文，原始内容不变。
- **编辑态**的保存按钮会根据当前标题、正文和标签是否合法实时更新。正文不能为空或超过 150,000 UTF-8 字节；标签最多 12 个，每个不超过 30 字。输入有问题时在正文之后直接提示，不会把错误藏在弹窗或后台。
- 新建记录沿用相同规则。首次打开空白表单不堆满必填警告，用户离开字段或填写内容后才按需提示。
- 编辑正文正常长度不显示冗余字节数；超过 85% 容量上限时显示字节计数提醒，超过上限则禁止保存直到修正。
- 输入非法的分类/标签相关设置会在折叠区边框与摘要位置呈现提醒；原本分类、标签与备注仍收在正文之后，不重新占据首屏。

改进只涉及已有 UI 和校验提示，安全侧的知识 Service 校验、修订号、网站权限、去重与原始数据保留均未修改。完整测试与独立专家评分见 `docs/framework/workstreams/knowledge-inbox-r246-quality-20261011.md`；没有当前版本的真实 Chrome 证据就不能宣称 95 分验收。
