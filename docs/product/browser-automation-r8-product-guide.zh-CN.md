# OpenDesk Browser R8：先看用户能做什么，再决定开发什么

> **产品取舍更新：2026-10-09。** 本页是给项目负责人、Codex 和新加入开发者阅读的**一页产品导航**，不是第二份功能矩阵、第二份工程排期，也不是功能已经完成的证明。最新实现与验证状态始终以具体源码、PR 和同候选测试回执为准。

## 1. 一句话定义产品

**OpenDesk Browser 是一个让人或 AI 使用 JavaScript 开发、运行与管理浏览器功能的工作台，避免每做一个小工具都要开发、打包和发布独立 Chrome 插件。**

它保留两种彼此不同、但共用可信宿主的运行方式：**网页增强脚本（Page USER_SCRIPT）**用于向页面加按钮、菜单、样式和交互；**浏览器自动化任务（Controller / RunHost / ChromePage）**用于跨页面操作、表单填写、数据读取及可记录的任务执行。源码是单文件还是多文件，不决定权限，也不意味着这两种执行环境可以合并。

正常使用不应要求用户理解 Candidate、ManifestHash、Broker、CAS、E07/E10 这些术语；它们是保证“能正常安装、不会被偷偷替换、出错能恢复”的内部手段。

## 3. 近期仅围绕两条用户可见的完整流程交付

### 第一优先：AI / Codex 直接开发并运行本地 JavaScript

**用户故事：**“我让 Codex 修改本地项目里的 JS，马上在现有 Chrome 网页上运行，看到结果；修错后再次运行，不再反复生成 JSON、上传文件或手动重新导入。”

期望流程：**授权本地目录 → 编辑当前源码 → MCP 调用既有 Native / Controller / RunHost → 真实网页执行 → 返回运行结果或具体错误 → 修改后按新源码重跑**。

这里的“直接运行”强调开发者不需要额外的手工打包/上传操作，**不等于绕过必需的内部源码校验、ESM 编译或安全审核**。多文件、npm、HTTPS ESM 是该流程的输入能力，不应成为三套互不兼容的开发入口。

**实施与验收边界：**
- 复用既有 RunHost、Authority、Controller、Storage 和文档身份；不创建第二个浏览器运行内核或另一套特权 MCP 服务。
- 本地目录只在明确授权的边界内读取；处理路径穿越、符号链接、依赖锁、源码哈希、旧版本缓存、超时、失联与权限撤销；不得将外部输入当成可执行的可信构建参数。
- `import` 可面向本地相对模块、受控 npm 与 HTTPS 依赖逐步扩展；远程 JS 必须在受控构建时获取和固定内容，最终扩展执行仍遵守 MV3 的本地打包/CSP 约束。**不提供扩展特权 Service Worker 中的任意 HTTPS 动态代码执行**。
- Codex 修改一个源文件后，在真实 Chrome 运行必须使用新内容；执行结果需关联 sourceHash、目标网页和真实 Run/Result。Node 组件 PASS 不能替代这一闭环。
- Sidebar 原有三个一级页签、单文件即时运行与 Controller Task 操作保持；无必要不新增按钮、下拉框和上传表单。

**2026-10-09 集成状态快照（执行前仍须核对最新 main）**：[PR #37 本地目录 / MCP](https://github.com/shopable-ai/opendesk-browser/pull/37)、[PR #38 npm 依赖迁移](https://github.com/shopable-ai/opendesk-browser/pull/38) 与 [PR #39 HTTPS ESM 安全构建](https://github.com/shopable-ai/opendesk-browser/pull/39) 均已合并。用户可按 [统一 JavaScript 操作指南](program-development-dual-format-and-sidebar.zh-CN.md) 选择普通脚本、MCP 本地相对 ESM、npm/HTTPS 显式锁定构建三条路径。**关键未完成项**：本地开发 Resolver 暂不接受 npm/HTTPS 原始 import；将其接入已有可信构建器、保留原 RunHost/权限边界并做同候选真实 Mac Chrome 验收才是后续工程目标。涉及 E02、E03、E05、E33、E34、E40。

### 第二优先：网页增强脚本可以安装，以后自动生效

**用户故事：**“我为一个网站写了按钮或工具栏，试运行后保存、确认安装，以后重新打开匹配的网站它自动出现；我还能停用、更新或删除。”

期望流程：**开发 JS → 当前网页预览 → 保存不可变版本 → Page 类型专属验证 → 明确确认安装与授权 → Chrome 按网址注册 → 后续文档自动运行 → 启用/停用/更新/恢复**。

已存在 Page 草稿、固定依赖机制、注册描述编译和 E07.1 不可变 Page Candidate；**Candidate 仅表示候选已保存，绝不等于已安装或已验证运行成功**。正式 Page Verification、Installed/Enabled 状态、`chrome.userScripts.register/getScripts/unregister` 受信对账，以及停用、撤权、更新后恢复仍需独立闭合。涉及 E07–E15 与 E40。

**必须按用户能观察到的结果验收：**匹配页面重新打开自动生效一次、不匹配页面零执行、停用后下一文档零执行、浏览器/扩展重启后准确恢复或明确失败；版本、来源和权限变更有可见批准，坏资源/撤权时拒绝执行。浏览器原生注册 API 返回成功，不等于目标网页的 DOM 效果正确。停用不会自动撤销此前已执行过的 DOM 修改。

### 始终保留：现有 Controller 自动化任务

“我的任务”中的 Controller 手动运行、停止、结果记录、ChromePage/Locator/SDK 等属于现有核心，持续维护和必要回归，但**不因为新优先级就推倒重写**。用户能够不用 AI 独立执行固定任务，是两条主线都要保护的基础体验。

## 4. 哪些先不开发？

| 近期暂缓项 | 为什么现在不做 |
| --- | --- |
| 完整油猴/ScriptCat 的 GM_* 兼容全集 | 没有正式页面脚本安装闭环时，扩展接口数量并不带来完整用户价值；特权身份和权限风险高 |
| 定时/后台长驻任务、Cron、多浏览器移植 | 浏览器生命周期、触发重入、恢复和跨端差异需在已有运行身份成熟后解决 |
| 在线脚本市场、账号云同步、订阅分发 | 需要独立信任、许可和隐私体系；先让本地工具可管理 |
| 复杂 UI 框架选择器、第二套编辑器、重复的 @require 图形化界面 | 现有 JS 编辑器、多文件 ESM、按项目选用 CSS/框架足够承载第一批真实需求 |
| 新的代理式执行内核、第二套数据库、另建通用 MCP 云服务 | 会与现有 RunHost/Authority/Storage 重叠，增加故障面 |

暂缓不等于删除 188 账本中的能力；只有出现明确用户需求、合法权限模型、现有结构可复用性和必要真实验收时，才按稳定 ID 重新排期。

## 5. 下一批实施顺序（交付优先级，不替换原 E01–E40 编号）

1. **以已合并源码为基线。** PR #37/#38/#39 已进 main，先复用本地 Resolver、受控 npm/HTTPS 构建器和原权限入口；优先修复真实使用缺口，避免重复分支/平行 Runtime。
2. **完成本地开发闭环。** 只补“本地改文件 → 真 Chrome 执行 → 结果 → 改后重跑”缺口；安全和失败用例不可删减，相关成功证据齐全再合 main。
3. **完成网页脚本安装闭环。** 复用 Page Candidate 和原有 User Scripts / Host / Storage，按类型建立验证、安装状态、原生注册及恢复；当前网页一次性 Preview 不可冒充自动安装。
4. **收敛真实验收。** 对受影响输入做定向回归；真实 Chrome、同产物构建/ZIP、原有 F3 合同按原始证据独立关闭；不因功能说明写完就标产品完成。

**为何本次交付顺序与早期“P0 先安装 Page”不同？** 原 R8 roadmap 的 P0–P4 是长期能力包。2026-10-09 根据 Codex 本地开发摩擦和并行 PR 已投入情况，决定先收敛最接近闭环的本地开发体验，再完成 Page P0 安装，不改变 P0 的产品重要性或安全要求。两个工程方向可在隔离工作区并行，但 `main` 集成和真实 Chrome 独占资源须串行。

## 6. 用 7 个动作判断有没有真正完成

**AI / Codex 本地开发（4 项）**：① 修改已授权本地 JS；② 通过 MCP 在真实 Chrome 的既有运行链执行；③ 得到真实结果或可定位错误；④ 修改文件后无需上传、执行的是新版本。

**网页脚本自动生效（3 项）**：⑤ 页面预览后可以完成正式安装；⑥ 重新打开匹配站点后生效、重启后状态准确；⑦ 停用后新文档不再运行（旧 DOM 效果不承诺回滚）。

每项分别记“尚未实现 / 组件已测 / 构建已核对 / 真实 Chrome 通过 / 仍有阻断”，并引用 commit、构建包 hash、Chrome 版本、目标页面、原始回执。测试目标页面统一使用 `examples/tasks/demo-form.html`，已有真实 Chrome 证据按 [测试复用指南](../framework/testing-guide.md) 检查影响后复用；原 F3/ZIP 不以这 7 项代替。

## 7. 遇到英文术语时的翻译

| 工程词 | 请直接理解为 |
| --- | --- |
| Candidate | 保存下来等待审核的固定脚本版本，不能表示已安装 |
| Verification / Available | 针对相应类型证明可以安全发布的检查和准入状态 |
| Installed / Enabled | 用户已安装 / 已开启，仍需检查 Chrome 真实状态 |
| User Scripts registration / reconciliation | 让 Chrome 记录哪些网址自动运行，并在重启/升级时核对恢复 |
| Controller / RunHost / Locator | 执行自动化任务 / 承载任务 / 定位网页元素 |
| ESM / import / dependency lock | 多文件模块引用 / 引入其他模块 / 固定实际依赖内容 |
| MCP / Native Host | Codex 调用工具的标准接口 / 本地程序与扩展之间的可信通信入口 |
| sourceHash / CAS / Authority | 确认运行的是哪份源码 / 防止旧版本覆盖 / 校验实际操作权限 |
| Component vs Chrome Native | 代码逻辑的定向测试 / 真浏览器安装和运行效果验证 |

**新增需求准入原则：**先写“用户从哪里点击或怎样调用、得到什么实际结果、失败如何呈现”，再查 188 总目录是否已有 ID，找现有代码消费者和独立验收，最后才确定要不要新增页面、依赖、权限或工程任务。用户故事不清晰的功能，暂不实施。
