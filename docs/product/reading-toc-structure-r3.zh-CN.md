# OpenDesk Browser 阅读目录 R3：紧凑原型、H1 与跨片段内容边界

> 状态：**设计冻结 / 独立 HTML 演示已验证；非真实网站运行验收**。2026-10-10。
> 原型：`../framework/prototypes/reading-toc-r3/compact-toc.html`。
> 下一轮正式实现：`../framework/prompts/goal-reading-toc-r4-in-page-main.zh-CN.md`（已升级为 R4.1，Side Panel 工具可安装是 P0）。

## 1. 产品范围和使用场景

目录（TOC）是**显示在原网页内的轻量阅读能力**，但其**安装、启用、站点范围和卸载**属于 OpenDesk Browser 的 **Side Panel「工具」Tab**。用户可从本地 `.opendesk-tool.json` 导入或通过扩展内置官方便捷安装入口取得 TOC 工具；不另外安装第二个 Chrome 扩展。优先适配单篇文档/文章、知乎等多回答文章页、ChatGPT 类多轮 AI 会话。Sidebar 的摘录、Markdown、笔记等可独立使用，共用来源身份与正文索引，但不是本原型上的菜单项。

- **网页内 TOC**：一个小卡片，只有 `CONTENTS`、三个图标视图和目录项；没有搜索、保存、解释文字或上一章/下一章底栏。视觉参考用户给出的 `.docs-toc-aside` 卡片，延续较小行间距、最多两行标题、蓝色定位线。
- **一级/当前章节/完整目录**：控制当前选定内容范围的展开详细程度，**不**自动改变阅读范围、切换回答或滚动正文。
- **目录点击**：定位到准确原文所在滚动容器，允许手动打断；正文滚动只更新目录高亮，不反向拉动正文。
- **超长目录**：卡片根据内容增高，达到限定高度后在目录内部滚动，不出现虚假的固定大面积空白。

### 1.1 产品入口与工具生命周期（R4.1 修订，优先级高于旧 R4）

- **P0 工具入口**：Side Panel「工具」→ 本地导入合法包或官方推荐「阅读目录」→ 核对权限与站点 → 安装启用 → 在当前已允许网页显示紧凑卡片。已安装工具支持重新打开管理、停用、站点范围调整、升级及卸载。
- **网页展示**：目录出现在正文旁边，不要求 Side Panel 持续打开。关闭 Side Panel 或切换工具 UI 不能自动停用已启用的网页 TOC；用户主动停用/卸载则撤销相应网页 UI 与服务。
- **宿主能力**：当前工具包 `opendesk.sidebar-tool.v1` 的 `currentPage.read` **只返回标题和 URL**，sandbox UI 不能读网页 DOM。正式实现必须由扩展自身受信代码提供限定的 TOC 能力，由安装记录、工具授权和站点范围统一管理，不得将导入包的任意 JS 注入网页。
- **安装渠道一体化**：本地文件导入与官方一键安装应共享同一包校验、权限审核、安装数据和更新/卸载流程。未来工具市场只是第三个获取/审核相同工具包的入口，不是另一套 Chrome 扩展体系；本轮不实现远程市场服务器或静默安装。
- **现有兼容性**：不得为新增 TOC 能力破坏旧版工具包，不能复用 sandbox iframe 长驻来伪装“网页自动启动”；需要对安装/启停/撤权/关闭面板/跨标签页/不同用户脚本权限进行测试。
- **权威实现任务书**：[`goal-reading-toc-r4-in-page-main.zh-CN.md`](../framework/prompts/goal-reading-toc-r4-in-page-main.zh-CN.md)，2026-10-10 已修订为 R4.1，把工具形态升级为 P0。R3 HTML 仍只负责视觉与交互基线，不是完整安装 UX 原型。

## 2. 区分页面类型和标题层级（本轮关键修复）

**核心规则：既不能普遍隐藏 H1，也不能盲目把 H1 当作整段会话的唯一根。**

### 2.1 单篇文章

- 页面题名有时是 `h1`（如文章头图旁的标题），可**仅在适配器可靠识别它是正文外的文档标题，或者将其明确标为 documentTitle 时**从目录项中排除；仍应保留为阅读对象的名称。
- 文章正文内部的 `h1` 不能因为页面已有 `h1` 就自动删除。即使 H1 出现在文章中间，也应作为新的顶层章节，后续 H2 为其子层级。
- 若正文从 H2、H3 开始，**以当前内容范围内有效出现的标题构建顶层**，不要求 H1 必须存在；使用标题栈按层级弹出，允许缺级和重复。
- 对网页不知道哪个 H1 是题名时，宁可保留可见 H1 或明确提示结构不确定，禁止“每个页面仅保留一个 H1”一类假设。

### 2.2 AI 对话（多 H1）

- **会话不是文章**。同一 AI 回答可以有多个 H1，每个 H1 都是该逻辑回答中的合法章节；不同 AI 回答也都可能包含 H1。
- 建立结构：`页面文档 / 会话 → 问答轮次（如有）→ AI 回答及版本 → 内容片段 → heading(H1…H6)`。
- 标题父子关系在**回答边界**重置，不能把后一条回答的 H2 挂到上一条回答的 H1；单个回答多个渲染片段时，父子关系应**跨片段继续**，不能在每一框重新起一棵无关目录。
- 对话中的回答首个 H1 通常也是用户需要定位的真实章节，不按文章“排除页面标题”规则隐去。
- “一级目录”是当前内容范围里的顶层导航，不等于 `document.querySelectorAll('h1')`；当回答没有 H1 时，H2 等级亦可顶层显示。
- 目录重复标签通过**来源/回答/版本/章节私有身份与原 DOM 节点映射**区分，不按标题文字或 DOM 全局 ID 唯一性判定。

### 2.3 同一 AI 回答可能分成多个框

- 浏览器中的不同 DOM 容器≠不同逻辑回答；同一回答可能分为正文、Markdown、代码、表格、工具结果等多个可见块。只有明确归属证据才能合并；不得仅用视觉相邻或相同 CSS 样式猜测。
- 示例 `answer-1` 包含三个 `data-part` 片段并含两个 H1，`answer-2` 是同一聊天页面的另一条独立回答。原型中的 `data-source-group` 是**专门制作的模拟归属标记**，并非 ChatGPT/知乎通用实际字段。
- 每条回答独立的 Heading 栈；每个同源片段共享该栈。独立回答和不同版本不串联。未能确认归属时保留独立内容片段，不误合并。
- 生成中 Markdown 围栏/代码块、blockquote、链接控件、隐藏节点、页面按钮文字不能被当作正文标题。Markdown 解析异常可能改变 DOM 呈现，但不应简单推断“分框=Markdown 错误”。

## 3. 标题和定位数据合同建议

适配器输出**可信边界**，通用索引算法处理各类页面；真实适配器具体选择器须通过目标站点实测验证。

```ts
// 设计合同（不是已实现 API）
type ContentRange = {
  documentKey: string; // URL/内容主体等复合身份，不等同于标签标题
  rangeType: 'article' | 'answer' | 'conversation' | 'multi-answer';
  status: 'complete' | 'partial' | 'ambiguous';
  groups: Array<{
    groupKey: string; // 文档/回答/版本/内容归属的复合身份
    kind: 'article' | 'answer' | 'unknown';
    versionKey?: string;
    segments: Array<{ segmentKey: string; root: Element; order: number }>;
    documentTitle?: Element; // 只有可验证的文章标题才能这样标注
  }>;
};
type HeadingAnchor = {
  headingKey: string; // 来源 + group + segment/heading + 版本的私有稳定标识
  element: Element;  // 仅保存在页面上下文中的短期节点引用
  tagRank: 1 | 2 | 3 | 4 | 5 | 6;
  label: string;
  groupKey: string;
  depth: number; // 基于当前组的标题栈，首个可见层级 depth 0
};
```

- 正文索引跳过由适配器明确标记的页面标题、代码、隐藏/装饰节点和 TOC 自身，不覆盖网页已有 ID、锚点、`history` 或 `location.hash`，不重排正文 DOM。
- 页面标题的排除条件必须是**可靠归属**，而不是全站 `h1:first-child`、全部 H1 或“除第一个 H1 外保留其他”。
- 有 HTML `id` 重复或缺失时，TOC 内用私有生成身份和元素引用精准跳转；避免 `document.getElementById()` 找错，也不为制造 ID 改写原网页。
- 动态页面需限制 MutationObserver 观察范围、做节流/增量失效，不在每次 token 流式更新时全页重新扫描；虚拟化和卸载要重核对来源身份。
- 若内容版本、来源、节点丢失或目标不可见，返回明确失败/部分定位状态，不尝试错误同名标题、不伪报成功；滚动完成以目标进入正确滚动视口为准。
- 正文滚动跟随必须只更新高亮。点击跳转的滚动可取消，支持固定导航/内层滚动容器与 reduced-motion。

## 4. HTML 原型边界与回归

`compact-toc.html` 是**无需 Chrome 插件即可查看的演示**，提供“文章 / 对话”两个原型场景切换（不是正式 TOC 卡片的一部分）。

原型模拟：

1. 文章题名 H1 经可靠 `data-toc-document-title` 排除；文章内部额外 H1 保留；H1 后的 H2 为子节。
2. 对话第一条回答跨三个 `data-part` 片段；在片段 1、2 分别出现 H1，在片段 3 出现之前章节的后续内容。
3. 对话第二条回答有自己的 H1/H2；各回答的标题栈独立。
4. 多个“小结”同名标题和重复 DOM ID，点击仅定位指定元素；不改写原文元素 ID 或站点 URL。
5. 目录仅三个图标视图，紧凑排版，行高随最多两行标题变化；无底部翻页区。
6. 正文可主动点击精确滚动；手动滚动目录高亮跟随；文章滚动根与对话内层滚动根分别测试。

本轮在独立 Chromium/Playwright 页面用 `set_content` 测试了 **36 项交互与布局断言**（桌面与移动端）。这属于**原型证据**，不能替代真实 ChatGPT、知乎站点适配、MV3 扩展安装或宿主安全验证。

## 5. 正式插件实施边界

- 复用 `src/entrypoints`、WXT / Chrome MV3 真实入口及既有“工具”体系（核查当前代码后决定入口位置），不新建任务执行内核、不过度依赖 Sidebar，也不将导入的沙箱工具直接当作网页 DOM 读写主体。
- 优先交付**网页内原生 TOC**，文章、知乎（如可验证）、AI 对话适配器分层；对未识别页面保守退化，不因 CSS 失效造成全页污染。
- 通用文章、知乎多回答、ChatGPT 多轮会话的**页面结构适配和真实 DOM 身份**各自独立验证。不要直接把本原型的模拟 `data-source-group` 选择器写入生产适配器。
- 不额外申请原本不需要的 `debugger` / Native / 全站新权限；遵守当前 manifest 权限/授权生命周期，按当前源码和浏览器实际授权状态处理。
- 本轮仅交付目录识别、渲染与跳转，Markdown 摘录、知识库、AI 整理可后续接入共享索引，但不成为目录发布阻塞项；相关风险另行记录。
- 修改前检查 `main` HEAD、远端更新和未提交代码，尊重并行任务；任何文件冲突须保留双方工作。生产构建、环境测试、真实 Chrome E2E 分级报告，不能把原型通过当作插件通过。
