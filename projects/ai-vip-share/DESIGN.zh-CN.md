### 1.2 R4 产品定位

从“代理一键开关”转为 **「AI VIP Share 会员权益、兑换与使用中心」**。

会员权益/账号/剩余时长/兑换码/更多商品是首要信息；具体代理协议、PAC 和域名清单为低优先级能力详情。用户在目标 AI 网站使用服务时，工具主要承担会员管理，而非每天手动选代理节点。

| A 已有会员/账号 | 打开工具 → 登录/绑定产品账号 → 查看会员与到期时间 | 已有权益，展示剩余时间 | 会员有效 ≠ Chrome 代理已连接；未验证不得显示伪状态 |
| B 手动兑换码 | 打开工具 → 输入兑换码 → 预检内容/账号 → 显式确认兑换 → 服务器返回权益 | 展示对应时长和新的到期日期 | 后端幂等、防重放、兑换码只传受信任 HTTPS，不得伪造成功 |
| C 专属激活链接 | 受信任购买/兑换页点开特殊链接 → 检测宿主与工具安装状态 → 可选安装确认 → 展示码/权益摘要 → 用户确认兑换 | 与 B 的同一兑换结果 | 链接不自动给浏览器扩展安装权限，也不自动执行具有副作用的兑换 |

辅助路径：点击「更多商品」浏览合法上架的 1 天、1 个月、3 个月、1 年等 SKU；付款在经验证的商户页面完成。购买回跳只带订单/兑换意图，不以 URL 声称付款成功。

## 3. 界面结构：一张会员主卡 + 兑换卡 + 商品入口

建议以 **320–390px Chrome Side Panel** 为约束，默认只展示下列三层：

1. **主卡「AI 会员」**：脱敏产品账号或“登录/绑定”，商品名称/版本、会员状态。主卡最醒目的是剩余时长及到期日期；最近兑换和记录入口在卡片底栏。主卡在访客、未开通、权益过期、无法核验时使用清楚的空/错误状态，不填假时长。
2. **「兑换激活」**：一个兑换码/激活码输入框 + 一个“立即兑换”按钮；不展示固定套餐时长列表。专属链接进入时新增紧凑的“已识别链接/待确认”提示；未安装工具时仅在这张卡里展开一步“确认添加工具并继续”，不新建高耸的独立安装页面。
3. **「更多商品」**：顶部次级快捷入口和正文“购买更多会员时长”入口打开同一个目录弹层；列示时长但不编造价格。实际购买链接仅在正式商品数据合法可用后开放。

底部新增常驻 **AI 网站访问控制卡**，只提供直接启用/停用本工具代理的单一主按钮；适用站点与技术说明仍可折叠。冲突和停止未确认在控制卡内直接呈现，会员仍是主信息。行为以第 10 节 R4.1 为准。

主界面不同时展示多张冗余网络状态卡，避免挤高侧边栏；产品和时间等高价值信息在首屏。所有提示/按钮使用浏览器统一 Design System tokens、语义 CSS，不在生产界面创建第二套框架。

## 4. 商品、账号、兑换码、时长的领域模型

四个概念**必须分离**，不能仅用一个 `enabled` 布尔值表示：

| 模型 | 示例字段 | 真正可信的来源 |
| --- | --- | --- |
| `memberAccount` | `accountId`、`displayNameMasked`、`sessionState` | 已审核的产品账号服务 |
| `productSku` | `skuId`、`title`、`kind`、`duration:{unit,value}`、`entitlementType`、`priceCurrency`、`priceAmount`、`availability` | 审核后的商品目录/商户服务 |
| `entitlement` | `entitlementId`、`accountId`、`skuId`、`startsAt`、`expiresAt`、`status`、`version` | 授权服务（服务端时间为准） |
| `redemption` | `redemptionId`、`voucherPreviewMasked`、`source`、`redeemedAt`、`grantedEntitlements`、可选的 `previousExpiresAt`/`newExpiresAt`、`idempotencyKey` | 兑换服务的原子账本与核验回执 |
| `installState` | `hostInstalled`、`toolInstalled`、`toolId`、`permissionState`、`epoch` | 浏览器宿主的可信安装管理器 |
| `accessState` | `authorized`、`proxyControl`、`runtimeStatus`、`lastVerifiedAt` | 公共 SDK + Chrome 原生状态回读 |

**会员账号 ≠ 设备码**：设备码只能用于设备授权或限制，不取代用户的商业会员账号；允许未登录访客先查看商品和输入兑换码，但兑换落账需要绑定用户权益归属。不得在工具页明文持久保存原始兑换码、登录口令或第三方 AI 会话。

### 4.1 权益类型与时长规则（时间类商品适用）

兑换卡只负责兑换/激活入口，**不显示固定时长档位**；兑换码可对应不同 SKU、活动、使用配额或时间权益。商品详情与成功回执才展示服务端确认的权益内容；不从兑换码前缀或 UI 文案推断时长。以下时长计算仅适用于时间类 SKU。

- 1 天 = 24 小时，或产品条款定义的自然日；必须选择并一致公开，不能混用。
- 1 个月/3 个月/1 年建议按服务端固定时区的 **日历月/年规则** 计算；需定义 1 月 31 日遇到 2 月、闰日、夏令时的行为。**不能一律把“一个月”写死 30 天**。
- 如果允许续时叠加，基础时间采用 `max(serverNow, currentExpiresAt)`；新 `expiresAt` 必须由后端事务确定、返回客户端。若不同权益类型不可叠加，按商品合同单独展示，不能混加。
- 兑换码验证与消费应为 **原子事务**，同一券码和 `idempotencyKey` 反复请求不重复加时；并发兑换、设备切换、断网重试需要返回可解释的唯一记录。
- 客户端可在内存中显示倒计时，但最终有效期以服务端核验为准，网络离线时只说明“上次核验时间/状态待确认”，不能无限延长。
- 兑换记录展示 SKU、来源、兑换时间、新增权益、到期变更及脱敏兑换码；不展示或上传完整敏感令牌到日志。


## 5. 专属链接：自动准备、必要时一次确认、原事务恢复（现行方案，2026-11-10）

**推荐且唯一实施路线：可信来源识别 → 无核销预检 → 根据已有安装/授权/领取状态分流 → 必要时一次业务确认 → 原事务结果与后续授权步骤。** 不使用三秒自动提交倒计时；可信来源和安装许可均不是权益核销许可。此节优先于原 R4 的固定双产品确认和默认 ticket 设想；历史证据不删除。当前正式安装包仍为 1.4.32，主线存在准备中的 1.4.33 源码，未完成本候选安装/实机验证，不能把源码等同正式包。

### 5.1 方案对比和选择

| 方案 | 首次/重复/取消/失败处理及用户收益 | 打开链接后额外业务点击预算 | 人为等待、页面跳转 | 错领风险、成本、关键依赖 |
| --- | --- | --- | --- | --- |
| A **自动预检 + 状态续接 + 必要时一确认（采用）** | 首次显示主体和权益后确认；已装不重装，已授权续接，已领回读，取消保留手动入口，失败查原事务 | 已装首次 1；相符已授权/已领 0；未装另有安装审阅；取消后主动预检可能 +1 | **0 秒**；原安装页接原激活卡，不抢别的标签 | 必须有可信来源、Provider 原子核销与真实恢复；较低误领风险，复用原安装器/业务 journal |
| B 固定安装确认、查看内容、确认兑换 | 首次可理解，但已装或取消后可能重复点击；已领仍必须回读 | 已装首次 2；缺工具约 3；已领 0 | 0 秒，可能安装页→激活卡 | 授权可做，但多一个无价值产品点击；维护简单但转化摩擦高 |
| C 三秒倒计时自动安装/核销 | 表面 0 点击；重复或失败仍要查状态 | 表面 0，**缺业务授权时不得实际核销** | 至少 3 秒，可能无意自动跳转 | 倒计时不是主体/权益授权；可能错领或越权；不采用 |

点击与时间为**设计预算**，不是实测点击、转化率或错误率。方案 A 把已授权状态复用与一次确认组合；C 若按安全合同补上必要确认，便退化为 A/B，因此不为凑数量强行保留。

### 5.2 权威入口、最小字段、准入合同

| 内容 | 解决什么问题 / 可信来源 / 是否可推导 | 缺失及冲突行为 |
| --- | --- | --- |
| 开发专属链接 `/activate?activation_code=…` | 仅 `DEVELOPMENT_ACTIVATION_URLS` 原有固定 HTTP LAN 来源与 Host `currentPage.info` 证明当前页；不是生产密钥保护 | 精确原始源/路径/单参数/码格式不符、编码别名、片段或权限缺失：**不带入、不预检、不核销** |
| 生产短期受限引用（候选 `intentRef`，目前未实现） | 先复用原会员业务引用及 `voucherPreview`，必须用途受限、短时、非长期卡密，绑定主体和稳定领取意图，不另造票据服务 | 未配置则保留手工入口；过期/冲突拒绝；原严格解析目前不接受 `intentRef`，不可谎称已经兼容 |
| `app/marketId/version` | 此场景固定 app 身份 `ai-vip-share`，版本由受信安装发行记录确定；不由链接重复传 | 缺可信固定发行不能新增安装；链接自带冲突身份/额外字段拒绝 |
| `targetId/targetUrl/returnUrl` | 来源/页面目的地由会话分配、Host 和原导航规则得到；不接受网页指定的第二跳 | 缺合法目标保留原卡、展示回执与手动入口 |
| 领取主体、SKU、数量、起效规则、动作范围 | 唯一权威是当前登录 Provider 的**新鲜结构化预检**；旧会员缓存、链接文本与码前缀均不构成证明 | 任一关键信息缺失/变动禁止提交，重新核对受影响决定；不得偷偷给错账号 |
| `previewId / idempotencyKey / claimIntentId` | 原预检 ID 和本地随机键分别用于这次确认及其恢复；真正跨客户端唯一性必须由 Provider 对稳定领取意图、主体和发放实例原子约束 | 没有稳定业务身份和查询能力，不开启生产自动领取；另一笔明确授权的新领取使用独立发放实例，不错误拦截 |

**不新增第二套白名单、宿主或安装器。** Framework 已有 Market trusted channel/sender、固定包审阅、Installed Authority 与原安装 journal；`opendesk.market.intent.v1` 严格字段未获修改，不能追加 `autoInstall/ticket/onInstalled`。生产 Market channel 和 `REVIEWED_SERVICE` 当前未配置：外部入口只可指引到受支持的宿主/原“扩展”安装流程，**网页不能静默安装 Chrome 宿主**。已合法安装且兼容的工具直接复用，无须因 Catalog 离线、旧版本/来源差异重装；新包审阅/Chrome 强制权限和停用/撤权仍按原合同。

**产品 Preview 前置依赖**：开发 LAN 原 `/api/preview` 只提供账号、SKU 和 grantSummary，不能证明完整的商业数量/生效/动作范围或跨设备稳定意图。生产需要在**原 Provider 端点**补足这些结构化回执、交易绑定、业务唯一约束和按业务 ID 查询能力，不新增专属 Host/独立注册。GET、预抓取、状态读取与预检必须是**无核销副作用**；来源合法只是准入，不是点击同意。

### 5.3 确定分流、操作预算及页面

| 前置状态 | 用户实际下一步 / 业务点击设计预算 | 其他不可省动作与禁令 |
| --- | --- | --- |
| 宿主未安装 | 真实 Chrome 宿主安装指引，返回保留未消费意图 | Chrome 安装确认独立计数；无静默宿主安装 |
| 有宿主，工具缺失 | 原发行安装器核验/审阅 → 原激活卡 | 工具安装审阅另计；版本/权限/完整性不可跳过 |
| 已安装并启用，链接合法，缺领取授权 | **自动预检零核销** → 核对本人账号/权益 → 点一次“确认激活” | **1 个业务点击**；Chrome 权限、Cookie 确认另计 |
| 同一意图已有相符且有效业务授权 | 原权威记录直接续接授权范围内的动作 | **0**，不得误把安装许可当领取许可 |
| 同一领取已完成 | Provider 稳定业务身份查询原 receipt | **0**，只展示结果，不重复安装/核销 |
| 账号、数量、商品、起效或动作范围有变化 | 仅重新核对变化决定 | 不复用旧主体或变更范围的确认 |
| 已取消，刷新、换票据、重开或跨 Surface | 自动预检暂停；人工“查看激活内容”→确认仍可用 | 手动预检 +1，必要业务确认 +1；不自动恢复 |
| 超时、断网、丢回执或重启 | 原 journal 与 Provider status 查询原笔 | 不换 key 盲目再提交，不以缺历史当终局未执行 |
| 已领但网站授权/Cookie/导航失败 | 保留领取结果，重新从原网站授权、每批确认或手动打开继续 | 网站步骤单独计数，不自动启用代理、不伪称第三方 VIP |

**默认没有人为等待/三秒自动消失**；网络与安装展示真实进度，已完成和未知结果可持续回读。沿现有安装审阅区域及原激活卡连续展示，不重画 Side Panel 或并行 `app.html`。已确认的两个 Surface 共享 Framework Core/安装身份/SDK/权限/业务状态，各自独立路由、滚动、焦点和草稿；本工具真实双 Surface 运行待验。

### 5.4 最终提交、取消、幂等与恢复

1. 原链路：`voucherPreview`（绝无消费）→ 显示主体/权益 → 可信手势确认 → 新鲜 `member GET` 校验 → 原 `beginRecovery` durable CAS 写前日志 → 提交边界再查来源、主体、预检有效期和取消代次 → 原 `voucherRedeem` POST → Provider receipt/会员刷新。授权内容不完整的生产服务不能开放此流程。
2. **提交前取消**：自动预检网络等待时可取消，迟到预检回执不得恢复自动资格；取消代次变化，仍在 GET 或等待 durable 写入时阻止 POST；若原 write-ahead 已确认且 POST **尚未**调用，只清理经核验的原事务。清理结果未知保留锁，禁止自行重兑。关闭流程视图触发同一“阻止尚未派发动作”规则；来源页离开会使受限页来源重核失败。
3. **POST 已派发后的取消**：不承诺撤销核销，只停止后续自动会话和导航；晚到的成功/失败只能写回原真实结果，不重新激活下一步。点击返回只关闭展示，不等于清除原 journal。
4. 取消持久化复用工具既有 SDK storage/CAS，最小新增 `aiVipAutoPreparationPauseR1` 只存 `{serviceOrigin,accountId}` 范围、不含码或票据，写后必须读回核实。目的仅是**禁止自动预检资格在新票据/同主体重开/双 Surface 意外复活**，不作为任何领取许可；失败按自动资格未知处理、人工入口仍可用。因为 Provider 目前没有稳定领取意图，采用更保守的同服务+同账号范围，可能暂停另一笔合法领取的自动预检，**绝不阻止其用户主动确认**。
5. 安装状态由原 Marketplace install journal/Installed Authority 负责；兑换由原 `aiVipRedeemR52` journal/CAS 和 Provider 负责；网站会话由原 Cookie journal/Store/Partition/逐批可信授权负责。各一份唯一事实来源，不复制后台账本；过期的安装意图不得抹掉已提交兑换的恢复线索。
6. **服务端硬条件**：按稳定领取意图+主体+发放实例做原子唯一和状态查询，保证多标签/不同客户端同笔不重复；本地锁/随机 key 不是跨端约束。另一笔经过明确授权的独立发放实例可以合法领取。没有生产证据则 fail closed；结果未知只查询原笔，只有服务端可验证的最终“未执行”且原协议允许才能重新确认。
7. 会员领取、会话写入、网站登录和第三方 VIP 核验分别回报；第三方页面不接收卡密/凭据或拥有独立核销器，授权失败保留结果及人工入口，绝不自动开启代理或抢占其他标签。

### 5.5 真实实现范围与解除条件

唯一业务源码 owner：`projects/ai-vip-share/`。本轮差量是 `src/activation-links.js` 严格解析及取消范围模型、`src/main.js` 开发链接自动无副作用预检与取消代次、原 LAN 指引和定向 tests；不修改 `src/marketplace/intent.js`、`src/ui/sidebar-tools/installation.js`、共用 SDK 或并行 `app.html`。原 SDK/Host/Authority/权限不复制，HTML/Vue/React 兼容不受影响。

生产解除条件依次为：运营方批准 HTTPS 来源及真实发行 channel；原 Provider 提供短期受限引用、完整权益/作用范围、稳定领取意图与跨端原子唯一/原笔查询；完成原严格协议升级和来源/身份/撤权审阅；本地 Codex 运行定向测试、同源打包并晋升新版、Chrome 实际安装及链接/站点验收。**当前 production Provider 和 Market channel 未配置，本候选未完成上述生产条件**；开发 fixture 不证明真实商业领券/网站 VIP。

## 6. UI 状态与错误处理（现行，替代第 5 节旧状态机的冲突文字）

| 状态 | 权威事实与允许行为 |
| --- | --- |
| `host_missing / tool_missing` | 真实安装状态；只给受支持的安装/恢复入口，不冒称已装 |
| `activation_link_pending / activation_review` | 固定来源识别与 Provider 新鲜预检；自动查看内容不等于领取；完整展示主体/商品/数量/起效/动作范围后才允许确认 |
| `activation_paused / cancelled` | 原取消代次与保守持久范围；不自动再预检，用户可以手动预检；不等于券已使用 |
| `redeeming / outcome_unknown` | 原 write-ahead、POST 派发界线和 Provider 状态；已派发不撤销，未知不重播 |
| `redeemed / member_active` | Provider receipt/会员结果；刷新失败不抹去已核实发放，网站结果独立 |
| `voucher_used / voucher_expired / voucher_wrong_account / sku_mismatch` | Provider 返回的终局或错误；停止错误主体领取，不暴露他人信息 |
| `provider_unavailable / tool_disabled / grant_revoked` | 授权与当前状态失效，停在安全边界；不自动恢复或扩权 |
| `cookie_unknown / navigation_failed / proxy_conflict` | 各走网站、导航或代理原有状态机；兑换成功不代表网页登录或代理已启用 |

### 10.1 用户界面与唯一启停按钮（R4.2 修订，优先于 R4.1）

### 10.3 可信停止与控制权边界（实现要求，非新公共 API）

复用现有 SDK、安装身份与唯一代理所有权机制，不在工具内再建代理服务/全局注册表。下列为行为约束，不新定义第二套可调用 SDK：

1. 本地先可靠记录 `desired=false`、停止待确认及请求代次，取消定时启用/重试意图；即使 Provider、会员会话或互联网不可用仍执行。存储失败也须如实显示结果未知，不能声称重启后一定不会恢复。
2. 拒绝过期的启用回执；后台恢复、代理变化通知、会员兑换、其他扩展被停用等都不能越过明确停止意图重新接管。若停止与在途 `set` 竞态，宿主必须串行化并清理晚到副作用；UI 丢弃晚回执本身不足以清理真实 Chrome 设置。
3. **跨 Chrome 扩展**：核对本工具仍持有本扩展已保存偏好的所有权后，执行自身作用域的 `chrome.proxy.settings.clear(...)`，让 Chrome 重新选择剩余配置。不使用 `set({mode:'direct'})` 或 `set({mode:'system'})` 伪装停用，不把旧快照强写回去覆盖用户新配置。
4. 其他扩展优先级更高时，本扩展旧偏好可能只被遮蔽而未删除；不能仅因 `controlled_by_other_extensions` 就跳过自己的清理，否则对方停用后本工具可能自行恢复。Chrome `get()` 只能看到当前有效值，不能单凭它证明被遮蔽的偏好已清除：需要自身清理完成回执和所有权账本，并补原生双扩展测试。
5. **同一 OpenDesk Chrome 扩展内的多个 Sidebar Tools** 共享 Chrome 代理偏好。`controlled_by_this_extension` 只表示 OpenDesk，不表示 AI VIP Share。读取 owner 工具 ID、安装 epoch、作用域及请求版本，并在既有全局代理写锁内原子校验/清理。若 owner 已是另一工具，只取消本工具的待处理请求；不调用会清掉另一工具代理的全扩展 clear。
6. 清理后核对 SDK 所有权账本、clear 回执及 Chrome 当前有效配置。若当前由其他工具/扩展管理，分别展示“本工具已停用”和“当前由其他来源管理”，不要求所有代理都关闭才算本工具退出。失败保留停止意图和待释放状态；重试不重新启用。
7. 只清理本工具实际取得且被用户授权的作用域；保留 regular/incognito 边界，不为停用扩大权限。原 regular 偏好可能被隐身窗口继承，正式实现需测继承和独立覆盖，不能把常规配置验证等同全部隐身配置验证。
8. 提供可信管理入口，由用户决定停用哪个扩展。整个 OpenDesk 扩展被手动停用仅作为后台无法恢复的最后兜底，并明确会影响其他工具；不能暗中调用管理 API 禁用别人的扩展。

**当前源码事实**：核查 `8dc346e0` 时，`src/ai-smart-access/lifecycle.js` 已有 durable STOP、对自身偏好的 clear 和回读，并明确清理被其他扩展遮蔽的旧偏好。本轮不把这项已有能力重写为“缺失”。正式 UI 的控制可发现性、同宿主多工具 owner 交接、晚到副作用和真实 Chrome 场景仍须按当前 SDK 实现逐项验收，不能用原型的内存模型代替。
