## 2026-11-11 · Web Flow R2 任务生命周期通知 P0（OD-AI-WORKFLOW-BRIDGE）

**用户真正要解决的问题：** Web Flow 手动、自动或经原计划批准的浏览器脚本执行后，用户需要知道是否真正开始、正在执行、脚本是否执行完成、结果是否实际回传、失败/UNKNOWN 如何处理，以及如何查看原始运行记录。这不是扩展更新提醒，也不重建调度器。

### 唯一实现与事件语义

- **复用展示：** 原 [公开 ui.notify R1.2](../../../docs/api/sidebar-tools.zh-CN.md#非阻断消息opendesktooluinotifyr12-生命周期与可安装实验室) 和唯一 React Toast Store；手动沙箱只使用可选的 notify.open/update/dismiss，可信「运行与授权 → 当前任务」使用原 Host addToolToast/updateToolToast，均消费可信只读运行状态，不新增 ui.toast、Quasar、Host、API 回调或执行权限。
- **默认静默：** 网页匹配、Scheduler 计划到期、草稿保存、等待批准都不等于执行；只有原准入后出现匹配 Run 身份，才提示准备/执行。反复读取同一状态应更新同一条通知，不通过通知新建 Run。
- **完成与回传分开：** 手动任务需原 clientRequestId 关联、匹配的持久 Controller Result/runId/resultId、outcome.ok=true 且资源 released，才能提示「脚本执行完成（仅脚本执行）」。执行结果报告 blocked/no_results/dom_changed/dom_unavailable/stopped 时仅提示脚本报告阻断/异常，不提示业务成功。可信自动任务需相同 requestId、persistence=verified、release=released 才提示脚本完成；只有 delivery=confirmed 才提示原对话结果已回传。单纯 completed、Toast 回执 accepted 或分配了 Run ID 不是业务成功。
- **失败与异常：** 原可信失败仅展示安全的错误代码和原任务入口；尚未创建 Run 的失败是准入/启动问题，不声称脚本执行失败。UNKNOWN 显示结果未确认、禁止自动重试；旧 Host、不支持、通知超时、权限撤销时保留原正文与原请求记录，不能因为通知失败而重试脚本、发送结果或扩大授权。网页文本不能伪造可信状态。
- **生命周期与恢复：** R1.2 每实例每分钟最多 3 条创建、每句柄 12 次更新、30 分钟有效，实例卸载、停用/撤权、安装代际变化使旧通知失效。句柄非持久执行身份，关闭提示不删除原 Run/Result。手动任务在「记录 → 查询原请求（只读）」查看；自动任务在「运行与授权 → 当前任务」及原请求记录查看。P0 仅已打开的 Side Panel/PC 工具宿主可见；关闭侧栏、刷新后仍保留原记录，不能承诺不可见宿主 Toast。

### 范围与分级

- **P0（本轮）：** 在原手动与可信自动两条执行状态链上接已有通知，更新单条状态与异常提示，保留原管理/查询入口；不改原调度、授权、运行或数据表。
- **P1（后续）：** 解决关闭宿主后跨 Side Panel/PC/多窗口去重、未读状态与恢复索引，仍由原 Run/Result 提供事实，不另建账本。

- **硬性验收否决：** 业务未成功却通知业务成功；通知扩大原执行权限；通知重复事件导致任务重新执行。源码、Node、可安装包、真实 Chrome、业务接受分层取证，不能相互冒充。

### MD 数据合同与可读性

唯一最小标识为文件首个非空行 `<!-- webflow-todo:v1 -->`，其后一个 `# 队列名`、一个 `## 目标` 正文，以及按文件顺序的 `## T01 名称` / `## T02 名称` 等固定 ID。每项下面分别使用 `### 输入`、`### 任务`、`### 产出`、`### 验收` 标题及非空正文；不可用 task ID 重复、字段重复、必填字段缺失或未闭合代码围栏。围栏内部的伪任务/字段标题仅作为文本，不生成任务。解析器要报告错误码和行号，不能自动猜补。来源示例：[md-demo.md](../examples/workflows/md-demo.md)。

当前支持 `auto:sum-count-marker:v1`、`auto:doubled-marker:v1` 两项已编码验算规则，以及明确写作 `manual: <核对方式>` 的人工验收；自然语言“质量好/95 分”不等于自动通过。第一版独立 Demo 限定 T01 输入 `numbers: [17, 28, 35]`、T02 输入 `artifact: T01` 加 `multiplier: 2`，可修改数字并重新定义下次运行。普通任务以后可扩展已审阅验收规则，不从 MD 中执行任意 shell/JS。

### 来源、运行版本、授权与状态

- 公共 GitHub Markdown 仅允许明确 HTTPS blob/raw 文件 URL，不接受 URL 密钥。**已确认隔离页 `src/sidebar-tools/sandbox.html` 的 CSP 为 `connect-src 'none'`，直接 `fetch` 必然不通**；读取改走现有 `OpenDeskTool.request('browser.network.request',{method:'GET',url,config:{responseType:'text'}})`，工具包须审阅新增 `network` capability，原宿主在 Chrome 尚无 `raw.githubusercontent.com` 网站访问权限时提示用户批准。原网络服务禁用 credentials、禁止自动跳转；只处理真实 HTTP 文本回包、计算内容 SHA-256，网络/权限/文件缺失明确报错，**不得回退内嵌演示数据**。私有仓库须独立的可信 GitHub 授权读取接口；本地相对路径基于已绑定授权工作区，绝对路径不构成权限。实际安装后的公共网络读取与域名授权 **CHROME_NOT_TESTED**。

- MD 只描述任务，不存储执行状态。聊天 URL、消息、真实发送回执、成果及 SHA、验收、UNKNOWN、恢复点必须留原 Durable Run/Result/权限所有者。恢复只查询/对账原操作身份；只有用户明确重跑才产生新 run。文件中的 `[x]` 不证明执行。
- 每个新聊天需在发送前确认账号/Origin、目标 conversationId、能力接入和监听 ready；新建、初始化、业务提交、工具结果回填分开计数。自动提交、成果写入、回填结果出现 UNKNOWN 时只按原身份对账，不重建/盲重发；草稿、IME、附件及其他 writer 占用必须停止。
- T01 可释放 T02 的必要条件为：原聊天回复完整且来源绑定；独立验算通过；成果已真实持久化并二次读取（版本、marker、内容一致）；原发送及附属任务均已结清。T02 的**实际提示词必须包含 T01 已读回的 JSON 正文**，不得仅包含文件名、路径或模型生成的概述；不得再带 T01 原始数组或预期答案。数字期望由可信验算器计算，Demo 基线 T01 `sum=80,count=3`、T02 `doubled=160`；修改 35→36，预期必须变 81/162，防硬编码。

### 2026-11-12 · 目标纠偏：AI 总控与有界子任务接力（OD-AI-WORKFLOW-BRIDGE-GOAL-RECOVERY-R1）

- **WebFlow** 管理任务意图路由、工作流顺序/父子关系、可信回传和暂停恢复；**独立网站 Controller Task** 仅负责创建/定位网页、草稿、原生提交与回答观察；**Browser Framework** 继续负责原 Installer、Authority、RunHost、Document、Durable Result 和防重放。projects/subagent/ 是可选的 Mini Chat 发起/展示消费者，不应成为 WebFlow 内核运行依赖，也不把 WebFlow 业务硬编码进 Subagent UI。
- 复用已存在的 webflow.task.intent.v1、V2 候选、安装 Task 和 opendesk.workflow.handoff.v2 数据合同；2026-11-09 历史提出的 webflow.conversation.create.v1 是待审**方案**，不是已获证明的生产协议。**先做真实消费者/缺口审计，证明既有协议无法表达必要用例后才考虑版本化新增**；禁止为父子任务新增第二套 Runner/Host/账本或向 V1 五字段偷加字段。

**分期且有界：** M1 真实 A→B→A（一个子任务，默认为结果回填草稿、是否发送独立授权）；M2 A→B/C→A 的连续任务；M3 有明确父子关系与依赖的**有界多级交接**；M4 通过独立 Provider Task 扩展其他 AI 网站。重复候选/消息、回填再触发、ACK 丢失、重新打开聊天、页面改变均需使用同一原身份只读对账，不自动新建或重复点击。任何继续执行都受原批准范围、最大步骤/派生数/并发、时限、预算、Stop 和人工接管约束；“持续执行”不等于无限授权或设备离线仍运行。

**验收与优先级：** 首先证明用户能完成一次**真实**“A 生成协议候选→已安装 Task 创建并执行 B→B 完整回复入原 Durable Result→正确回填 A，且无重复发送”的 M1；随后才能验证 A 收到结果后生成下一轮候选的闭环。用户提出的总控/子任务目标高于 R2/R3 的两阶段草稿专项，但**不废弃已有 0.2.0/0.3.0 代码、版本锁、权限保护或已取得的真实证据**。SOURCE、NODE、PACKAGE、CHROME、BUSINESS 单独报告，只有真实 Chrome/BUSINESS 证据才能标为产品可用。

## 3. 用户流程与授权语义

### P0 调试路径（允许保留）

AI 输出候选 → 用户手动“采用”或建立请求 → 查看真实 Task / 目标 / 参数 → 用户执行 → 网页操作 → 持久结果 → 原聊天。

### P0 目标路径 A：自动发现 + 必要的一次批准

AI 完整回复 → **OpenDesk 自动发现并准备候选** → 未获本次执行许可时显示准确任务、网站及参数 → 用户点击一次必要的批准/执行 → 原有可信执行与结果回传。

不能把发现候选的按钮点击当作产品的正常必要步骤。采用候选不代表已经运行。

### P0 目标路径 B：已预批准后的自动触发（旧模式保留）

用户先通过**可信 UI**批准明确的一次请求或受限执行计划（包括 Task/目标/参数和有效范围）。AI 完整回复并匹配该许可后，OpenDesk 自动核验和触发，无须再次点击“采用/执行”；成功之后仅一次向原聊天交付。

**本阶段已有“一轮自动批准”的历史技术实现，不等于已实现长期全局自动授权。** 不得为了减少点击而扩大授权；缺少许可、匹配不明或高风险操作时保守停止并请求必要确认。用户可停止和撤权；模型不能自行新增、延长或扩大授权。

### V0.1-R2：可信持续批准后的自动触发（2026-11-02）

用户在真正的 OpenDesk Side Panel「扩展 → Web Flow」页头下通过“自动运行”滑块和“任务范围与授权”（全局可信设置保留同一入口），准备并审阅已安装任务的精确地址、完整参数和安装身份，主动点击「批准此任务持续自动准入」，再开启默认关闭的总开关。后续新 `webflow.task.intent.v1` 候选在相同批准范围内自动准入，无须采用、执行或五分钟批准。此许可仅允许提交候选，Controller 和 Chrome 原网站权限仍逐次核验。

初始精确模式批准绑定 taskId、version、manifestHash、contentHash（对应原 program.sourceHash）、scriptId、revision、installationId、generation、精确 targetUrl 与规范化 args。该模式中参数或地址改变、任务停用、安装/源码/代际变化均不继承旧批准。总开关关闭及逐任务撤销即时保存，仅阻止后续准入，不承诺回滚已开始的动作。Worker 恢复不重放历史候选或 UNKNOWN。可变化的业务输入按下面最新合同审核，不从旧精确批准推断。

该增量的源码、组件、构建与 Chrome 证据分别记录在[唯一执行计划第 12 节](execution-plan.zh-CN.md#12-v01-r2-持久授权与自动准入2026-11-02)；未取得真实 E1/E2/E3 前不能标 PRODUCT_DONE。沙箱 Web Flow UI 不获得私有授权 API，持续授权组件只由固定可信宿主编译加载。

### 任务范围授权与可变化的业务输入（2026-11-04）

自动运行开关只决定是否接收新任务；可信任务授权决定允许的任务、安装版本、目标和输入范围。对已审阅的百度搜索，可一次允许 `query` 按该安装版本实际 Schema 的长度/类型约束变化，其他参数（当前 `limit:3`）、精确目标和全部安装身份保持固定。换合法关键词直接沿原准入与执行链自动运行，不能因为示例输入不同再要求逐词批准。目标、固定参数或安装改变时重新审阅；缺网站权限仍走原权限链。不能把任意任务的 Schema 当成允许收件人、金额等参数自动变化的授权证据；当前可变字段仅由 Web Flow 自己的已审阅搜索策略声明。

审核卡片先展示任务、本次输入与可变化/固定边界，“允许更换关键词并执行”保存规则后只执行同一原候选；“仅允许此关键词”保留在高级入口。任务授权设置提供同样两种选择，切换选择使旧审核失效。历史精确授权不静默扩大；用户可从原授权转换并审阅一次，转换完成后不再为规则内的词重复批准。新策略由可信 Host 从解析出的真实安装 Schema 生成，不能采用 AI/页面/沙箱传入的放宽 Schema；持久 Ledger 在准入、预留及最终 Controller 提交前继续核验策略、撤权与安装围栏。原 candidate/source/request、单次消费、UNKNOWN 不重放和原聊天结果交付合同不变。

本轮变更的组件验证不代表本机已转换旧授权；新的 Chrome 原生批准及不同关键词真实执行证据仍单列 `NOT_TESTED`。

### 本次命令的可见回执

侧栏 Web Flow 的“运行与授权 → 当前任务”应将当前任务名称/版本、手动或预批准触发、目标网址、参数与执行状态放在同一区域；完成后展示同一运行的持久返回值，并明确资源释放、原聊天收到结果、AI 续答的不同事实。原始结果和运行身份默认折叠，按需展开。返回数据只作为原始数据展示，不能当成新的任务指令。右侧开发页的草稿和历史查询独立存在，不是 Bridge 当前运行的完成证明。

「查看执行页面」仅定位本次运行中、仍有效的自有目标；定位中、已切换和定位失败有独立提示，完成回执不能覆盖失败信息。运行结束、撤权或文档身份改变后，不为方便观察另开页面、重新执行或重放副作用。格式解析/绑定失败还未提交 execute 时，取消应明确撤销授权、不会执行；已提交 execute 的停止未知与回传未知继续保守处理。

实现和具体操作入口见 [Task README](../../../examples/tasks/README.zh-CN.md#看见网页动作分别测试手动和自动触发)。这些显示规则不放宽五字段协议、来源/安装核验、一次消费或持久防重放。

### 自然语言与任务代码的关系

**2026-11-03 用户最新澄清：正常官网聊天是主入口。** 用户正常在 ChatGPT 发送需求，由 AI 生成受限任务候选，OpenDesk 再核验并执行。“准备/生成 ChatGPT 指令”只能是可选的诊断与示例辅助，不能成为每一次任务的必经步骤；用户不应自行填写协议、Task ID、candidateId 或复制授权卡才能使用。必要的一次接入、能力说明及权限审阅须由真实产品明确呈现并保留证据，不能把每轮复制固定 JSON 让 AI 回显冒充正常聊天已经可用。普通消息尚不能稳定产生可执行候选时，应明确标记该入口未就绪及具体缺口，不能只显示含糊等待或旧任务成功。

该澄清不授权本地执行器猜测自然语言后直接运行，不放宽既有五字段候选、已安装任务、精确范围、原生发送见证和 Authority。需要补齐的是 AI 如何获知可用能力及正确生成候选、正常消息的真实联通和清晰的执行回执。旧“自然语言理解不属于本需求”限定本地执行器职责，不得解释成用户必须每轮手工使用协议生成器。此前复制回显链和 HTML 分数仅保留原证据等级，不能证明本主入口已交付。

固定格式是官网 AI 与 Bridge 之间的数据合同，不是用户输入表单。AI 在一次接入的能力说明范围内按约定输出候选；OpenDesk 负责检测、严格解析和调用已安装脚本。`runId`、SHA 等运行身份属于高级详情。本地执行器不从自然语言自行选择或创建脚本。当前开发接入说明来自原 Task Catalog 核验的已安装任务及完整参数 Schema，另列有效精确批准，不能把批准样本当作程序能力上限。说明须在 ChatGPT 当前项目的项目设置中审阅、保存；它只在所选项目生效；普通聊天可单独发送一次可见能力说明，仅限该聊天。两者都不代表全局 ChatGPT、原生工具或 MCP 已连接，也不授予执行权限。

**新精确范围（2026-11-03，后续保留为高级固定输入模式）：** Schema 支持但未批准的完整新候选保留原 candidate/request/source/installation，明确待批准且零执行。可信“当前任务”展示本轮参数和来源/安装身份，不要求重填 JSON；原生点击“批准此精确范围并执行”后，同一原请求沿原准入围栏仅提交一次。每个任务仍只有一个有效批准；选择固定输入模式时，新批准会替换该任务原精确范围，不并存、不变成通配；选择可变关键词模式则按上文新合同匹配。后续匹配批准规则的新普通消息无需再次接入或审批。不符合 Schema 的需求明确未执行，不能改参数迁就批准。真实原生 Stop 会退休本轮发送见证，迟到完整候选不恢复；官网短暂的 cancelled DOM 标记本身不作为用户停止手势。

## 4. 协议与可信执行边界

### P0 任务候选

**两部分回复（2026-11-09）：** AI 对执行请求先用一小段正常中文说明准备执行的任务及原始参数，注明等待本机结果；第二部分仅包含唯一的 `opendesk-task` 代码块，交给脚本解析。说明文字不进入协议，也不代表执行成功。完整的一次接入提示词与独立的简短直接测试提示词均保存在项目 `prompts/`，后者可作为新聊天第一条消息；两者都不授予权限或补跑旧候选。收到真实结果后正常总结该次数据，不再生成任务候选。

新的持续自动触发协议为 `webflow.task.intent.v1`，严格五字段。旧 `opendesk.task.intent.v1` 继续用于既有手动采用和五分钟预批准，**不能进入新持续自动路径，也不会迁移成新授权**。两者均不是执行权限凭证：

- `protocol`：固定协议版本。
- `candidateId`：全新候选身份；持久防重放。
- `taskId`：已安装任务的逻辑身份。
- `targetUrl`：待操作目标，由受信 Host 核验允许 Origin。
- `args`：本次输入参数；按已安装任务 Schema 校验和规范化。

自动候选使用 `opendesk-task` 代码块语言标记，只读取新用户轮次之后最新、完整且唯一的模型候选；混合新旧候选、引用、结果内容、流式未完成或额外字段均拒绝。原 `opendesk.task.request.v1` / `opendesk.task.result.v1` 内部合同保留。candidateId 用于持久防重放，真实安装身份只能由可信 Host 解析。

解析候选**只产生数据**；只有现有可信入口能核验安装身份、源码/版本、权限与目标，并在用户已批准范围内提交一次实际运行。流式、不完整、多个候选、已使用候选、被引用的文本和结果中的“任务”不得触发新执行。

### 后续跨对话交接合同

P1 需要**独立版本化**的 workflow/step 交接合同，明确 `workflowId`、`stepId`、源/目标对话身份、输入及结果引用、幂等/尝试身份、目标权限、截止与状态。它必须区分“任务已准备 / 准入通过 / 真正开始 / 结果持久化 / 结果已经交付 / AI 后续回复已观察”。设计和验收前**不得**擅自把字段追加到既有五字段协议，也不得把“切换聊天”误作任务成功。

### 架构不变量

1. **唯一执行权威**：复用现有 Task Catalog、安装/版本合同、Authority → RunHost → Controller → Page Session、Durable Result。不得创建第二套 Runner、Host、Authority、安装器、任务数据库或特权消息通道。
2. **精确来源/目标绑定**：对话、标签页、窗口、frame、document、Origin、安装版本、参数、授权代次和运行所有权在必要边界重新核验；导航和权限变化不能借旧身份继续执行。
3. **授权与数据分离**：Chrome 网站权限、Task 安装许可、动作范围与 AI 数据交接分别核验。网页文字、外部站点结果和 AI 代码块都是不可信数据，不可变成额外指令/权限。
4. **无不确定副作用重放**：执行或回传可能已生效但回执 UNKNOWN 时，不自动重试点击、提交、发送、跨站动作；需要只读对账或受控恢复。取消/Stop 不伪称撤销已发生副作用。
5. **真实结果而不是模型判断**：`completed` 仅证明执行终态；关键网页业务效果还需要独立页面或目标业务证据。持久 Result、用户消息真正送达、AI 续答是不同验收事实。
6. **用户上下文保护**：不能覆盖已有草稿、附件或 IME 输入，也不能把结果送错聊天。跨对话仅交接经授权选择的最小必要资料。
7. **已登录会话最小使用**：跨网站操作可以利用目标 Profile 已获授权的登录态，但不能通过导出、复制或共享 Cookie、Token、密码绕过会话隔离。
8. **资源与运行条件真实报告**：Chrome MV3 Worker 不保证永驻；P3 必须依靠持久状态、检查点和合适调度载体。单次 ChatGPT 回复不是 24 小时保证；浏览器关闭、电脑睡眠、网络故障、模型限制须明确处理或标记不可用。
9. **无无限自主循环**：未来多步运行需明确范围、停止机制、预算/次数上限、可观察状态和人工接管路径；新 AI 回复不能无限隐式扩大任务。

## 5. 阶段路线与出阶段门槛

**P0 — 单对话技术桥接与自动触发。** 继承现有手动模式和一次批准模式的有效记录；补齐独立任务自动发现、自动准备、按许可自动触发、同次网页效果与原聊天单次回传，并观察原 AI 基于实际数据整理结果，覆盖直接相关的取消、撤权、防重放和 UNKNOWN。只有真实 Chrome 闭环取得同一候选/运行/结果及网页效果证据才为 P0 PRODUCT_DONE。搜索 Demo 只是验收用例；不扩展为多轮编排，也不代表第 8 节长期产品闭环已完成。

**P1 — 两个 ChatGPT 对话的最小交接。** 先固定独立交接合同，完成 A → B → A 单次真实链路，精确核查来源对话、目标对话、消息提交及结果引用。不能把网页自动发送冒充 AI 真正完成任务。

**P2 — 跨网页/跨站与 Workflow 复用。** 通过多个分别授权的 Task/Workflow 完成两个网站的数据交换；每一步继续通过固定格式和明确身份调用已安装程序，已有单 Origin Task v1 不因“工作流”名义被放宽。

**P3 — 持久队列与长期恢复。** 保存调度状态、幂等身份、步骤结果、停止/取消、UNKNOWN 对账；验证浏览器/Host/系统可用性边界。目标是条件满足时持续推进，而非承诺 ChatGPT 单轮无限回答、设备离线仍运行。

**P4 — 多 Profile / 多账号执行节点。** 独立的登录态、授权、任务及结果存储范围；节点选择、故障隔离和恢复均需新的真实证据，不以一个 Profile 成功代替全部。

每个阶段**独立授权、独立验收**。P0 验证通过后记录下一阶段接口约束，但不自动开发 P1–P4、production、全量压力和多浏览器矩阵。

### 责任划分

### 状态必须分层

`SOURCE_IMPLEMENTED`、`COMPONENT_TESTED`、`BUILD_VERIFIED`、`CHROME_NATIVE_VERIFIED`、`PRODUCT_DONE`、`PARTIAL`、`FAILED`、`UNKNOWN`、`NOT_TESTED`、`NOT_SCORED` 各自只表达真实证据。历史成功仅对其实际代码/安装候选有效；新代码不得自动继承旧原生 PASS。测试数量、单次搜索成功、专家自评和完成态文本不得互相替代。

### 防止在相似对话之间重复工作

- 将多个相似聊天视为**同一产品的不同阶段/测试**，每次先做跨对话差量核对，不重放封存 candidate/run。

## 8. 连续任务的产品形态与完整业务链（2026-11-01）

### 8.1 一个 Browser，按职责组合

**方案选择：Web Flow 作为 OpenDesk Browser 内的独立业务扩展应用，以 `projects/webflow/` 为项目根；Browser Framework 继续提供通用能力。** 使用同一个 OpenDesk Browser Chrome 扩展，应用内部区分网页动作编排、AI 交接与持久调度业务。用户已确认独立目录归属；运行时接线与正式安装仍需按阶段实现和验收。

新增 Web Flow 的任务定义、步骤衔接、结果整理、交接包、恢复决策和应用界面代码归本项目。公开 SDK、Authority、RunHost、Controller、通用存储/调度仍归框架；发现公共能力缺口后才按原规则最小扩展。现有 `src/native-agent/` 中的 Bridge 属当前已存在的接线事实，后续若提取其业务实现到本项目，需同时核对消费者、固定构建来源、安装身份与测试，不在本次目录调整中搬动源码。

| 方案 | 取舍 | 本轮决定 |
| --- | --- | --- |
| 一个 Browser 内的组合能力 | 复用账号所在 Profile、既有授权、运行与结果链；内部模块分别维护 | 推荐作为当前实施方向 |
| 两个独立 Chrome 扩展 | 增加安装、版本、跨扩展消息、身份及状态一致性成本；现有仓库未证明需要这个隔离边界 | 当前不采用 |
| 既有 Native / 远端执行节点承担持续运行 | 仅在要求用户浏览器关闭后仍实际操作网页时评估；必须另有可用浏览器、账号授权与真实部署证据 | 后续环境能力评估，不作为本轮前提 |

“一个 Chrome 扩展”不等于把 Page Program、Sidebar Tool、Controller Task 的安装身份与权限合并。现有 AI Send Queue 已是组合产品：唯一 owner 为 `projects/ai-send-queue/`，Page 负责网页队列，Sidebar 当前仅提供使用提示。保留这些明确职责，不复制旧目录或重新建队列产品；本轮也不恢复已取消的 Sidebar 消息列表。

另有 [ChatGPT 计算接力样例](../../../examples/tasks/chatgpt-relay-calculator-r1.README.zh-CN.md)：原 Controller 草稿结合公开 `AppStorage`，已经写出固定 A→新对话 B 及单记录检查点代码，当前说明仍为 `SOURCE_IMPLEMENTED / CHROME_NOT_TESTED`。遇到未完成检查点会拒绝新运行，不是自动恢复器。优先复用其任务相关性、原文保存和防重放思路；真实运行前先核对现行原生输入及跨 document 合同，不把它当通用跨对话能力已交付。公开 Controller `AppStorage` 也应纳入持久能力预检，不能把 Page 的内存限制推断为整个仓库没有持久化。

Web Flow 的每个网站动作继续经过 Task Catalog → Authority → RunHost → Controller → Page Session → Durable Result。AI Workflow Bridge 负责核验来源、选择已经明确声明的后续步骤、构造交接包及确认交付；调度状态进入现有持久化体系。网页 Page 组件只能通过经审阅的公开能力参与，不能直接取得宿主私有数据库或任意 Native 通道。

先验证公开 SDK 是否满足消费者。现有 Sidebar 存储、App Service 或定时任务不自动等于 Page 持久队列或后台浏览器执行能力；不足时按原 Extension Type & Ownership Gate 给出可复现的公共缺口，再由对应 owner 最小扩展。不得提前创建第二套数据库、Runner、Host、Authority、安装器或新的“万能后台”。

### 8.2 需要真正跑通的业务链

1. 用户在对话 A 发起明确研究/开发任务，或选择一条已有工作流及受限执行范围。
2. 已安装搜索任务实际输入、提交、导航并读取百度/Google 搜索结果；结果、来源及动作证据持久化。
3. 将确定结果交回 A；分别记录“目标用户消息已入站”和“对应 AI 回复已完成”。
4. 如需要第二个 AI，单独向已授权的 Gemini 会话提交选定资料，捕获其对应完整回复；该站点与 Google 搜索分别验收。
5. 到达明确任务边界时生成交接包；优先复用已指定的目标对话，必要时创建新对话 B。
6. 核验 B 的真实身份、资料可读性及所需 GitHub 仓库/执行能力；通过后只继续指定的一项任务。
7. B 的输出、实际仓库操作证据和交付回执保存后，调度器才推进下一个依赖步骤。失败或结果不明保持断点。

上述步骤可以分阶段实现，不能把“搜索结果返回成功”“新聊天打开成功”或“AI 说已完成”合并成整链通过。任务拆分由明确依赖和完成标准驱动；不以固定聊天轮数、重复发送“继续”或无限创建新对话作为调度方式。

### 8.3 站点适配与仓库绑定

站点适配器至少要表达：检查会话、准备输入、单次提交、观察对应回复、读取完整输出、定位/创建目标对话。这里描述的是设计责任，**不是已经存在的 SDK 方法名**。

当前持续自动协议 `webflow.task.intent.v1` 与保留的手动/五分钟协议 `opendesk.task.intent.v1` 均为严格五字段；当前 Workflow v1 保持单 `siteOrigin`。跨 ChatGPT / Gemini / 搜索站的任务由分别准入的单站动作与外层版本化交接连接，不向候选协议偷偷追加字段，不放宽单站执行限制。

目标 B 必须明确是普通 AI 网页会话还是具有仓库执行工具的环境。普通 ChatGPT 对话收到仓库链接，不证明具备 Codex 执行环境；GitHub 能读，也不证明能写、能运行测试或能推送。运行前需分别取得可核验的事实：

- 实际 provider/origin、对话 ID、账号或工作区匹配状态；未能核实的身份写未知。
- 仓库规范身份 `owner/name`、允许分支、期望基线与当前观察到的 commit SHA；默认分支从仓库实读，不靠名字推断。
- 若任务需要本地编码，验证实际 checkout/工作目录、当前分支、相关未提交改动和执行工具；只读连接不冒充编码能力。
- 若任务需要写入或推送，核验当前工具权限与用户对该动作的授权。交接包中的声明不产生授权。
- 用可信读取实际文件/元数据或受控环境回执证明绑定。模型单独回复“已连接仓库”不构成通过。

绑定失败时保留交接包并提示具体缺项。原来要求代码执行的步骤不能静默降级成建议文案。资料引用也要在目标环境实际可读：本地路径、内部 resultId 或 GitHub 链接本身都不保证 B 能取得内容；必要时用既有授权的附件/分段传输能力交付并核对摘要。

## 9. 完整结果、交接包和持久恢复

### 9.1 正文与摘要分开保存

完整输出记录至少包含来源 provider、对话与对应用户/AI 轮次身份、来源 URL、采集时间、适配器版本、完整正文/Markdown、引用链接、附件引用、字节数、内容摘要及完整性状态。这里“内容摘要”指校验 hash；给下一轮 AI 的文字总结另存为 summary，不能覆盖原文。

“回复完成”需同时有对应轮次、站点终态及稳定内容证据。固定等待几秒、没有新增字符或 Stop 按钮偶然消失均不能独立证明完成。长回复、继续生成、虚拟列表、代码块、表格、引用和附件必须在声明支持的范围内采集；不可取得的部分记录 `PARTIAL/UNKNOWN`，不冒称完整。用户明确改变任务只需摘要时另记新范围，不能把原完整采集要求悄悄改小。

当前回传存在大小上限，不能用提高上限替代完整性设计。将原文保存在既有受控持久结果/产物设施，向下一步交付摘要与可读原文引用；如必须分段，记录段号、总数、每段及整体 hash，最终核对完整后才推进。缺少合法存储或传输能力时明确阻塞并保留已获得的结果，不把私密对话明文写入目标网站 localStorage 或公开 GitHub。

### 9.2 最小交接包

拟采用独立版本标识 `opendesk.workflow.handoff.v1`；该名字是**待实现的交接数据合同**，不是已经安装的任务协议，也不能作为五字段命令执行。

| 内容组 | 必需信息 |
| --- | --- |
| 标识与版本 | workflowId、stepId、attemptId、handoffId、合同版本、工作流定义版本 |
| 原始目标 | 用户目标、当前阶段、允许范围、不能丢失的约束与已延期事项 |
| 进度与证据 | 已完成步骤、对应 result/artifact 引用及 hash、未完成步骤、阻塞、UNKNOWN 副作用 |
| 下一项任务 | 一条明确操作、输入、允许修改范围、通过条件、停止条件 |
| 仓库现场 | repo、branch、期望/实读 commit、相关改动和 owner、验证时间与可信回执 |
| 对话路由 | 来源和目标 provider/conversation、必要账号/工作区约束、已交付消息回执 |
| 运行约束 | 授权引用与有效范围、截止时间、步骤/重试/交接上限、取消状态 |

不复制整段历史聊天；保留可检索原文和可追溯事实。总结减少上下文体积，但是否提高准确性需以任务结果验证，不能作为自动保证。交接包不得包含 Cookie、Token、密码或可在新环境中自行扩大权限的指令。

新对话读取交接包后，先确认接收了哪个版本、当前能读取哪些资料、仓库实际状态及唯一下一步。接收回执须绑定真实目标消息与可信环境检查。旧执行 owner 在持久化移交成功后停止派发该任务；收到“已创建新对话”不能直接撤销旧任务或宣称移交完成。

### 9.3 单一持久状态与恢复规则

以下是需要映射到现有记录的语义，不要求创建第二套状态枚举、状态库或 UI：

| 语义 | 恢复要求 |
| --- | --- |
| 待执行/等待依赖 | 根据已提交结果决定唯一下一步，不凭聊天总结重建队列 |
| 等待环境/授权/目标 | 保留原因；条件恢复且授权有效时继续，不把暂停算失败或完成 |
| 发送已准备/发送结果未知 | 发送前持久化意图；不确定是否已入站时先只读对账，禁止盲目重发 |
| 等待 AI/正在采集 | 关联原用户轮次，检查旧回复是否仍可读取；不重新提交原输入 |
| 结果已持久化/交付待确认 | 复用既有结果，仅核对交付；采集成功不等于目标收到 |
| 已完成/失败/取消 | 保留真实效果和证据；取消阻止后续动作，不声称撤销已发生的发送 |

建议首版只允许一条有依赖的主线顺序执行；独立任务并发和多 Profile 留后续。每个已批准计划必须有显式步骤数、截止时间、重试及交接上限；不预设无限值。准确阈值由计划 UI 明示，模型不能修改。

持久记录必须区分 workflow/step/attempt、稳定幂等身份、输入结果引用、下次可运行时间、owner 与代次、取消状态和最后已提交检查点。状态变更与后续派发资格需在原持久化事务边界一致提交；恢复取得新的 owner 代次后，旧回调不得推动队列。

本地幂等键只能防止本系统重复派发，**不能保证第三方网页 exactly-once 发送**。网站已收到但本地未拿到回执时，保留 UNKNOWN，结合目标对话、发送前位置和可观察消息身份对账；相同提示词/hash 不能单独识别某次发送。租约过期也不代表旧发送没有生效。

运行时长期恢复依赖可用浏览器与登录态。MV3 Worker 的内存和定时器不能作为队列唯一事实源；Chrome alarms 仅负责唤醒检查，启动/更新后从持久状态重建所需 alarm。睡眠、浏览器关闭、会话失效时保存等待原因；设备恢复后重新验证安装、授权、目标 document 与仓库状态，禁止复用旧 document 的短期批准。

Chrome 官方依据：[Worker 生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)、[alarms](https://developer.chrome.com/docs/extensions/reference/api/alarms)、[storage](https://developer.chrome.com/docs/extensions/reference/api/storage)。2026-11-01 查阅的 alarms 文档在 Chrome 150+ 提供 `persistAcrossSessions`，但更新仍可清除 alarm，不能把 alarm 当队列或用它唤醒睡眠设备。现有 Native 集成是否独立常驻要实际核验，[Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) 连接本身不证明 24 小时运行。

## 11. 通用网页任务适配 V1.1

用户于 2026-11-03 要求将网页任务入口升级为通用平台。目标是：已授权网页的任务事件，经统一发现、网站及适配器识别、原 Task Catalog/Authority、原 Controller/RunHost 执行，持久保存原 Run/Result 并交付正确接收方；关闭 Side Panel、切换标签、Worker 休眠和浏览器重启后安全查询与对账。ChatGPT 是首个案例，不为每个网站复制授权、执行器、任务库或调度器。实际进度及关键门禁只在[执行计划 12.13](execution-plan.zh-CN.md#1213-持续目标与关键测试条件2026-11-03)维护。

**统一选择 C：Generic Runtime + 少量固定 Site Adapter + 受限声明式 Profile。** Runtime 负责顶层页面事件、协议识别、候选传递、会话和适配选择；不授予权限、不执行 Task。Profile 只选择已编译、已审查的适配器与协议。网站产生的 JSON、DOM 和消息均是不可信候选；配置声明不能替代真实 sender/document、Chrome 网站权限、原安装身份及 Authority。

四个对象分别管理：Site Profile 是站点路由数据；Adapter 是固定适配代码；Task Script 是经原流程安装的自动化版本；User Permission 是实际批准范围和 Chrome 权限。不同来源可共享同一 Generic Adapter，但不能共享未批准的 Task 来源范围。原无来源字段的自动批准只代表 ChatGPT，不能解释为所有已登记网站；现有逐 Task 批准只保存一个来源范围，重新批准会替换原范围。

**Adapter Creation Policy：**

1. 遵循标准任务协议的普通网站使用 Generic，不创建专用 JS。
2. 仅匹配来源不同，增加 Profile，不复制监听器。当前只支持精确 HTTP(S) origin；同一 origin 最多一个有效 Profile，不支持隐式路径优先级。
3. 必须识别特殊 DOM 时才建 DOM Adapter；网站完成标记、轮次和结果位置须有真实证据，不能从导航选择器推断回复完成。
4. 有独立消息机制才建 Protocol Adapter；特殊观察或回传才建 Site Adapter。网站 DOM 不放入公共 Runtime。
5. 特殊权限进入原权限审查、真实用户手势及 Authority；Profile 不含权限、远程 JS 或能力授予字段。
6. 适配器版本来自固定代码目录，Profile 同时记录自身版本和所需 Adapter 精确版本；未知、停用或升级不匹配均拒绝。升级先撤旧注册，再登记新身份；已失效候选保留终态和防重放记录，不借新版本重放。
7. 版本兼容无法证明时停用对应 Profile。不能以放宽全部站点选择器修复一个网站，也不能因注销注册就假定旧 Content Script 已销毁。

**注册、批准及恢复规则：** 可信 Side Panel 读取并校验配置，用预期旧配置比较后保存，避免覆盖另一窗口的新登记；普通站批准动作在真实手势中申请来源和目标网站权限，再核对原 Task 安装快照，最后保存原持续批准。单独写 Profile 不授权执行，权限拒绝不保存批准。停用/删除、权限撤销或版本变化时对账动态注册；已载入文档仍经后台逐次核验。新文档不能领取旧文档私有结果，已消费请求不能转交新 Host。结果交付先持久记录发送意图；丢失回执保留 UNKNOWN，不自动重发。Worker/浏览器恢复只沿原 Run/Result 对账，不能恢复任意 JS 栈或盲目再次执行。

`SOURCE_IMPLEMENTED`、`COMPONENT_TESTED`、`CHROME_NATIVE_VERIFIED`、`PRODUCT_DONE`、`BLOCKED`、`NOT_TESTED` 分开记录。Node、内存编译和临时组件扩展均不能证明真实产品 Chrome 全链通过；第二 AI 网站没有真实完成/回传证据时保留未完成。

## 2026-11-11 · ChatGPT 项目文件 Headless Runtime 产品合同（OD-AI-WORKFLOW-BRIDGE）

**目标：** 正常使用 ChatGPT，不出现 WebFlow「项目文件／打开／×」悬浮调试 UI；原官网消息见证、完整回答、文件路由、已许可读取/修改不退化。任务状态、停止、错误与修改审阅由 OpenDesk 可信扩展界面完成，侧栏关闭不自动停止文件任务。

**唯一运行链：** 原 ChatGPT Bridge 发现轮次 → 无 DOM、无页面 Toast 的 Headless 文件 adapter → 原文件 Service / Controller → 旧 Native 工作区授权、稳定写入账本、SHA 校验、独立读回。未增加第二套 Runner、Host、文件授权或任务数据库。

**控制面：** 可信 WebFlow Side Panel「运行与授权」链接到现有 native-agent/settings.html#chatgpt-files-controls；「原文件任务管理」只读列出任务身份，按 sourceTabId / sourceDocumentId / projectId 查询原状态、停止任务，或在授权审阅时打开一次性绑定的原文件审阅页；未建立项目任务的人工操作也可从可信设置页选择当前窗口的真实官方 ChatGPT 主文档，经过二次文档核验后领取原一次性审阅入口。Host 校验设置文档 sender、真实原 ChatGPT tab/document、授权和当前项目，普通网页及沙箱不能冒用。文件正文、修改前后对比、完整回执仅在原授权实时有效时披露。

**故障边界：** Stop 立即标记同来源待执行操作，已派发副作用以真正回执结算；UNKNOWN 不换 ID 重放。撤权、来源更换或文件处理禁用时，历史正文隐藏。旧 diagnosticsVisible 保留作为向后兼容存储字段，不能重新生成网页悬浮 UI，也不代替 enabled 和文件授权。

**验收：** 网页源码与定向测试需证实无浮窗 DOM、单次发现、Stop 身份及撤权遮蔽；Node CI 与 Chrome/Native 分层记录。真实 Chrome、安装、Native 和用户对话未执行时均为 NOT_TESTED。
