## 0. 原始目标：我们究竟在解决什么

为使用 ChatGPT、Claude、Gemini、Grok、DeepSeek 等网页版 AI 的个人用户，规划 OpenDesk Browser 的 AI Insight 能力。帮助用户理解：

- 自己提出了哪些**真实问题**，而非只数消息、对话和模型次数；
- 一个问题如何跨多个 AI、多个对话、多个尝试被推进、搁置、恢复、解决或放弃；
- AI 的**可观察**请求耗时、长任务、等待、并行，以及用户可观测的切换与恢复成本；
- 每次尝试为何有效或无效，哪些回答被采纳，哪些成果有真实验收证据；
- 与个人/项目目标、计划、里程碑、知识和下一步行动有何关系；
- 如何在不鼓励多提问、多并发、多加班的前提下减少重复解释、无效返工并复用有效成果。

**具体场景**：同一个扩展 Bug 先在 ChatGPT 对话 A 尝试修复，AI 工作 40 分钟但测试失败；接着在 Claude 对话 B 排查；再回 ChatGPT 对话 C 完成修复与验收。产品应显示「1 个问题、3 段尝试、3 个关联对话、每次的观察时长/结果/证据/下一步」，而不是把 3 个对话误统计为 3 个问题。

**北极星方向**：每周经用户确认且有可追溯证据的有效问题推进数（有证据地排错、解除阻塞或合理停止也可算推进）。这是候选产品指标，并非经市场验证的最佳 KPI。

**竞争定位**：不再开发另一个泛用聊天搜索、时间统计、提示词库、知识库或自动化内核。差异化主线是 **问题身份 → 可解释过程 → 可信结果 → 可执行改进**。

## 2. 不得丢失的完整需求宇宙

16 个一级领域（不是 16 个必须立即开发的产品模块）：

1. 数据观察：站点/消息/执行事件、观察覆盖、来源可信；
2. 问题身份：跨平台同问题、子问题、相似关系、误合并纠正；
3. 解决过程：尝试、重试、修正、状态、放弃与重新开启；
4. AI 执行：提交、首响应、生成、完成、异常、分位数；
5. 等待行为：前后台、空闲、切换、并行、完成提醒、返回成本；
6. 提示词质量：目标、上下文、约束、验收、改写收益；
7. 回答质量：正确性、证据、可用性、完整性、采纳、修正收益；
8. 结果与成果：Artifact、验收、失败原因、价值与版本；
9. 目标与计划：Goal、Plan、Milestone、探索、偏航与目标变更；
10. 知识与经验：结论沉淀、历史检索、复用、过期提醒；
11. 时间与工作习惯：学习/探索/生产/审核/休息，不推断职业或注意力；
12. 多模态：文字/图片/代码/文件/音视频，区分输入、生成、引用；
13. 使用额度与成本：官方值、网页观察值、估算严格分列；
14. 复盘与行动：日报/周报/月报、阻塞、建议、采纳效果；
15. 协作与交接：有授权的团队成果共享，不把个人活动变成员工排名；
16. 隐私与控制：逐站点权限、正文单独同意、暂停、保留期、导出与删除。

这些是研究空间。优先级不能只按功能数量，也不能以「统计更全面」取代用户真实收益。

## 3. 仍须继续深入研究：P0 / P1 / P2 研究问题与验证方法

### P0-1：Problem 身份与问题范围漂移（第一优先）

**待解决**：同一 Bug 跨平台多对话如何识别？需求范围扩大后何时是新 Problem？一个对话里多个问题、父子问题、相似问题、方案变体如何区分？多人及跨设备引用会不会碰撞？

**设计约束**：
- Problem 使用本地稳定 UUID，不用标题、模型文本或向量哈希作为身份；
- 关系显式区分 SAME_PROBLEM / SUBPROBLEM_OF / RELATED / SIMILAR / DISTINCT / UNKNOWN；
- 强锚点同时包含命名空间，如仓库 + Issue 编号、项目 + 任务 ID、来源对话 ID；
- 语义相似仅用于提出候选，不直接合并。关系决策保留支持/反对证据、操作者和版本；
- 允许用户拒绝、撤销合并、拆分并触发派生统计重算；保存用户曾否定的关联约束；
- 问题目标、范围和验收标准可能发生版本变化，不能用新状态覆盖旧历史；
- 目标问题与「问了一次 AI」不是一对一关系。

**验证**：人工建立标注集，覆盖同问题跨 3 对话、同项目不同 Bug、相似但不同问题、父子问题、范围变更和错误合并。以候选 Precision/Recall、误合并率、人工审阅负担与纠错恢复完整度评估；无样本不得宣称 95% 精确率。

### P0-2：真实完成、验证与可归因结果

**待解决**：AI 说「代码已修复」、运行器返回 completed、用户点击「完成」、独立测试通过，究竟有何区别？相互矛盾的证据如何处理？失败尝试的排错价值如何记录？

**设计约束**：
- 区分 CLAIMED_BY_AI / RUN_RECORDED / USER_CONFIRMED / EVIDENCE_VERIFIED / UNKNOWN；
- Outcome 与 Evidence 多对多；Evidence 记录来源、对象、时间、版本、校验结果与有效范围；
- Run/Result 只能证明其合同内的操作结果，不能自动证明最终业务问题解决；
- 明确验收标准、证据缺口、已失效或被新测试推翻的结果；允许 reopen；
- 将「排除错误方向」「需求变更引起返工」「AI 内容错误」「环境/权限阻塞」分别归因。

**验证**：构造 AI 声称成功但测试失败、历史成功后来回归失败、人工确认但缺技术回执、工具回执成功但目标失败四类 fixture。

### P0-3：长任务、观察缺口与并行时间真值

**待解决**：网页冻结、后台节流、刷新、浏览器重启、服务工作线程终止、页面显示运行但实际中断时，时长是否还能准确推导？跨设备时钟如何统一？

**设计约束**：
- 保留 SUBMITTED_OBSERVED、FIRST_OUTPUT_OBSERVED、OUTPUT_PROGRESS_OBSERVED、COMPLETION_OBSERVED、STOP_OBSERVED、ERROR_OBSERVED、OBSERVATION_GAP、STATUS_UNKNOWN、REGENERATED；
- 页面没变化不等于完成，网页执行状态不等于服务端计算状态；
- 区分提交到首响应、可见生成时长、请求墙钟跨度、问题解决周期；
- 累计响应时长是时长**总和**；并发墙钟暴露是区间**并集**；用户实际工作时间两者都不是；
- 两请求例：A [0,40] 分钟，B [10,35] 分钟，总和 65、并集 40、重叠 25；
- 缺失完成事件时保留区间不确定性和右删失状态，不补造完成时间；
- 指标呈现 P50/P90/P95 前需声明样本数、观察覆盖、统计窗口；时钟与时区改变不能伪造精度。

**验证**：模拟时钟+确定性测试覆盖 30/60 分钟、并行、重复事件、异常中断、可见/隐藏变化、暂停/撤权；真实 Chrome 另作有授权的站点测试。

### P0-4：真实多 AI 站点适配可行性

**待解决**：ChatGPT、Claude、Gemini、Grok、DeepSeek 哪些提交/回复/完成信号可稳定识别？虚拟列表、再生成、工具调用、流式长响应、登录变化如何处理？

**设计约束**：
- 每站点独立 Adapter 版本和能力矩阵（可识别会话、提交、首次输出、完成、再生成、附件）；
- 仅按精确获批 Origin 采集；不因主扩展广泛权限而自动扩大业务授权；
- 站点 DOM 变化时适配器必须降低覆盖标识、退出错误统计，不能从其他站点选择器猜测；
- 不为调研自动发送私人对话消息；无授权实站记 BLOCKED/NOT_TESTED；
- 先验证两个适合的站点，再扩展其余平台，不能把研究中提及的五个平台当成均已支持。

**验证**：对真实或合规受控页面建立站点能力表、版本、观察证据、失败与恢复条件。

### P0-5：用户实际负担、隐私和信任

**待解决**：用户是否愿意一直关联 Problem、确认结果？弹窗、提示、授权是否干扰思考？正文泄露和模型外发风险如何控制？

**设计约束**：
- 元数据观察与正文语义分析分级授权；正文分析需单独明示范围；
- 可随时暂停、撤权、导出、按 Problem 删除、清空派生统计，云/外部模型另行独立授权；
- 不以安装、全站访问权限或已启用其他工具推导 AI Insight 同意；
- 仅在高价值时建议关联，优先不打断用户；探索与休息不打低效标签；
- 隐私删除覆盖索引、派生指标、缓存和可控副本；不能冒称外部副本已删除。

**验证**：带回放的可用性测试，记录操作步骤、完成率、误点、人工确认成本；撤权、跨 Origin、删除与残留专项测试。

### P0-6：从图表到真正有用的下一步

**待解决**：用户打开数据后做什么？哪些建议是真的可执行？任务恢复摘要是否比普通统计更有价值？

**设计约束**：
- Side Panel 首屏优先「当前问题、已知结论、待验证、下一步」；
- PC 展示问题关系、尝试时间线、证据、返工、等待与复盘；
- 所有建议展示触发条件、证据、风险、用户可选动作；允许忽略和关闭；
- 严禁把持续使用、更多提问、更多并发或更长工作时间当成功效；
- 不强迫先配置大而全的目标/计划体系。

**验证**：针对「跨对话继续修 Bug」「恢复上周研究」「AI 声称已完成但未验收」三场景评估任务恢复时间、遗漏率与实际采纳反馈。

### P1：高价值扩展研究（先保存，不扩大 R5 范围）

| 议题 | 关键研究问题 | 建议依据 |
| --- | --- | --- |
| 恢复成本 | 返回时重新阅读、重新定位文件和重建上下文花多长时间？ | 经授权事件 + 用户确认；不能全算主动工作 |

| 知识过期 | 历史成果与当前版本、环境是否仍适用？ | Artifact 版本/有效期/复验时间 |
| 个人成长 | 学习、探索、生产、审核的习惯变化是否稳定？ | 长期同意、避免推断个人能力 |
| 推荐效果 | 建议是否真的降低返工或恢复成本？ | 可选 A/B、前后对照、用户反馈及反向指标 |

### P2：暂缓能力（仅保留假设）

- 完整北极星目标与项目管理体系：与现有任务/知识能力边界尚需验证；
- 全平台历史自动导入：存在账号、可得性、授权、历史缺失及成本问题；
- 多模态全面识别、精确费用与额度分析：需分离官方值、估算与未知；
- 团队共享与商业化：必须先解决默认私有、最小成果共享和反监控设计；
- 手机使用与真实注意力推断：网页扩展无法可靠观察，禁止伪造；
- 自动全天候监控与不必要的并发建议：风险大，非首版价值核心。

## 4. 统一数据与证据口径（待转化为可测试 Schema）

### 4.1 核心实体

Goal、Plan、Milestone、Problem、Attempt、Conversation、Turn、Prompt、Response、Execution、Observation、Artifact、Evidence、Review、Outcome、Recommendation。

- Goal/Plan 是目的与计划，不是每条 Prompt 的必填归属；
- Problem 是稳定问题身份，Attempt 是尝试，Conversation 是平台容器；三者不能混为一物；
- 一个 Problem 多 Conversation；一个 Conversation 多 Problem；一个 Attempt 可跨多个对话片段；
- 一个 Prompt 可对应不同再生 Response；每次 Execution 独立，有自己观察状态和缺口；
- Outcome 不应仅由 Answer 的语义判定，必须标注证据等级；
- 记录 Event ID、source、adapterVersion、observedAt、scope、consentVersion、identity、coverage 和 dedupeKey；
- 分离原始事件、可复算派生指标、AI 推断、用户确认、独立验证及用户反馈。

### 4.2 可信度等级

- O：获授权且确实观察到的事件；
- D：从完整 O 按明示公式计算的派生值；
- I：有来源但未校准的 AI 推断/建议；
- C：用户主动确认的状态；
- V：在限定验收条件下经独立回执/测试验证；
- U：目前不可观测或数据不足。

对「问题已解决」「用户注意力」「实际服务端计算时间」等标签，缺证据时显示 U，不以 I 代替 V。

### 4.3 时间口径

- TTFV = 首次可见输出时间 − 观察到提交时间；
- 生成观察时长 = 完成观察时间 − 首次可见输出时间；
- 请求观察跨度 = 完成观察时间 − 提交观察时间，仅在区间与归属有效时给精确值；
- 单 Problem AI 时长总和 = 相关可信 Execution 各自跨度相加（并行允许重叠）；
- 并发跨度 = 对各可信执行区间求并集，不能和上一个值混用；
- 解决周期 = 首次可确认开始到符合定义的验收/关闭时间；未关闭计右删失；
- 浏览器前台时间 ≠ 用户注意力；用户等待 ≠ 全部浪费；用户在线 ≠ 服务端仍运行；
- 只从授权以来真实发生的事件生成时间线，历史导入或空白区间不反推秒表。

### 4.4 数据质量与偏差

去重需要覆盖重复 DOM Mutation、刷新恢复、跨标签观察、重复事件入账、重新生成（必须算新 Response）与多问题共享同一次回答（全局只计一次）。对于 P50/P90/P95 记录样本数、窗口、覆盖率与右删失。复杂任务更可能跨 AI 迁移，不能直接据均值宣称某模型更高效。已确认与未知的结果必须分开作为分母展示。

## 6. MVP 的明确取舍

R4 评估三条路线（主观加权评估、非用户调研）：A 统计+提示词 79.2，B 问题+等待 90.4，C 目标+成果 79.8。选择 B-Lite。

**首版应优先体验：**
1. 已授权两个平台的元数据观察、请求计时与覆盖提示；
2. Problem 创建、关联候选、人工确认、误关联撤销；
3. 问题/Attempt/Conversation/Execution 时间线；
4. AI 声称完成与用户/独立验收分级；
5. 下一步和可编辑工作恢复摘要；
6. 少量有证据的复盘与建议。

**首版暂缓：** 大型目标管理、复杂团队分析、全量历史抓取、所有站点同时支持、完整提示词评分、精确 token/费用推断、自动发送或无授权外部模型语义分析。

**界面分层：**
- AI 网页：极轻量问题关联/状态/完成提醒入口；不遮挡网站；
- Side Panel：当前问题、结论、待验收、继续工作、关联与撤销；
- PC：问题中心、执行与并行时间线、证据成果、复盘、覆盖和隐私；
- Single App · Multiple Surfaces，使用现有统一外壳，数据与动作合同一致。

## 8. 反方与数据伦理检查

每次设计与实现都要反问：

1. 用户真的需要这个功能吗？是否只增加了仪表盘复杂度？
2. 指标是否可靠？是否把不可观测状态伪装成事实？
3. 是否为提高分数鼓励多提问、多并发、持续工作或抑制休息？
4. 是否把探索/失败误判低效，或用 AI 对人的能力/职业进行武断判断？
5. 跨模型迁移和提示词质量的结论是否被问题难度、样本选择或观察缺失混淆？
6. 是否重复 Time Review / Knowledge Inbox / Web Flow / Prompt Shortcuts 的既有底座？
7. 是否有正文采集、第三方传输、跨账号混合、删除不完整、团队监控风险？
8. 如果平台原生提供统计/搜索，本产品还是否因问题身份与成果验证而有独立价值？

## 9. 优先验证的成功门槛（拟议，不是当前成绩）

- 问题候选关联：先建立独立标注集和解释证据，再评估精确率与人工确认成本；候选 Precision 目标 ≥95%，不能据模型置信度冒充真实准确率；
- AI 观察：明确事件覆盖率、错报完成率、数据缺口；提议关键事件覆盖目标 ≥95%，完成错报率目标 ≤1%，必须在可观察且有授权的样本里核验；
- 用户价值：用户能独立关联、继续、验收问题，记录恢复用时、误关联率和可感知实际收益；
- 隐私安全：关键撤权、跨站、正文访问、删除及外发测试全部通过才可以进生产。

实际未执行标 NOT_TESTED；环境不可用标 BLOCKED；评分高不能覆盖缺陷。八专家需独立给出百分制评分与扣分理由，最终用算术平均而非累加，力争 ≥95，但不得为凑分伪造结果。
